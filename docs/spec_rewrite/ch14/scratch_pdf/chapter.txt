14. Stopped-sim services
§9.6 previewed the services as activation clients. They are initialization, trim and linearization.
Everything they share reduces to one artifact, the condition value. A condition is the datum that
says "set this build to this state." §14.1–§14.4 settle its representation, composition and application.
§14.5–§14.6 cover the boundary-zero sequence and root-input totality (the requirement that an
application establishing a complete world cover every root input). §14.7–§14.9 cover the trim service
in full. §14.10 covers linearization. A fourth stopped-sim service, checkpoint, returns a checkpoint
(the Model's state at a frame top as one value). A checkpoint is not a condition and has no algebra,
and restore! puts it back (D-273).
Lifecycle preconditions. Every service requires a non-running simulation. While a run exists the
loop owns the stores between drains (the frame-top swap that publishes staged device writes into
the root inputs), and a service reading or writing them would race it. Pause is no exception, by the
doctrine that freezes the roster. Pause is a control-plane state inside a run, so a prohibition that holds
mid-run holds while paused (§11.3, §12.1).

14.1 Conditions are path-addressed overlays on the declared defaults
A condition may specify state fields (x on the continuous tier, s on the discrete) and modes (m,
continuous components only, §3.2). All three are addressed by a §8.6 slash path plus a field name. It
may also specify root inputs, addressed by face. It never specifies outputs, which are derived data.
It never specifies workspace (component-declared mutable scratch arriving as the ws bundle field).
Entries are validated in the §13.1 collecting form. The full list is checked, violations are collected,
and one DiagnosticError is thrown.
The overlay base is always the declared defaults. Every store has a declared initial value
(declaration-by-initial-value, §8.2), so conditions are naturally sparse. Applying one means "fresh
run from the x_init, s_init and m_init defaults, with these overrides" (D-063). A condition is an
initial condition and nothing else (D-273). A simulation's state past its initial instant is a checkpoint
(the Model's state at a frame top as one value), not a condition, and it has no algebra (D-274).
Doctrine. Addressing conditions by path does not reopen the observation-by-path rejection (§13.5).
That rejection was about runtime coupling, where a root-authored predicate reaches through
generic seams the root does not own and breaks on substitution. A condition is a design-time
statement about a concrete build. It is authored in the same vocabulary as local_wires, which also
speaks paths, about children its author owns. The composition law (§14.2) makes the parallel exact.
Pre-sweep doctrine. Condition writes precede the first sweep by definition. A would-be init value
that depends on swept outputs is therefore either analytically known to the caller or an equilibrium
constraint. The first case is trim's α_filt = α_a. There α is a decision variable, so the value is known
above, not computable below. The second case is a job for the trim service, not for init.
"Caller-computable" reaches past closed-form knowledge to environment queries. A condition
needing one constructs the same handle the sweep will produce, and then calls the same query
function the consuming component calls. There are two routes to that handle. One is the value-level
constructor (the plain public function building a field handle from the component and input values,
§8.2), applied to the same values the baseline writes into the environment component's root inputs.
The other applies in a rig where an isbits handle itself is a root-input value (§4.4, D-364). There the
condition simply holds the value the baseline wrote. Either way there is one implementation of the
field math, evaluated one level up, with no pre-sweep and no new mechanism. Where closed-form
enforcement of a target is not wanted at all, the second escape already covers the case. Promote
the eliminated state coordinates to decision variables and enforce the targets as residuals on swept
outputs. That route needs no environment access at condition time whatsoever.

14.2 Fragment composition: locality without schema
Init knowledge is component-local. The engine knows n_eng → ω = n_eng·ω_rated, and nothing above
it should have to. Making that locality a schema entry was rejected (D-064). That spelling would
declare initialize(::C, spec), today's f_init! reborn declaratively, and add an assembly-level rule
routing sub-specs to children.
What preserves the locality is an idiom, not schema. It is the condition method, a method of the
framework's condition generic, shipped beside the component and dispatched on the component,
returning the component's own fragment. The generic is framework-owned so that an owner's
pull reaches a child's fragment across a package seam. A model package extends it through import
Redstone: condition, as it extends the declaration family (§8.1). No shadowing check covers it: a
method written to a foreign condition fails loudly at the owner's pull, as a MethodError naming
the child.

The locality law here is the one §6.1 states for connections, now in its third instance. The three
instances are local wires, computed interface connections and conditions. Each level speaks its
own fields, its declared children's names, and its own faces. Delegation runs by dispatch at every
genericity seam. An at prefix may stop at any child's faces, owned or generically held, because the
face graph is total (D-207). A deep at or condition path resolves wherever the structure has it (§13.3,
D-414). Absolute paths exist only in the flattened entry list, a compiled derivative of the composition,
as cell offsets are of local_wires. Substituting a component invalidates precisely the fragments its
owner shipped, nothing else. The build checks the law wherever it can see what the law constrains.
Wiring resolves one level (§6.1). The faces a u payload names resolve through the export chain,
under any at prefix (D-207). No check refuses a deep path past a generically held field (D-414). An
author who ships a fragment for a family scopes it by dispatch on the holding's type parameter,
so a fragment reaching into one powerplant is defined for the aircraft that hold that powerplant.
Ownership alone is convention. It is a fact about who maintains the code, and the build cannot see it,
so keeping a deep path inside an owned subtree is idiomatic rather than machine-checked (D-065).
set/at/combine are §13.7 standard-library material, ordinary artifacts with no privileges.
A combine collision is two entries on one leaf. Collisions are errors at resolution, and the error
reports both origins. The message names the layering combinator: "combine is collision-intolerant
by design — use override(base, patch) to layer." Last-writer-wins was rejected (D-065). That
rejection is also why the combinator is not Base.merge, and is no longer named after it (D-204).
Base.merge is last-wins on NamedTuples, the exact semantics rejected here, and its own name
should not promise them. Because combine is its own function, a bare NamedTuple blended into
a node cannot fall through to any last-wins method. The blend is still closed explicitly. A
combine(::Fragment, ::NamedTuple), or any other blend of a condition node with a bare NamedTuple,
is an error method. Its message is directive: wrap the NamedTuple in set(…) (or at(prefix, set(…)))
and combine nodes with nodes. The rejection carries a kind like every other. It is ConditionNodeMisuse
(Appendix C), carrying the offending argument's type and the node kinds in hand. It is raised at
composition time, before any resolution pass runs or any origin exists. That is why it is its own
kind and not a ConditionResolution sub-kind (§14.3). The explicit, ordered layering spelling, override,
belongs with the use case root-input totality produces (§14.6).
14.3 Resolution: flatten, validate, compile once
Resolution takes the root node plus a Build. Flattening is the only place path strings are ever
concatenated. It is a trivial recursion with a path accumulator, and it also records each entry's tree
position, its getfield/getindex step tuple.
The collecting pass then checks each flat entry:
• the path resolves, with did-you-mean (the offending name plus the list-in-hand it should have
matched) over children;
• the field is declared in the target's x_init/s_init/m_init;
• the value type is convertible to the declared leaf type;

=====PAGE 5=====
• input faces reach root inputs;
• no (path, store, field) is duplicated.
The Build supplies two lookup families. Schema is the evaluated declarations, and it is the authority.
It answers whether you may write this field, and at what leaf type. Layout is the destination. It
holds the x backing ranges, the store indices for s and for m, and the root-input indices from the
activation (the build's typed products at a given scalar type). The names and the face chains come
from Structure (the structure step's product, the components, wires, faces and tiers), never from an
activation, since no activation fixes them (§9.1, D-253).
A valid list compiles to a plan. Per leaf, the plan holds a lens (the compiled navigation step of a
condition entry), a destination offset, and a converter. The lens is the position tuple lifted to a type
parameter, so navigation of the fixed tree type is type-stable.
Rule. The converter is baked now, selected per leaf from that leaf's type in the resolved shape.
Why. Leaf types are shape facts, carried by the tree type along with the full nesting and every field
name (§14.4). Selection therefore consults no runtime fact and stays a resolution-time bake.

14.4 One plan, two ways to apply it
The paradigm-change tax feared at execution does not materialize. All string work, validation
and addressing are functions of the shape of the condition (the path-addressed sparse overlay
that sets a build's state). Every hot path holds the shape fixed while varying values. Execution is
therefore resolve-once/execute-many, with two ways to apply one plan.
• Specialized apply! serves the service that iterates, trim's per-evaluation write. It unrolls stores
through the baked lenses and converters. Those are the same machine operations as today's in-
place writes: zero-alloc, no strings, no dispatch. The per-iteration shape check is the mechanism
of §9.5 transferred. The tree type is proven by dispatch, and it carries the full nesting, every
field name and leaf type. A =
=
= sweep over the prefix strings closes the remainder. =
=
= on strings
compares content, so a prefix computed at run time pairs with the compiled one exactly as a literal
does, at the cost of one short comparison per at node. Shape drift (a tree of another type, or a
prefix that differs at a position) is ConditionShapeDrift (Appendix C), a structured error rather than
silent corruption. The cost is Julia codegen once per condition shape, and it grows with the shape's
writes. On Julia 1.13 it measures 10 to 50 ms up to 32 writes, 0.09 s at 64 and 0.2 s at 128 (docs/
reports/20261002_tuple_walks/). That cost is noise against the model's own first-sweep warmup
(seconds), and against the 10³–10⁴ optimizer evaluations the codegen amortizes over.
• The dynamic walk serves the one-shot uses, init! and linearize's operating condition. It
executes the same validated entry list by runtime dispatch per write. That takes microseconds
in total, with allocation permitted, since the stopped-sim path was never under the zero-alloc
regime (§9.8). It needs no per-shape codegen. Fifty structurally different scripted conditions cost
fifty walks, not fifty compiles.
Rule. Which of the two a service uses is internal, never user-facing API.
A compiled plan or reader carries the activation it was compiled at and applies only to a store set of
that activation. That pairing is a framework invariant the services uphold, not a user-facing check.
Neither plans nor readers are user values.

The names carry a deliberate get_ prefix. A selector is a deferred read, a value describing the read the
compiled gather will perform. The prefix names that action, and it keeps five short common nouns
out of the namespace user declarations share with domain code.
There is no selector for a value a component computes without declaring it, and there cannot be one,
because only cells are addressable (§4.2, §8.3). So a reader that wants one is asking the producing
component to declare it an output (§8.3). get_face addresses an output face of the mount level, the
level its read set is mounted at (§14.9). At the root that face is root-exported. Either way the read is
an integration read (§11.2).
Rule. A selector resolves against a source, before any client policy applies.
The table selectors (get_output, get_input, get_face) resolve against a table source. A table source
is a boundary snapshot, or the scratch tables a service evaluation instantiates (§14.8). The store
selectors (get_state, get_deriv) resolve only against live stores. The table/store axis separates table-
borne values from store-borne ones, not snapshots from services.
Only stopped-sim service evaluations, checkpoint, and post-run inspection of the live stores (the
replay-to-inspect, §11.2) ever hold live stores. The snapshot deliberately carries no state stores
(§11.2), and ẋ buffers are integrator scratch, not boundary-consistent objects outside a service
evaluation. A reader resolving for a table source that names a store selector is therefore refused at
resolution, as a ReadResolution (D-406). The resolver takes the source it resolves for, so the rule is
the resolver's and not a client's. The honest remedy (§11.2) is to declare the field in y_types, return
it from y_state, and read the resulting port (§5.3).
Client policy rides on top. It is D-083's service and inspection sides restated as a resolver property.
• Service reads speak the contract. Trim's reads and linearization's taps (the three selector lists
declaring what linearization seeds and reports) name get_state/get_deriv/get_output/get_input/
get_face. They do so within the scopes the locality law (§6.1) and fragment scoping (§14.2)
describe, as authoring guidance (D-414). get_face is the set's seam-crossing member. It resolves
through export chains exactly as mounting (relocating a whole problem or tap set with at(prefix,
…)) resolves root input faces (§14.9), so the read side mirrors the write side. An equilibrium
equation meant to outlive the build it was posed against therefore binds the curated face behind
a generically-held child rather than a path into it. A service evaluation needing an undeclared
intermediate has one remedy, and it is the same for every client. The component exports it (§14.7).
• Inspection readers admit the whole family, within the source rule. Output-device bindings,
log extraction by series and snapshot inspection take deep paths, get_face names and leaf
addresses alike (D-406, D-407, D-414). The store selectors reach only the inspection clients that
actually hold stores (checkpoint, post-run inspection). A snapshot-bound reader is barred from
them by source, not by client.
• ignore_stop_requests is not a family client. It names requesters from the Build's requester roster,
period (§13.5, D-060, D-316). Termination is run policy over the requests the model declares, and
no path selector reaches ignore_stop_requests.

14.5 Boundary zero: an ordinary boundary with authored incoming transitions
apply! establishes the stores at t₀. The init service then completes the §10.6 macro-sequence with an
empty integrate. The sequence is project → [sweep → guards → handlers]* → due s_update calls
→ first snapshot. After the first snapshot init! takes the trace header, the checkpoint (the Model's
state at a frame top as one value) of the state the sequence leaves (§11.5, D-274). The parity with an
ordinary boundary is exact, not approximate. The pieces follow one by one.
• Project runs. Authored x can sit off-manifold. A hand-assembled quaternion may be ulps off unit
norm, or a condition (the path-addressed sparse overlay that sets a build's state) may write part
of a constrained block against fresh defaults. Projection after condition writes holds the same
position it holds after any other x mutation. And it costs nothing when the state is already clean.
• The sweep runs, and every discrete output stage publishes, due or not (D-205). t₀ is a grid
point of every phase-free divisor, so the Φ = 0 components are due in full. An offset component
(§10.5) is not due, because its first tick is at Φ·Δt_base. Its output stages run at boundary zero all the
same, publishing from the authored s and the t₀ table in the ordinary sorted walk. That evaluation
is establishment, not a scheduled sample. The schedule owns every instant after t₀, and the first
sample the component's s_update consumes remains its Φ·Δt_base tick's. What the rule buys is
a t₀ snapshot carrying the authored world fully evaluated. No published cell holds the probe's
synthesized values. That is the §14.6 barrier extended from the root inputs to the whole table.

• Events run. A condition can land a guard predicate in holding territory (firing on not-holding
→ holding transitions, never bare sign changes). An authored stall flag, or a strut authored into
contact, does exactly that. The event then fires visibly at t₀ rather than one step later. The prior
rule grounds that timing (§10.6). Boundary zero establishes every guard prior (the event's stored
predicate sample from the previous boundary) as not-holding. Suppressing those firings was
rejected (D-067), on the stage-on-interaction lesson of §11.7 (widgets stage on edit or activation,
never per render pass). Insurance that masks invariant violations is anti-diagnostic (D-026). The
trace header is taken after the sequence (§11.5). Replay restores it and runs no boundary zero,
so whatever fired at t₀ comes back as part of the restored state and never fires twice (§12.7).
The checkpoint records the post-firing state faithfully and suppresses nothing. A stop request
already reading STOP_REQUESTED is a different category. Nothing fires. The request simply holds in
the published t₀ snapshot and the loop reacts (§13.5).

• Trim is untouched by all of this. Optimizer iterations are raw write → sweep → read cycles

• A guard firing at commit is a wanted failure signal. Today's hand-written trim asserts (!

the verdict was read at. Both movers take the same remedy, specified with the report in §14.8.
14.6 Root-input totality: the missing-value error and the override combinator
Root inputs are the one initialized datum without declared defaults. That is the bare-types decision
(§11.3), upheld here (D-068). So a root input's only source before boundary zero (the initialization
boundary: the ordinary macro-sequence with an empty integrate) is the condition. Three consequences
follow.
Totality is a precondition of starting, checked by the service. A condition value is legitimately
partial. Fragments compose, and trim iterations write subsets. So "every root input covered" is not
a property of conditions. It is a property of every application that establishes a complete world over
virgin stores. That principle, not an enumeration, names the sites. They are init!, trim's setup application
to freshly allocated scratch stores, and trim's commit through boundary zero (§14.8). That
is one class, one mechanism and one kind. Each compares the resolved plan's root-input coverage
against the Build's input_faces before writing anything. A shortfall is one collected, declaration-
ordered diagnostic (UninitializedInputs, a §13.2 kind) naming every uncovered face. Coverage is
a plan-level fact, because both operands are resolution-time data. The check is therefore one
comparison, and it runs before any evaluation, not merely before any write. Pre-write means all-
or-nothing. A rejected init leaves the sim exactly as it was, the same posture as failed trim.
The probe-value barrier is structural. The probe_value synthesis (§9.3; zero/false/first-enum/
T()) exists so build-time probes can exercise code with fabricated inputs. A fabricated zero is a fine
probe input and a terrible flight condition. A silently zeroed mixture kills the engine and sends the
user debugging aerodynamics. The services path simply contains no call to it. A root input gets a
condition value or the application errors, with no third branch. Replay likewise never synthesizes.
The trace header holds every root-input cell as boundary zero left it, and with totality enforced that
record is complete by construction (the requirement discharged, §11.3).
Baselines are aircraft-shipped condition functions, layered by override. Nobody hand-
writes ~20 root-input values per script. Today SystemsInitializer's @kwdef defaults carry that load.
Their successor is ordinary user math in one authoritative home, such as ready_for_taxi(ac) or
cold_and_dark(ac), returning full-coverage conditions. But "baseline plus tweaks" collides with the
duplicate-leaf error (§14.2) by design. The collision is the intent. Hence the fourth node kind,
override(base, patch). It is ordered and asymmetric, where combine is symmetric and collision-
10
=====PAGE 11=====
intolerant. At resolution a leaf present in both takes the patch's value, with the origin recording both
layers ("patch overrode base's throttle"). Collisions within one layer remain errors. Variadic layering
(override(campaign, aircraft, todays_case)) composes. Trim uses it on day one. The committed
condition is override(baseline, solution), the solver's handful of values over full coverage (D-068).

solve because they carry no information for it (D-262).

14.8 The trim service: solver seam, scratch stores, commit and report
A TrimProblem is an inert value until a service runs it. trim! is that service. It drives a solver it holds
behind one method, works on scratch stores of its own, commits a converged solution the way init!
would, and returns a report.

=====PAGE 14=====
The backend seam
The signature is trim!(model, problem; baseline, t0 = 0.0, backend = LevenbergMarquardt()),
where model is a Model (a deployment materialized at one scalar type) at Float64 (D-319). trim!(sim,
problem; …) gates on the simulation's lifecycle and commits through the simulation's init!. The
default backend is an in-house dense Levenberg–Marquardt. For decision dimensions ~10 with exact
Jacobians, the core is ~100 lines: a damping loop, a small linear solve, a convergence test. That is the
§10.2 stepper precedent exactly, a tiny needed core against a heavy dependency. The per-residual
physical tolerances sharpen the case (§14.7). They are a convergence test no external package spells
natively. That is precisely why the service, not the backend, applies it.
The backend contract is a pinned signature, value-passed, with one required method per backend.
That one method is the seam.
solve(backend, eval!, d0, lower, upper, tol) -
> (; d, status, n_evaluations, n_iterations)
eval!(r, J, d) is in-place and always fills r, the residual vector packed in tolerances' field order. It
fills J iff J !== nothing. The Jacobian is requested by argument, so a Jacobian-free backend simply
always passes nothing, and there is still exactly one evaluation method to implement.
d0, lower and upper are packed Vector{Float64} in guess's field order, with ±Inf meaning unbounded.
The declared side is canonical on both ends, and the service has canonicalized before packing (§14.7).
A backend that ignores bounds therefore ignores two vectors, not a missing argument.
tol is a Vector{Float64} in tolerances' field order. It is data the backend may stop on, under the
service's per-backend-family translation below, and it is decisive of nothing.
The return holds d, the solution, status::Symbol from a deliberately open set, and the diagnostic
counts n_evaluations and n_iterations. The status is recorded verbatim in the report because the
verdict is the service's (D-158). The name solve is subject to the exported-name audit (pending.md)
like every other API spelling. The backend sees vectors and never names, so the solution it returns
unpacks by the same order it was given.
The convergence verdict is the service's, uniformly
converged means all(abs.(rᵢ) .≤ tolᵢ). That is the per-residual box test (§14.7) in its own physical
units, evaluated by the service at the backend's returned point. It is one residual evaluation,
noise against the solve that produced it. That verdict, and nothing else, gates the commit and fills
TrimReport.converged. The backend's returned status is recorded in the report as diagnostic data,
and it is authoritative over nothing.
The tolerance translation, per backend family
The tolerance translation is the service's too, per backend family. In least-squares backends the
tolerances are the stopping criterion. They feed the per-residual test directly, so LM's damping loop
tests exactly what the service will re-test.
The derivative-free scalar fallback is NLoptBackend(:LN_BOBYQA) in a package extension. It passes
nothing for the Jacobian, keeps today's algorithm one keyword away, and leaves the framework
core carrying zero optimizer dependencies. For that fallback the service squares and normalizes.

in the report: "converged with elevator at its upper bound". That is the classic CG-limit diagnostic,
today inferable only from mysterious residuals.
Scratch stores, stated without type luck
Every trim! invocation instantiates a fresh working store set. Each half of it (below) is a scratch
Model of its own, materialized from the deployment the service was called on (D-317, D-319). The set
holds the x backing, the s and m stores, the root input and signal tables, and the derivative buffer. The
set is built from the activation's layout (the build's typed products at a given scalar type). The layout
is the reusable compiled artifact. The buffers are per-invocation and die with the call (stopped-sim
allocation, §9.8). Each set also calls every workspace allocator once, at the activation's scalar (D-077).
The Dual backend's buffers being un-aliasable by type is defense in depth, not the mechanism. A
Float64 backend (NLopt) gets equally fresh buffers. The invariant is backend-independent. The
simulation's authoritative stores have exactly one writer, the commit through boundary
zero (the initialization boundary: the ordinary macro-sequence with an empty integrate).
Setup applies override(baseline, condition(guess)) to the scratch set once, and that application's
full coverage is checked here. The check is the comparison of the resolved plan against the Build's
input_faces (§14.6), one plan-level comparison before the first evaluation. Sweeps therefore see a
complete world. Raw instantiation is sound exactly because of that check, since every root input is
written before any read. An incomplete baseline is one declaration-ordered UninitializedInputs at
setup rather than a whole solve against undefined cells.
The frozen cells are established, not probe-seeded. At the seeded activation the discrete tier is
frozen (§9.4). Its stages never run there, so nothing at that activation can derive a discrete output cell
from the authored s. Setup therefore instantiates the scratch set in two halves. A nominal set takes
the composite first, by the dynamic walk (§14.4), and runs one establishment round. That round
is boundary zero's sweep with every discrete output stage admitted, due or not (D-205), with no
projection, no guards and no s_update. The seeded set is then written by the specialized apply!, and
its frozen cells are copied from the nominal set as zero-partial constants (the embedding of §14.3).
Every cell the iterations read is thus derived from the authored world. A frozen cell holds what the
authored discrete state publishes, which makes "held at the operating point" literal. No scratch cell

=====PAGE 16=====
holds the probe's synthesized values. That is the §14.6 barrier reaching the scratch world, as D-205
made it reach the published one. The iterations are untouched. They are raw write → sweep →
read cycles at the seeded activation, over the continuous chain and x_deriv alone (§14.5). The zero-
decision problem (below) is the nominal half alone, and its one evaluation is that establishment
round (D-213).
The commit applies the same composite over the same baseline (override(baseline, condition(d*)),
§14.9), so its coverage is setup's. Commit's totality check is therefore structurally unfailable through
the trim path, and it stands as the shared init!-boundary defense. A converged solve is always
committable. TrimReport therefore carries no committed flag, and the no-throw doctrine needs no
exception.
Iterations rewrite the composite's write-set via the compiled plan. The write-set is
override(baseline, condition(d)), the same tree setup resolved, so a store both layers touch merges
exactly as it did at setup. An LM evaluation is one Dual-seeded sweep yielding r (value parts) and
J (partials) together. No convergence means no commit. Non-convergence is the service's box test
failing at the returned point, whatever status the backend attached to it. No commit means the
sim is bit-for-bit untouched, including "never initialized". Today's warn-but-assign is structurally
impossible.
The same structure covers an interrupt. Ctrl-C during a long solve unwinds an ordinary Julia call
operating on per-invocation scratch stores. No commit has happened, and the simulation is bit-for-
bit untouched, exactly as a non-converged solve leaves it. The services need no counterpart to the
loop's boundary masking (§12.4).
The commit, in full
The committed solution is applied as an init! in every respect. It is override(baseline, solution)
through boundary zero, with the pre-write root-input totality check (§14.6), the sequence (§14.5)
and guards at commit.
The t0 argument that anchors the grid, and its default, are the same for both init-service entry points
(§14.5). The recorders restart exactly as §12.6 states for init!. The trace and the log are new objects,
and any batches still in staging cells (where a device's pending write batch waits between drains)
are cleared.
A fresh recording starting at its own anchor is unattended mode's natural shape. A trim at a point
reached by flying is not offered. Trim takes an authored baseline. Fly-then-retrim is checkpoint the
flight, then author the trim's baseline from what the checkpoint (the Model's state at a frame top as
one value) shows (D-273).

The AD obligation, scoped
The default formulation requires Dual genericity of exactly the continuous output-stage chains and
x_deriv, plus the user's assignment and residual math. The discrete tier's stages and s_update, and the
event system's guards and handlers, never see a Dual. They are frozen constants with zero partials,
semantically exact (§8.2).
This is not a new obligation. It is the same activation linearization is defined on. AD-readiness is also
a build-checked property. The Dual probe detonates pinned intermediates with a culprit-naming
InexactError, and build(world; activations) puts it in CI. The robustness comes from enforcement,
not hope.

14.9 Mounting: problems as relocatable values

a condition-valued function over the decision space. reads/residuals are the equations that pin the
free variables down. guess/bounds say where to search. Solving makes the implicit condition explicit.
The commit is then literally an init, override(baseline, condition(d*)) through boundary zero (the
initialization boundary: the ordinary macro-sequence with an empty integrate). The services unify
as clients of one condition algebra. init! applies an explicit condition, and trim! searches a family
for the member satisfying its equations.

14.1 Conditions are path-addressed overlays on the declared defaults
A condition is the value an author writes to say which state a build starts from. This section covers,
in order, what a condition may specify, the overlay base, why addressing a condition by path is
legitimate, the pre-sweep doctrine and the environment queries a condition may make.
A condition may specify state fields, x on the continuous tier (one side of the hybrid formalism)
and s on the discrete. It may also specify modes, m, which only continuous components have (§3.2).
All three are addressed by a slash path (§8.6) plus a field name. Beyond state, a condition may
specify root inputs (the root's own input faces). It addresses them by face (the name a port wears
on its component's boundary). It never specifies outputs, which are derived data (D-063). It never
specifies workspace (component-declared mutable scratch arriving as the ws bundle field) (D-306).
Condition entries are validated in the collecting form (§13.1). The full list is checked, violations are
collected, and one DiagnosticError is thrown. A condition entry naming an output or a workspace
field is one such violation, ConditionResolution with reason :undeclared_field (Appendix C).
The overlay base is always the declared defaults (D-063). Every store (the framework-owned
home of a component's x, s or m state) has a declared initial value under declaration-by-initial-value
(§8.2), so conditions are naturally sparse. Applying one means "fresh run from the x_init, s_init and
m_init defaults, with these overrides" (D-063). A condition is an initial condition and nothing
else (D-273). A simulation's state past its initial instant is a checkpoint (the Model's state at a frame
top as one value), not a condition, and it has no algebra (D-274).
Addressing conditions by path does not reopen the observation-by-path rejection (§13.5, D-409).
That rejection bars a run from acting on reads its model did not declare. A condition is not such

a read. It is a design-time statement about a concrete build, written before the run begins, and the
locality law of §14.2 is how an author keeps it to children the author owns.
A would-be init value that depends on swept outputs is either analytically known to the
caller or an equilibrium constraint (D-064). This is the pre-sweep doctrine, and it holds because
condition writes precede the first sweep (one pass through the execution order against the current
state) by definition. The first case is trim's α_filt = α_a (§14.2). There α is a decision variable, so
the value is known above, not computable below. The second case is a job for the trim service, not
for init.
"Caller-computable" reaches past closed-form knowledge to environment queries (D-139).
A condition needing one constructs the same handle the sweep will produce, and then calls the
same query function the consuming component calls. There are two routes to that handle. One is
the value-level constructor (the plain public function building a field handle from the component

condition trim! takes as a keyword) writes into the environment component's root inputs. The other
applies in a rig where an isbits handle itself is a root-input value (§4.4, D-364). There the condition
simply holds the value the baseline wrote. Either way there is one implementation of the field math,
evaluated one level up, with no pre-sweep and no new mechanism. Where closed-form enforcement

outputs. That route needs no environment access at condition time whatsoever.

Resolution turns a composed condition (the path-addressed sparse overlay that sets a build's state)
into plans the services can apply. It takes the root node plus a Build (the artifact build(world)
produces). This section covers, in order, flattening, the collecting checks, the two lookup families,
the plan, the converter rule with its two cases, and overlay partiality.

Flattening is the only place path strings are ever concatenated (D-065). It is a trivial recursion
with a path accumulator, and it also records each condition entry's tree position, its getfield/
getindex step tuple.
The collecting pass then checks each flat condition entry:
• the path resolves, with did-you-mean (the offending name plus the list-in-hand it should have
matched) over children;
• the field is declared in the target's x_init/s_init/m_init;
• the value type is convertible to the declared leaf type;
• input faces reach root inputs;
• no leaf is written twice, where a u payload's leaf is the root input its face resolves to.
Each check names its kind (Appendix C). A path that does not resolve is PathResolution with

or :no_store or :assembly_path where the target has no such store or is an assembly. A value that
does not convert is ConditionResolution with reason :unconvertible. A face that reaches no root
input takes one of the face reasons §14.2 names. A leaf written twice is DuplicateConditionLeaf.
The Build supplies two lookup families. Schema is the evaluated declarations, and it is the authority.
It answers whether you may write this field, and at what leaf type. Layout is the destination. It
holds the x backing ranges, the store indices for s and for m, and the root-input indices from the
activation (the build's typed products at a given scalar type). The face chains come from Structure
(the structure step's product, the components, wires, faces and tiers), never from an activation's
typing; the names a declaration evaluates to are the same at every activation (§9.1, D-253).

14.5 Boundary zero: an ordinary boundary with authored incoming transitions
apply! establishes the stores (the framework-owned homes of components' x, s and m state) at t₀.
The init service then completes the §10.6 macro-sequence with an empty integrate (D-067).
The sequence is the following.
project → [sweep → guards → handlers]* → due s_update calls → first snapshot
In the sequence, a sweep is one pass through the execution order against the current state, and
a guard is the declared function that decides when an event fires. A due component is a discrete
component scheduled to run here, and a snapshot is the immutable publication that closes the
sequence. After the first snapshot init! takes the trace header, the checkpoint (the Model's state at a
frame top as one value) of the state the sequence leaves (§11.5, D-274). The parity with an ordinary
boundary is exact, not approximate. The pieces follow one by one, in run order. Projection (the
optional per-component hook x ← x_projection(x)), the sweep, events and the due s_update calls
come first. Then come the t₀ argument and what boundary zero (the initialization boundary, the
ordinary macro-sequence with an empty integrate) means for trim.
• Project runs. Authored x can sit off-manifold. A hand-assembled quaternion may be ulps off unit
norm, or a condition (the path-addressed sparse overlay that sets a build's state) may write part
of a constrained block against fresh defaults. Projection after condition writes holds the same
position it holds after any other x mutation. And it costs nothing when the state is already clean.
• The sweep runs, and every discrete output stage publishes, due or not (D-205). t₀ is a grid
point of every phase-free divisor, so the Φ = 0 components are due in full. An offset component
(§10.5) is not due, because its first tick (an instant at which its stages and update run) is at Φ·Δt_base.
Its output stages run at boundary zero all the same, publishing from the authored s and the t₀
table in the ordinary sorted walk. That evaluation is establishment, not a scheduled sample. The
schedule owns every instant after t₀, and the first sample the component's s_update consumes
remains its Φ·Δt_base tick's. What the rule buys is a t₀ snapshot carrying the authored world fully
evaluated. No published cell holds a synthesized probe value (a fabricated value a build-time probe
runs on). That is the probe-value barrier of §14.6 extended from the root inputs to the whole table.
• Events run. A condition can land a guard predicate, a Bool-valued form or the sign of a continuous
function, in holding territory (firing on not-holding → holding transitions, never bare sign
changes). An authored stall flag, or a strut authored into contact, does exactly that. The event
then fires visibly at t₀ rather than one step later. The prior rule grounds that timing (§10.6,
D-292). Boundary zero establishes every guard prior (the event's stored predicate sample from the

14.6 Root-input totality: the missing-value error and the override combinator
Root inputs (the root's own input faces) are the one initialized datum without declared defaults. That
is the bare-types decision (§11.3), upheld here (D-068, D-376). So a root input's only source before
boundary zero is the condition (the path-addressed sparse overlay that sets a build's state). Boundary
zero is the initialization boundary, the ordinary macro-sequence with an empty integrate. Three
consequences follow. They are the totality check, the probe-value barrier, and baselines (aircraft-
shipped, full-coverage condition functions) layered by override, the ordered, asymmetric layering
combinator.
Totality is a precondition of starting, checked by the service (D-068). A condition value is
legitimately partial. Fragments (the leaf nodes of the condition algebra, built by set) compose,
and trim iterations write subsets. So "every root input covered" is not a property of conditions.
Totality is a property of every application that establishes a complete world over virgin
stores (D-149). That principle, not an enumeration, names the sites. They are init!, trim's setup
application to freshly allocated scratch stores, trim's commit through boundary zero (§14.8), and
linearization's operating condition under about, applied to its own scratch (§14.10). That is one group
of sites, one mechanism and one kind. Each compares the resolved plan's root-input coverage against
the Build's input_faces before writing anything. A shortfall is one collected, declaration-ordered
diagnostic (UninitializedInputs, Appendix C) naming every uncovered face. Coverage is a plan-level
fact, because both operands are resolution-time data. The check is therefore one comparison, and it
runs before any evaluation, not merely before any write. Pre-write means all-or-nothing. A rejected
init leaves the sim exactly as it was, the same posture as failed trim.
The probe-value barrier is structural (D-068). The probe_value synthesis (zero, false, the first
enum value or T()) exists so build-time probes can exercise code with fabricated inputs (§9.3).
A fabricated zero is a fine probe input and a terrible flight condition. A silently zeroed mixture,
the mixture setting of FlightPhysics' PistonEngine, kills the engine and sends the user debugging
aerodynamics. The services path simply contains no call to it. A root input gets a condition value
or the application errors, with no third branch. Replay (the ordinary loop with its drain reading the
trace) likewise never synthesizes. The trace header (the trace's fixed preamble) holds every root-
input cell as boundary zero left it, and with totality enforced that record is complete by construction.
36
=====PAGE 37=====
That discharges the requirement that a root input no device feeds hold a defined value from the first
frame (§11.3).
Baselines are aircraft-shipped condition functions, layered by override (D-068). Nobody hand-
writes ~20 root-input values per script. In Flight.jl the @kwdef defaults of SystemsInitializer, the
systems initializer of its Cessna 172 model (c172.jl), carry that load. Their successor is ordinary
user math in one authoritative home, such as ready_for_taxi(ac) or cold_and_dark(ac), returning
full-coverage conditions. But "baseline plus tweaks" collides with the duplicate-leaf error (§14.2)
by design. The collision is the intent, and the fourth node type, override(base, patch), exists
for it (D-068). It is ordered and asymmetric, where combine is symmetric and collision-intolerant.
At resolution a leaf present in both takes the patch's value, and the origin names both layers. Collisions
within one layer remain errors. Variadic layering (override(campaign, aircraft, todays_case))
composes. Trim uses it on day one. The committed condition is override(baseline, condition(d*)),
the solved condition over full coverage (D-068).

Decisions and parameters
FlightPhysics' decision-variable supertype, AbstractTrimState{N}, is dropped. It is an alias of StaticArrays'
FieldVector{N, Float64}. Its only job was vectorization, and vectorization is the service's
(D-069). The service packs and unpacks by field order, and that order is the guess NamedTuple's
own. This seam runs on the rule §9.5 states, "the names are the pairing, order carries no
semantics" (D-151). lower and upper are checked at setup for key-set equality with guess and for
Float64 fields. They are then canonicalized to guess's field order by the same type-level reorder
(NamedTuple{keys(guess)}(lower)). A permuted bound spelling is therefore a non-event, rather than
α's bound silently applied to throttle. A key-set or field-type mismatch is TrimProblemInvalid. Guess,
bounds and the returned solution share one spelling, and Base.merge(guess, (throttle = 0.3,)) is

converts.
TrimParameters is the struct in Flight.jl's c172.jl that holds a trim's targets and settings.

the compiled plan (§14.4).

Residuals and checks
The user supplies a residual system, not a scalar cost (D-069). It is authored as a NamedTuple
of named equations. The residual function that returns it has this signature.

What the solver varies is passed, and what is fixed per problem is closed over (D-118).
The gathered reads and the decision NamedTuple arrive as arguments. d is the one value that cannot

the environment, and never writes it (§14.9).
The returned NamedTuple's names are the equation names the report and the failure messages
use (D-118). The service packs residuals and tolerances to the solver's vector by field order.
The order is tolerances' field order, the declared side again, canonical for the residuals. Each residual
return is reordered to it (NamedTuple{keys(tolerances)}(r)) before packing (D-151). An equation

decisions rule holds symmetrically on both ends of the seam. Names pair, and order never does.
Names and types are checked at setup, because the guess evaluation the service performs anyway
observes the residual key set. A tolerances key-set mismatch, or any field-type disagreement on
either side of the seam, is TrimProblemInvalid (Appendix C), with the offending field and the names
or types in hand. Order is never a mismatch.
Checks are equations the service reports once, at the committed state, and never solves
(D-262). checks has the residual function's signature, and check_tolerances pairs with its return
as tolerances pairs with the residuals'. The service gathers the checks after the commit, from the
sweep of boundary zero (the initialization boundary, the ordinary macro-sequence with an empty
integrate), and reports them (§14.8). Setup observes their return's shape at the guess evaluation, as
it observes the residuals' (§14.8). Their reads join the problem's one read set.
The reason for the checks lies in analytic elimination. Under it, the condition math pins the airspeed
and the flight-path angle from the targets and the atmosphere the user's params record holds, while
the world measures against the atmosphere the baseline wrote. If the two disagree, the residuals
vanish at a true equilibrium that is not the requested point, and nothing in the residual system can
tell (D-139). A check reading EAS (equivalent airspeed) from the world's airdata at the committed
state and subtracting the requested value is where a world measurement meets the request, so any
mismatch moves it. The checks stay out of the solve because they carry no information for it (D-262).

14.8 The trim service: solver seam, scratch stores, commit and report
A TrimProblem is an inert value until a service runs it. trim! is that service. It drives a solver it holds
behind one method, works on its own scratch stores (mutable working storage whose contents are
never authoritative), commits a converged solution the way init! would, and returns a report.
The backend seam
The signature is trim!(model, problem; baseline, t0 = 0.0, backend = LevenbergMarquardt()), where
model is a Model (a deployment materialized at one scalar type) at Float64 (D-319). A Model at another
scalar is refused as ArgumentInvalid with reason :non_nominal (D-319). A Model that a simulation has
claimed is refused before any check, as ArgumentInvalid with reason :claimed, since the call commits
(D-318, D-319). The baseline keyword takes a baseline (a full-coverage condition, such as an aircraft-
shipped function returns). trim!(sim, problem; …) gates on the simulation's lifecycle and commits
through the simulation's init!.

it returns unpacks by the same order it was given (D-151).
The convergence verdict
The convergence verdict is the service's, uniformly (D-150). converged means all(abs.(rᵢ) .≤
tolᵢ). That is the per-residual box test (§14.7) in its own physical units, evaluated by the service at
the backend's returned point. It is one residual evaluation, noise against the solve that produced
it. That verdict, and nothing else, gates the commit and fills TrimReport.converged. The backend's
returned status is recorded in the report as diagnostic data, and it is authoritative over nothing.
The tolerance translation
The tolerance translation is the service's too, per backend family (D-150). In least-squares backends
the tolerances are the stopping criterion. They feed the per-residual test directly, so the damping
loop of Levenberg–Marquardt (LM) tests exactly what the service will re-test.

Scratch stores
Every trim! invocation instantiates a fresh working store set. Each half of it (below) is a scratch
Model of its own, materialized from the deployment the service was called on (D-317, D-319). The
set holds the x backing, the s and m stores, the root input and signal tables, and the derivative buffer.
The set is built from the layout of the activation (the build's typed products at a given scalar type).
The layout is the reusable compiled artifact. The buffers are per-invocation and die with the call
(stopped-sim allocation, §9.8). Each set also calls every workspace (component-declared mutable
scratch, arriving as ws) allocator once, at the activation's scalar (D-077).
The Dual backend's buffers being un-aliasable by type is defense in depth, not the mechanism. A
Float64 backend, such as the designed NLopt fallback, would get equally fresh buffers. The invariant
is backend-independent. The simulation's authoritative stores have exactly one writer, the
commit through boundary zero (the initialization boundary, the ordinary macro-sequence with an
empty integrate) (D-070).
Setup applies override(baseline, condition(guess)), the problem's condition at the guess layered
over the baseline by override, to the scratch set once. That application's full coverage is checked
here, as §14.6 requires (D-149). Sweeps therefore see a complete world. Raw instantiation is sound
exactly because of that check, since every root input is written before any read. An incomplete
baseline is one declaration-ordered UninitializedInputs at setup rather than a whole solve against
undefined cells.
The frozen cells are established, not probe-seeded (D-213). At the seeded activation the discrete
tier (the discrete side of the hybrid formalism) is frozen (§9.4). Its stages never run there, so nothing
at that activation can derive a discrete output cell from the authored s. Setup therefore instantiates
the scratch set in two halves. A nominal set (one at the Float64 activation) takes the composite
first, by the dynamic walk (§14.4), and runs one establishment round. That round is boundary zero's
sweep with every discrete output stage admitted, due or not (D-205), with no projection (the per-
component x_projection hook), no guards and no s_update. The seeded set is then written by the
specialized apply!. Its frozen cells are copied from the nominal set, Float64 values that a continuous
consumer reads as zero-partial constants (§9.5). Every cell the iterations read is thus derived from

"held at the operating point" literal. No scratch cell holds a synthesized probe value (a fabricated
value a build-time probe runs on). That is the probe-value barrier of §14.6 reaching the scratch
world, as D-205 made it reach the published one. The iterations are untouched (§14.5). They run
at the seeded activation, over the continuous chain and x_deriv alone. The empty problem (below)

The commit (below) applies the same composite over the same baseline, so its coverage is setup's.
Commit's totality check is therefore structurally unfailable through the trim path, and it stands as
the shared init! defense (D-149). A converged solve is always committable. TrimReport therefore
carries no committed flag, and the no-throw rule (below) needs no exception.
Iterations rewrite the composite's write-set via the compiled plan. The write-set is
override(baseline, condition(d)), the same tree setup resolved, so a store both layers touch merges
exactly as it did at setup. An LM evaluation is one Dual-seeded sweep yielding r from the value
parts and J from the partials, together (D-069). No convergence means no commit. Non-convergence
is the service's box test failing at the returned point, whatever status the backend attached to it
(D-150). No commit means the sim is bit-for-bit untouched, including "never initialized". Flight.jl's
warn-but-assign, where the Cessna 172 trim warns on a failed optimization and assigns its result
anyway, is structurally impossible.
The same structure covers an interrupt. Ctrl-C during a long solve unwinds an ordinary Julia call
operating on per-invocation scratch stores. No commit has happened, and the simulation is bit-
for-bit untouched, exactly as a non-converged solve leaves it. The services need no counterpart to
the loop's boundary masking (§12.4). An interrupt inside the commit's boundary zero moves the
simulation to built and propagates raw (§13.4, D-223).
The commit, in full
The committed solution is applied as an init! in every respect. It is override(baseline,
condition(d*)) through boundary zero, with the pre-write root-input totality check (§14.6), the
sequence (§14.5) and guards at commit. That check requires the application to cover every root
input.
The t0 argument that anchors the grid, and its default, are the same for both init-service entry points
(§14.5, D-110). The recorders (the trace and the log jointly) restart exactly as §12.6 states for init!
(D-110). The trace (the primary record of a session) and the log are new objects. Any batches still
in staging cells (where a device's pending write batch waits between drains) are cleared.
A fresh recording that starts at its own anchor is the natural shape of an unattended run (a run with
empty staging and no snapshot readers). Trim is not offered at a point reached by flying. It takes an
authored baseline. Fly-then-retrim is spelled as a checkpoint (the Model's state at a frame top as one
value) of the flight, then a trim baseline authored from what the checkpoint shows (D-273).

14.9 Mounting: problems as relocatable values
This section treats a TrimProblem (the closed nine-field value a trim solves) as a relocatable value.
Mounting (relocating a whole problem or tap set to a prefix) is the work of at, the scoping
combinator. The section says what a problem is, then how at lifts one, how a mounted read set and
mounted input entries resolve, why a problem never authors the environment, and how worlds,
thin rigs (worlds holding only the aircraft and its environment) and swarms use the lift.
A TrimProblem is not a condition but an implicitly specified condition (D-071). A condition is
the datum that says "set this build to this state". condition is a condition-valued function over the
decision space. reads/residuals are the equations that pin the free variables down. guess, lower and
upper say where to search. Solving makes the implicit condition explicit. The commit is then literally
an init, override(baseline, condition(d*)) through boundary zero (the initialization boundary, the
ordinary macro-sequence with an empty integrate). override is the ordered, asymmetric layering
combinator, in which the patch wins on a shared leaf. The services unify as clients of one condition
algebra. init! applies an explicit condition, and trim! searches a family for the member satisfying
its equations.
at lifts a problem field by field, and each field falls in one of three cases (D-071, D-277). The
condition field is condition-producing (path-relative), so the lift post-composes it. The reads field is
a read set, and the lift prepends the prefix to the set's mount chain (the prefixes it is mounted under,
root first). Every other field is path-free and passes through. The rule that residual math sees only
the gathered NamedTuple (§14.7) is what makes the residuals path-free.

14.10 Linearization: tap selectors, one seeded pass, a pure query
linearize computes the matrices A, B, C and D about an operating point in one seeded evaluation,
and it commits nothing. What it seeds and reads is a tap set (three labeled lists declaring what
linearization seeds and reports). This section covers, in order, the tap set, the operating point, the
seeded pass, the leaves the pass seeds and the leaves it holds frozen, the returned value, the guidance
on coordinates, the recorded sampled-data extension, and declared non-participation with the local
derivative rule.
The tap set
Flight.jl's per-aircraft XStateSpace/UStateSpace/YStateSpace structs, plus the get_*_ss/assign_*_ss!
shuttle methods, run to ~150 lines of bookkeeping per variant. All of it becomes three selector
lists (the closed family of deferred reads resolving against a source). The three lists are declared
together as one tap set, taps(x = …, u = …, y = …) (D-072, D-272). Membership is closed per
list. The x list takes get_state, the u list get_input, and the y list get_output and get_face (§14.4). The
NamedTuple key is the label control design slices by.
A tap names one scalar (D-272). Its leaf address (the field name with dotted and bracketed steps
below it) resolves to one scalar leaf (§14.4, D-276). So a vector leaf yields named scalars, one tap
48
=====PAGE 49=====
per element. A seeded tap, in the x or u list, reaches its scalar through one index step at most and
never a .name step, because a seed is written into a whole state field or root input (the root's own
input face), or into one array element of it. A seeded tap's leaf is exactly Float64. Any other seeded
address is rejected at resolution as a TapResolution. A y tap is a read and takes any leaf address. A
tap resolving to a vector or a struct is rejected at resolution as a TapResolution, and so is a member
in the wrong list. A second tap resolving to a site already seeded is rejected naming the earlier label,
since one site is one column and a second seed there would overwrite the first (D-272).

The x list is validated against the x_init stores of the continuous tier (the continuous or discrete side
of the hybrid formalism), the u list against faces, and the y list against y_types. An x tap naming
a discrete store is rejected at resolution as a TapResolution, with the tap and its tier in hand
(D-197). That is the no-silent-zeros rule (§9.5). The discrete tier is frozen (§8.2), so its only possible
partials are zeros. The rejection's next-move guidance points at the recorded step-map extension
below. The lists compile to offsets once, and relocate whole via at(prefix, taps) (D-072). The shuttle
layer's successor is that compiled writer/reader pair, and no hand-written state-space mapping
remains (§7.1, D-072).
The operating point
Linearization is a pure query (D-072). It commits nothing and runs no boundary zero (the initialization
boundary, the ordinary macro-sequence with an empty integrate). It works only on scratch
buffers (mutable working storage whose contents are never authoritative), and nothing it computes
becomes authoritative. Flight.jl's restore-the-trim dance, the re-assign! after the FiniteDiff package
dirtied the model, has no successor.
The default operating point is the checkpoint of the simulation or the Model (a deployment
materialized at one scalar type) as it stands (D-274, D-319). A checkpoint is the Model's state at a
frame top as one value. The default point is checkpoint(sim) on a simulation and checkpoint(model)
on a Model, each restored into the scratch world with no boundary zero (§12.6, D-274, D-319). The
frozen tier's cells (the typed entries of the signal table) are the checkpoint's held cells. After a trim!
commit, linearize(sim, taps) or linearize(model, taps) is about the trim point with nothing re-
specified. about = <condition>, with t0 beside it, linearizes anywhere else without touching
the sim, the condition's coverage checked as §14.6 requires (D-272). t0 is admitted only there, and
a t0 passed without about is an ArgumentInvalid.
The seeded pass
Each invocation instantiates its own scratch store set, the trim service's mechanism verbatim (§14.8),
and establishes the operating point in it (above). It then runs the seeded Dual evaluation, one
direction per x tap and per u tap, in groups of width directions per pass (D-072). width is a keyword
of linearize, default 8 (D-272). The default width's scalar type is named. A build can therefore

pre-materialize its activation (the build's typed products at a given scalar type) through activations
(§9.4), and a tap set of any size then linearizes with no compile at the keyboard (D-272). Value parts
give ẋ₀ and y₀. Partials give A and B against the x- and u-seeds, and C and D against the same seeds read
at y. All four come out simultaneously, exact to machine precision. linearization_walkthrough.md

Seeded and frozen leaves
Unseeded states sit constant at the operating point, and so do unseeded root inputs (D-072).
Establishing the operating point embeds their Float64 values as zero-partial constants. The discrete
tier is frozen with zero partials, which is precisely "linearize with the discrete state held" (§8.2).
Partials enter through per-invocation seeding, one rule for x and root inputs alike (§7.2, D-297).
§8.2 states which root inputs the schema leaves seedable (D-295). A root input whose input entry is
declared Pinned is declaredly unseedable, and its cell is frozen at every activation.
Selecting such a root input as a B-matrix tap is rejected at tap resolution as a TapResolution,
with the offending input entry in hand, rather than silently yielding a zero column (D-295, D-296).
Under fan-out the rejection names the pinning consumer, not the face alone. A root input is
unseedable whenever any one of its consumers demands frozen, which is the fan-out meet (§8.2,
D-168). The author's next move is to promote that leaf to a tolerant input entry, or to route the tap
around it. Either move depends on knowing which leaf froze the root input. A discrete consumer
pins its input entry by tier, not by declaration (§8.2), so a root input it reads is unseedable at every
activation with nothing to promote. The rejection then names the tier, and the next move is to tap
the continuous cell that consumer drives, or the recorded step map below (D-272).

The returned value
linearize returns a Linearization value (D-072, D-272). It holds ẋ₀, x₀, u₀ and y₀ as NamedTuples
under the tap labels, A, B, C and D as matrices, and the three label sets of the taps (D-272). On
that data, FlightPhysics' subsystem/delete_vars survive as pure label-indexed matrix slicing, with
no model involvement. Flight.jl's c172x_ctl LQR (linear-quadratic regulator) pipeline consumes it
with cosmetic changes. FlightPhysics' LinearizedSS, the component, survives separately, as an
ordinary continuous component in the migrated library (D-072). Its x_init is the state vector, its
faces are labeled, and the affine update lives in y_direct/x_deriv. It has no privileges, and its schema
is everyone else's.
Coordinate guidance
The recorded guidance is that linearization taps should select minimal-coordinate mechanizations
(D-072). Perturbing Euler-angle states is meaningful where seeding quaternion components steps
off the unit-norm manifold. This is why Flight.jl's C172X design code linearizes the aircraft's {NED}
variant, the one built on north-east-down (NED) kinematics. design_world(ac) (the thin rig that
mounts an aircraft for trim and linearization) rigs that variant, promoting implicit practice to stated
rule. The coordinate choice belongs to the tap author, not the framework.
The sampled-data extension
The sampled-data Dual activation is recorded, not built, a worked-out extension deliberately
left unimplemented with its seams named (D-073). The frozen-exact doctrine is consumer-scoped,
not a capability wall. Trim and linearization differentiate the continuous dynamics with the discrete
state held, and for that a frozen discrete output (a zero-order-hold constant with zero partials) is the
exact answer, as §7.2 states (D-072). The frozen discrete cell is not an AD limitation on the signal
path. It is the true zero of an instantaneous dependence that the hybrid semantics never had. The
signal flow through a discrete component is temporal, not instantaneous, and AD follows the actual
data movement. frozen_discrete_walkthrough.md works the three-component chain through.
Differentiating "through" the discrete side means differentiating a different object. That object is
the sampled-data step map Φ : ((𝑥𝑘, 𝑠𝑘), inputs) → (𝑥𝑘+1, 𝑠𝑘+1), taken over the model's whole
state, both letters at once. One evaluation of Φ integrates one period, then runs the due ticks. The
extension is additive along existing seams.
• Walked-leaf parametrization of the discrete tier's real-scalar state leaves. Counters and enums
stay pinned, like m.
• Opt-in participation on discrete components, with frozen-exact staying the default. A participating
component opts in through an explicit trait, and that trait turns the walk on for its contracts
(its declared interface). Its Float64 leaves follow the scalar and Pinned keeps its meaning, exactly

The honest limit is that Φ is differentiable only where the event pattern is locally constant. Exactness
across a firing needs saltation corrections (the jump terms a sensitivity takes across an event). The
scope is therefore event-quiescent operating points, which trim points already are, because guards
at commit see to that (§14.5). The scope comes with a loud diagnostic if an event fires inside a
differentiated step. Two consumers wait. The first is the closed-loop trim extension (§14.7), whose
s_update(s) - s = 0 residuals would currently need the derivative-free fallback, since a frozen
s_update has no Jacobian columns. The second is exact discrete-time linearization of the full loop,
which is digital design on the exact discretized plant instead of continuous linearization plus Tustin's
discretization.
Declared non-participation
Both halves of non-participation have a spelling (D-263). The output half is the freeze door, which
declares a leaf frozen under differentiation as §8.2 and §9.5 spell it (D-286). An opaque wrapper,
such as an FMU (a Functional Mock-up Unit, a packaged simulation unit) or a C aerodynamic table,
and a deliberately severed coupling can therefore both say so in the schema, instead of showing up
in Jacobians as unexplained zero rows. The conformance check holds them to it at every activation
(D-286). The input half is the FFI door (§8.2). A consumer's Pinned input entry declares "never hand
me partials", enforced at the wire (§6.1, D-263). At a root input, such an input entry is the forbid-
seeding marker itself. That marker carries semantics rather than mere protection, because it types
the root-input cell at every activation. An unseeded root input is therefore a choice, where a Pinned-
entry root input is a declaration (D-295).
An implementation that cannot take Duals has a third move. The marker records that a leaf carries no
partials, not that an implementation cannot propagate them. A component that must participate
keeps its input entry tolerant and supplies its own local derivative inside the stage (D-266).
A C table or an FMU whose coupling matters to the Jacobian is such a component. It evaluates at
the value and obtains a local Jacobian by whatever means it has, such as a finite difference at a step
its own grid suggests or the table's analytic slope. It then chains that Jacobian onto the incoming
partials (D-266).
