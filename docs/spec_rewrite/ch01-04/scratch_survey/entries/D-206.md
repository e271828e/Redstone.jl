7562	### D-206 — Rename root slots to root inputs
7563	
7564	**Status.** ratified
7565	
7566	**Position.** The write surface's member term is renamed: "slot" / "root
7567	slot" / "root input slot" → **root input** ("the model's root inputs" where
7568	prose flow wants it), sweeping the spec and its companions per the standing
7569	rename rule — forward, never the log. Four API spellings follow:
7570	
7571	- the condition fragment keyword `slots` → `inputs`
7572	  (`fragment(; x, s, m, inputs)`);
7573	- the table selector `get_slot(face)` → `get_input(face)`;
7574	- the diagnostic kind `UninitializedSlots` → `UninitializedInputs`;
7575	- the diagnostic kind `RootSlotTypeConflict` → `RootInputTypeConflict`.
7576	
7577	**Spec.** [§4.1][s4-1], [§11.3][s11-3], [§14.2][s14-2], [§14.4][s14-4], [§14.6][s14-6], [Appendix C][sC]
7578	
7579	**Rationale.** "Slot" was opaque coinage: it demanded a recall step on every
7580	read, where "root input" decodes itself — and under [D-208][d-208] the definition
7581	collapses to near-tautology (a root input is the root component's input
7582	face), which is what vocabulary should do. The qualifier "root" carries the
7583	real distinction against the input ports, faces and entries that exist at
7584	every level. The bare spellings `inputs` and `get_input` are safe in their
7585	scopes — nothing else in a fragment payload or the selector family could be
7586	meant — and `get_input`/`get_output` gain symmetry, with the inherent
7587	addressing asymmetry (face name vs structural path, [§11.3][s11-3]'s write-surface
7588	rule) accepted.
7589	
7590	**Rejected.**
7591	- *Keeping "slot":* brevity was its only virtue; it never carried its
7592	  meaning.
7593	- *`get_root_input`:* precise but heavy in the selector family's naming.
7594
