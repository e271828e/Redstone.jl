139:## 1. Introduction
140:
141:**Purpose.** Redstone is a framework for modeling and simulating hierarchical
142:[hybrid causal systems](#g-hybrid-causal-system) (models that mix continuous
143:dynamics, periodic discrete dynamics and events, exchanging values through
144:directed ports). Its home domain is aircraft guidance, navigation and control:
145:vehicle dynamics, sensors and avionics, simulated offline or interactively in
146:real time. The formalism itself is domain-neutral.
147:
148:**Capabilities.** A model is written as a tree of [components](#g-component) in plain Julia. The
149:build checks the tree. A simulation runs a [`Model`](#g-model) (the tree compiled at one
150:scalar type, ready to step) ([§9][s9]). The framework provides these capabilities.
151:
152:- Continuous dynamics with algebraic outputs, integrated on a fixed step, with
153:  events either located by root-finding or checked at step boundaries
154:  ([§2][s2], [§10][s10]).
155:- Multi-rate periodic discrete dynamics at declared sample times, held
156:  zero-order between ticks ([§3.2][s3-2], [§10.5][s10-5]).
157:- A build that derives the execution order from declared feedthrough and
158:  rejects algebraic loops by naming the cycle ([§5][s5], [§9][s9]).
159:- A runtime [periphery](#g-periphery) (the devices, GUI and scripts that
160:  exchange data with a running simulation) that writes by staging and reads by
161:  snapshot ([§11][s11], [§12][s12]).
162:- An input trace that replays any run bit-identically ([§11.5][s11-5]).
163:- Stopped-sim services for initialization, trim and linearization, with exact
164:  automatic-differentiation Jacobians ([§14][s14]).
165:
166:**Design criteria.** The design answers to five criteria. Wherever it admits a
167:capability it does not build, that capability is weighed against them as a
168:[guarded addition](#g-guarded-addition).
169:
170:- **Zero-allocation stepping and type stability.** The inner loop allocates
171:  nothing, and the test suite asserts it ([§7.5][s7-5], [§9.7][s9-7]).
172:- **Real-time interactive operation.** A simulation runs paced against the
173:  wall clock, with devices and a GUI attached ([§10.7][s10-7], [§11][s11]).
174:- **Live introspection.** Every published signal can be inspected by path,
175:  during a run and after it ([§11.2][s11-2]).
176:- **Compositional flexibility.** Components compose hierarchically, and a
177:  component substitutes for another behind the same declared contract
178:  ([§6][s6], [§8][s8]).
179:- **Rigor and error locality.** Structure is declared and checked at build
180:  time, so a mistake fails where it was made, with a diagnostic naming it
181:  ([§8.4][s8-4], [§13][s13]). Components are plain Julia with no macro DSL, so
182:  debugging, tooling and comprehension work on the language's own terms
183:  ([§8.1][s8-1]).
184:
185:**Origins.** Redstone began as a replacement for `FlightCore`, the simulation
186:core of the Flight.jl package. Flight.jl also holds `FlightPhysics`, its
187:physics library, and `FlightApps`, its applications. The early design read
188:those two packages as its requirements. Every capability they demonstrated had
189:to survive, and none of their interfaces had to. Older entries in the decision
190:log reason against `FlightCore` and cite that code, and the case studies that
191:tested the design against it live in `companions/flight_case_studies.md`.
192:Redstone itself does not depend on Flight.jl.
193:
194:**Scope of this document.** This document is the
195:[normative statement](#g-normative) of the design. It states what the
196:framework *is*, in the present tense. Part I fixes the formalism and the
197:component model. Part II covers authoring and the build, Part III execution
198:and the runtime periphery, and Part IV failure handling and the stopped-sim
199:services. The appendices index the author-facing contracts, the API, the
200:diagnostic kinds and the vocabulary. `pending.md` registers what the
201:implementation still owes this document and the questions the design leaves
202:open. It also lists the release work this document does not ask for. The
203:explainers in `companions/` are not normative, and this document wins
204:wherever they disagree.
205:
206:Decision rationale lives in `decisions.md`, including the alternatives
207:considered and the reasons they were rejected. This document cites it throughout
208:as linked `D-nnn` entries, one entry per settled decision. Entry numbers are
209:stable and never reused, so a citation here always names the same entry there.

213:## 2. Formalism
214:
215:The framework simulates **[hybrid causal systems](#g-hybrid-causal-system)**. Such a system has five parts.
216:
217:- **Continuous dynamics.** $\dot{x} = f(x, m, u, t)$ with algebraic outputs.
218:- **Multi-rate periodic discrete dynamics.** $s^{+} = g(s, u, t)$ at declared
219:  rates, with outputs held zero-order between [ticks](#g-tick).
220:- **Zero-crossing events.** [Guard](#g-guard) functions with handlers, under two detection
221:  policies, stated below.
222:- **Post-step manifold [projection](#g-projection).** An optional per-[component](#g-component) hook `x ←
223:  x_projection(x)`, applied after each accepted step. It covers quaternion
224:  renormalization, DCM orthonormalization and any other manifold-valued state.
225:  It is the cheap end of the projection-methods family from geometric
226:  integration.
227:- **External inputs.** The runtime injects them asynchronously, from pilot
228:  controls or the network, under the staging rules of [§11][s11].
229:
230:### 2.1 Events: two detection policies
231:
232:Both policies share one declaration, a [guard](#g-guard) function plus a handler. Only
233:detection differs.
234:
235:- **[Boundary-detected](#g-boundary-detected) (cheap).** The framework checks each guard for a
236:  not-holding → [holding](#g-edge-semantics) edge against its [prior](#g-prior) ([§10.6][s10-6]) at step [boundaries](#g-boundary) only.
237:  There is no root-finding and no step rejection. The handler fires at the end
238:  of the step in which the edge was observed. The cost is one guard evaluation
239:  per event per step. This policy is fully compatible with fixed-step real-time
240:  execution.
241:- **[Localized](#g-localized) (precise).** The framework finds the crossing instant by
242:  root-finding. This policy serves events where timing precision genuinely
243:  matters. [§10.4][s10-4] gives the mechanics.
244:
245:Detection policy never depends on real-time [pacing](#g-pacing) ([§10.7][s10-7]).
246:
247:**Time events and state events.** The discrete [tier](#g-tier)'s [ticks](#g-tick), declared by
248:`sample_times`, are [time events](#g-time-event). Their instants are known in advance and
249:scheduled ([§10.5][s10-5]). Everything declared through `StateEvent(guard, handler)` is a
250:[state event](#g-state-event). Its instant is unknown and must be detected, by boundary check or
251:by localization. That is why the declaration is named `state_events` ([§8.2][s8-2]). The
252:criterion is detection versus scheduling, not which fields a guard reads. A
253:guard over an input is still a state event.
254:
255:This arrangement gives step-boundary logic *well-defined semantics*. The
256:crossing defines the transition. Detection resolution is an execution-policy
257:detail.
258:
259:A guard defines a **[predicate](#g-predicate)**. It does so in one of two forms, either a
260:`Bool`-valued form or the sign of a continuous function under the normative
261:convention **positive = predicate holds**. Writing the guard's sign value `σ`,
262:holding means `σ ≥ 0`.
263:
264:An event fires when its predicate transitions from not-holding to holding. This
265:is [edge semantics](#g-edge-semantics), and it is uniform across both forms. [§10.6][s10-6] states the prior
266:bookkeeping. The opposite crossing direction is declared as a second event with
267:the negated guard. Stall entry and exit are one such pair.
268:
269:Which form an author declares is not a free choice. **The guard's return type is
270:the declared policy.** A `Bool` return declares boundary-detected, and the sign
271:form declares localized ([D-179][d-179]). [§10.4][s10-4] states the rule, the exactness result
272:that motivates the `Bool` form, and the gate idiom for localizing mixed
273:predicates.
274:
275:### 2.2 Exclusions (deliberate)
276:
277:- **No DAEs / algebraic constraints.** The actual need is state manifolds, and
278:  [projection](#g-projection) covers it ([D-001][d-001]).
279:- **No SDEs / stochastic integrators.** Noise processes such as Dryden/von
280:  Kármán turbulence and sensor noise are modeled as ordinary RNG-driven discrete
281:  processes, that is, shaping filters. That modeling is faithful to how they are
282:  specified, and it is cheap. One consequence is elevated to a framework
283:  guarantee, **deterministic [replay](#g-replay)**. RNG state lives in [component](#g-component) discrete
284:  state (`s`), never in ambient globals, so the same seed gives a bit-identical
285:  trajectory.
286:- **No unconditional per-step hook**, so no `f_step!` equivalent. Every current
287:  use decomposes into one of two mechanisms. Projection covers quaternion
288:  renormalization. [Boundary-detected](#g-boundary-detected) events (checked for edges at step
289:  boundaries only, no root-finding) cover engine phase transitions and the stall
290:  hysteresis latch. For one class the mapping tightens semantics.
291:  Level-triggered cross-component resets become edge-triggered events. The gear
292:  friction regulator under `!wow` is one such reset ([§5.3][s5-3], [D-001][d-001]).

296:## 3. Component taxonomy
297:
298:There are three classes. Two of them are leaves with crisp, closed semantics,
299:and one is pure composition.
300:
301:### 3.1 Continuous component (the hybrid primitive)
302:
303:A continuous component is a classical hybrid automaton. It has these facets.
304:
305:- **Continuous state** `x`, an isbits struct of real scalars ([§7][s7]).
306:- **Mode variables** `m`. These are piecewise-constant values (enums, integers,
307:  flags) that parametrize the [flow](#g-flow) and change *only* through event handlers.
308:- **Flow** $\dot{x} = f(x, m, u, t)$.
309:- **Two output stages** ([§5.2][s5-2]).
310:- **Events**, each a [guard](#g-guard) plus a handler. A handler may update `m` and may
311:  reset the component's own `x`. Both guard and handler read the fresh [boundary](#g-boundary)
312:  [signal table](#g-signal-table) ([§5.3][s5-3]).
313:- An optional **[projection](#g-projection)**.
314:
315:Any facet may be empty. In particular, a [component](#g-component) with *no* continuous state,
316:only modes, events and mode-valued outputs, is an FSM. A single primitive
317:therefore supports both factorings of mode logic.
318:
319:- **Internal modes** suit tightly coupled cases, such as stall hysteresis inside
320:  the aero component. They preserve cohesion and enable reset maps.
321:- An **external FSM component** feeding modes through a [port](#g-port) gives maximal
322:  purity, independent testability and swappable supervision logic.
323:
324:**Rule of meaning.** A supervisor *commanding* a mode change is an ordinary
325:**input**. A component *detecting* its own transition is an **event**. The two
326:mechanisms carry two meanings and do not overlap.
327:
328:### 3.2 Periodic discrete component
329:
330:A periodic discrete component has these facets.
331:
332:- **Discrete state** `s`, any isbits value ([§7][s7]).
333:- **Update** $s^{+} = g(s, u, t)$ at a declared rate.
334:- **Two output stages**, with [feedthrough](#g-feedthrough) applying at update instants. A
335:  proportional path is direct feedthrough. A state-only output is not.
336:
337:Each [tier](#g-tier) carries its own state letter. `x` is the argument of the [flow](#g-flow) map
338:under `f`, and `s` is the argument of the jump map under `g`. The two are
339:different objects. `x` has a derivative and lives in the flat [buffer](#g-buffer). `s` has
340:none and is latched in a [store](#g-store) between [ticks](#g-tick). So they are spelled differently
341:([D-195][d-195]). Nothing is lost by the split, because a leaf is strictly one tier
342:([D-056][d-056]) and no [component](#g-component) ever reads another's state. A discrete component's `s`
343:influences continuous dynamics only **through signals**. Those outputs are held
344:zero-order between ticks.
345:
346:**`m` is continuous-only.** A discrete component has no mode store. Its FSM
347:enums, flags and counters are ordinary `s` fields.
348:
349:**Why.** `m` exists on the continuous side because modes must change *between*
350:flow evaluations, which is what handlers do. On the discrete side `g` already
351:runs at the only instants at which anything may change. A second store would
352:duplicate the discrete tier's own state semantics under another name.
353:
354:### 3.3 Assembly
355:
356:An assembly is pure composition. It holds submodels, [local wires](#g-local-wire) and
357:boundary [faces](#g-face). **It has no dynamics of its own.** Hybridness emerges at the
358:[assembly](#g-assembly) level. An aircraft is continuous vehicle parts plus discrete avionics
359:parts. The two-leaf split was upheld against the integrate-and-dump challenge
360:([§3.4][s3-4], [D-056][d-056]). Assemblies are flattened away for ordering. They are
361:retained as the navigation and introspection hierarchy (GUI, logging, paths) and
362:as declaration-level [rate scopes](#g-rate-scope) ([§10.5][s10-5]).
363:
364:### 3.4 Why two leaf classes, not one hybrid primitive
365:
366:Why two leaf classes at all? One all-in-one primitive could carry continuous
367:state, modes *and* discrete state, with `x_deriv`, events *and*
368:`s_update`. A purely continuous or discrete [component](#g-component)
369:would then fall out of whichever facets an author declares.
370:[Class](#g-class) is already read off declaration shape ([§8.5][s8-5]), so the
371:question is whether the two declaration sets should be exclusive. They are
372:([D-056][d-056]).
373:
374:**Why.** The split is between *time bases*, not state classes. The continuous
375:primitive is already hybrid, with `m`, [guards](#g-guard) and handlers
376:([§3.1][s3-1]). What separates the classes is [sweep](#g-sweep)-driven versus
377:[tick](#g-tick)-driven execution. And the settled rules force a merged
378:[component](#g-component)'s two halves to communicate exactly as two siblings
379:do. There is [one home per datum](#g-one-home-per-datum) ([§5.2][s5-2]),
380:`x_deriv` sees only the continuous state and `s_update` only the
381:discrete one, and `s⁺` is decoded only at the owner's next tick, because
382:`s_update` runs last. That deferred decode is what makes ticks→events
383:structurally impossible and what terminates the [boundary](#g-boundary)
384:iteration ([§10.6][s10-6]). Cross-[tier](#g-tier) influence inside the merged
385:class still routes through published table [cells](#g-cell). The all-in-one
386:component is therefore an [assembly](#g-assembly) of two primitives in a
387:trench coat. It buys no expressiveness and incurs costs of its own, which
388:[D-056][d-056] enumerates. One of those costs is not bookkeeping. The sampling
389:[seam](#g-seam), the ZOH and the `z⁻¹` delay, is the most bug-prone boundary
390:in a flight-control stack. A monolith swallows it. The split keeps it a
391:visible wire.
392:
393:#### The hardest case: integrate-and-dump
394:
395:A strapdown IMU is the strongest challenge mounted against the split. Its direct
396:formulation integrates raw increments continuously:
397:`ẋ.ϑ_c = ω_ic_c`, `ẋ.υ_c = f_c_c`, the coning attitude increment `q_c_cc`
398:and the sculling integral `ẋ.υ_c_sc = q_c_cc(f_c_c)`. Then, at the IMU's
399:own `Δt`, a discrete step reads the integrals, publishes the sample, and
400:**zeroes them**. In interval terms, these piecewise quantities are integrals
401:over $[t_{k-1}, t_k]$ with their weights re-anchored at each reset. `ϑ_c`
402:$= \int_{t_{k-1}}^{t_k} \omega^{c}_{ic} \, dt$ and `υ_c`
403:$= \int_{t_{k-1}}^{t_k} f^{c} \, dt$ run from zero, `q_c_cc`
404:$= q_{c_{k-1} \to c(t)}$ runs from identity, and `υ_c_sc`
405:$= \int_{t_{k-1}}^{t_k} R^{c_{k-1}}_{c} f^{c} \, dt$ has its rotation
406:anchored at the interval start. These are exactly the forms the differencing
407:idiom of [§8.6][s8-6] recovers from the cumulative stores, term by term. The reset is
408:periodic, not condition-triggered, so events are the wrong [tier](#g-tier).
409:And the reset is a discrete-tier write into continuous state, exactly the
410:operation this design forbids. `s_update` writes only its own `s`, and
411:handlers are the sole resetters of continuous state, [guard](#g-guard)-driven.
412:Integrate-and-dump falls squarely into the crack between the classes. It is
413:tightly coupled continuous and periodic dynamics in one physical instrument.
414:
415:**Algebra removes the reset.** Every interval-relative integral becomes a
416:cumulative one, and a discrete sampler differences consecutive samples against
417:its latch. [§8.6][s8-6] spells that idiom, its exactness condition and the
418:resulting assembly in full.
419:
420:**Verdict.** The strongest counterexample landed on the two-class taxonomy
421:with *less* code than the direct formulation. It keeps the same thirteen integral
422:scalars and the same math, minus the reset block, and it brings three
423:structural gains. The sampling [seam](#g-seam) became a wire. The error model
424:became a discrete sibling, which makes the truth/corrupted sample pair
425:separately loggable. And linearization got sane. Under a `Dual` [activation](#g-activation) the
426:discrete tier is held ([§8.2][s8-2]), and "integrators that never reset" *is*
427:the cumulative formulation. The framework's rules pushed the model into the
428:only form its own linearization semantics could coherently handle. One escape
429:hatch is recorded, unbuilt. If interval-relative dynamics ever neither factor
430:algebraically nor tolerate the latch-back wire, the
431:[guarded addition](#g-guarded-addition) is a **tick-triggered handler** on
432:[continuous components](#g-continuous-component) (periodic events). No known
433:case needs it ([D-056][d-056]).

437:## 4. Ports and signals
438:
439:### 4.1 Immutable value semantics
440:
441:[Ports](#g-port) exchange **immutable values**, typically isbits structs (floats,
442:`SVector`s, enums, nested immutables). The framework owns a **[signal table](#g-signal-table)**,
443:with one concretely typed **[cell](#g-cell)** per output port in the flattened model. A
444:producer's output [stage function](#g-stage-function) (`y_state`/`y_direct`, the two output
445:stages every component provides, on either [tier](#g-tier)) returns a named tuple of fresh
446:values. The framework writes each of those values into its cell, and consumers
447:read cells.
448:
449:**Vocabulary.** These names are binding throughout this document.
450:
451:- A bare *cell* is the table entry, and only that.
452:- A *store* is the framework-owned home of one of a component's state letters,
453:  `x`, `s` or `m` ([§7.1][s7-1], [§7.3][s7-3], [D-302][d-302]). An `x` store is a range of
454:  the [buffer](#g-buffer). Stores are not cells.
455:- A *[staging cell](#g-staging-cell)* is a distinct compound term. It is the per-[device](#g-device) inbound
456:  register of [§11.4][s11-4]. Unlike a table cell it is mutated frame by frame, and it
457:  sits outside the table's publish-once discipline.
458:- A *[root input](#g-root-input)* is a source cell fed by the [periphery](#g-periphery) rather than by a producer
459:  ([§11.3][s11-3]).
460:
461:Stated precisely, the signal requirement is **immutability plus frozen
462:references**. Signals may reference bulk data ([§4.4][s4-4]) provided that data is
463:read-only for the duration of the run. `isbits` is the common case, not the
464:rule.
465:
466:This requirement has four consequences.
467:
468:- There is no aliasing, ever. Nothing can be mutated under a consumer's feet.
469:- Concurrent reads from the GUI and logging threads are safe by construction.
470:- Isbits payloads allocate nothing, because named tuples of isbits are isbits.
471:- Each cell has a definite freshness, tied to its producer's position in the
472:  [execution order](#g-execution-order) ([D-004][d-004]).
473:
474:### 4.2 Consumers see ports, not stages
475:
476:The [port](#g-port) is the addressable unit. A [component](#g-component)'s outputs appear to consumers, the
477:GUI and logs as one flat namespace of ports (`dyn.vel`, `dyn.f_c_c`). A
478:reader reaches a leaf inside a port value through the port's
479:[leaf address](#g-leaf-address) (the field name with dotted and bracketed
480:steps below it, [§14.4][s14-4]). Which output stage computes which port is an
481:ordering annotation, invisible outside the component. Moving an output between
482:stages is non-breaking *for consumers*. No wire, log or panel sees it. The build
483:does see it, because the [feedthrough](#g-feedthrough) graph and stage membership change ([§9.1][s9-1]).
484:
485:**Visibility.** Which ports exist at all is a declaration-layer decision. The
486:output [contract](#g-contract) *is* the public interface. There are no private intermediates. A
487:value a later function needs is a declared port like any other, and a stage
488:result outside the contract is a build error ([§5.2][s5-2], [§8.3][s8-3]). A presentational
489:*unlisted* flag, skipped in logs and GUI but still connectable, is closed
490:([D-016][d-016]).
491:
492:### 4.3 Table mechanics and port granularity
493:
494:[§4.2][s4-2] fixed the [port](#g-port) as the addressable unit. Four questions remain. What is a
495:port on a [component](#g-component)'s boundary? How do values travel into cells and out of them?
496:What may a port hold? And how much should a single port carry? The last question
497:has two answers, one owed to the parties that read a port and one to the parties
498:that write it.
499:
500:#### Ports and faces
501:
502:A component's **ports** are its signal endpoints, one [cell](#g-cell) and one producer
503:each. Its **[faces](#g-face)** are the names those ports wear on the component's boundary.
504:For a leaf the two coincide. For an [assembly](#g-assembly) every face aliases an interior port
505:through its boundary declarations ([§8.6][s8-6]) and never creates an endpoint. The
506:distinction is kind-blind. Wiring and the [periphery](#g-periphery) address a child's faces
507:without knowing whether it is primitive or composite.
508:
509:**Rule.** The port is the atomic unit of the entire periphery. It is one cell,
510:one [root input](#g-root-input), one staged write, one [device](#g-device) [claim](#g-claim) ([§11.3][s11-3]), one [trace](#g-trace) address
511:and one GUI liveness verdict ([§11.7][s11-7]).
512:
513:#### Scatter and gather
514:
515:**Scatter/gather is the whole protocol.** A [stage function](#g-stage-function)
516:(`y_state`/`y_direct`, on either [tier](#g-tier)) returns a named tuple. The
517:framework scatters each field into that port's concretely typed cell. Every
518:reader gathers views from cells. The readers are the next stage,
519:`x_deriv`/`s_update`, [guards](#g-guard), wired consumers and [snapshot](#g-snapshot) capture.
520:
521:**The aggregate `y` is a merge semantically and virtual physically.**
522:Semantically, a component's `y` is the merge of its stage products, `merge(y_x,
523:y_xu)` on the continuous [tier](#g-tier) and `merge(y_s, y_su)` on the discrete. It carries
524:declared ports only. Physically no such object exists. `y` is reconstructed per
525:call from cells, as register-level field loads at zero cost for isbits, and is
526:never stored as an object.
527:
528:Name collisions across a component's stages are a build error.
529:
530:#### What a port may hold
531:
532:**Stage returns are named tuples of port values, period.** A custom struct is a
533:first-class port *value*. It is one field of the returned tuple, one declared
534:port, one cell (`pose = KinPose{T}`). Nested fields get no cells of their own.
535:A reader reaches one through the port's [leaf address](#g-leaf-address) (the
536:field name with dotted and bracketed steps below it), `"pose.q_eb"`
537:([§14.4][s14-4], [D-276][d-276]), and a wired consumer takes the bundle whole. Bare-struct
538:returns are rejected ([D-036][d-036]).
539:
540:A port value's leaves are what the leaf walk reaches through `Real`s, static
541:arrays and isbits structs. An enum is one leaf, pinned ([§8.2][s8-2]).
542:`StopFlag` is the one enum with a framework meaning. An output port of that
543:type is a [stop request](#g-stop-request) (a port that ends the run when it
544:reads `STOP_REQUESTED`), and a `StopFlag` nested in a port of another type or
545:declared as a root input is refused (`IllegalPortType`, [§13.5][s13-5], [D-316][d-316]). The walk
546:stops at an immutable type that is not isbits and treats it as one opaque leaf
547:(a leaf the table stores whole, references included). That leaf is the
548:[field handle](#g-field-handle) ([§4.4][s4-4]). A `Symbol` is an opaque leaf too. Julia classifies
549:it mutable, but it is interned, immutable and never freed, the same grounds
550:[§7.3][s7-3] admits it in a store on, so a `Symbol` mode publishes like any other
551:([D-243][d-243]). A mutable type anywhere in a port value is refused, and so is an
552:opaque leaf surfacing as a root input, which has no synthesis
553:(`IllegalPortType`, [D-237][d-237]).
554:
555:#### Granularity, read side
556:
557:**Rule.** Wiring is port-granular. There are no sub-field connections. A
558:consumer that wants less than a bundle takes the bundle and destructures it,
559:in its own stage or through an unbundling component (a `y_direct` leaf that
560:takes the bundle and publishes its fields, a candidate for the standard
561:library of [§13.7][s13-7]), or asks the producer for a loose port ([D-276][d-276]). A
562:field-projection connector is a [guarded
563:addition](#g-guarded-addition) (a capability the design admits but does not
564:build). Its shape is obvious, and it is not built.
565:
566:**Granularity guideline.** Authors should bundle what *shares a stage* *and is
567:consumed together*. The first criterion is trivially enforced, because each port
568:has exactly one producing function. Bundling across dependency footprints is the
569:classic mistake. A kinematics bundle mixing pose, which is stage 1, with
570:velocity-derived quantities, which are stage 2, must split. Fan-out is free, so publishing both a bundle
571:and a hot loose field (`pose` *and* `q_eb`) is legitimate. It costs one extra
572:isbits cell.
573:
574:**Example.** The sketch below shows the bundle, the loose hot field and a face
575:aliasing an interior port, in declaration form.
576:
577:```julia
578:#a continuous leaf: one bundle port and the hot field published loose — two cells
579:y_types(::Kinematics) = (pose = KinPose{Float64}, q_eb = RQuat{Float64})
580:
581:#the enclosing assembly: each face aliases an interior port, creating no endpoint
582:output_wires(::Vehicle) = ("kin/pose" => "pose", "kin/q_eb" => "q_eb")
583:```
584:
585:#### Granularity, write side
586:
587:**Write-side rule.** **Bundle what is written together.**
588:
589:**Rule.** Data written by different external writers, or at different cadences,
590:must not share a port.
591:
592:Pilot commands are the case in point. They are scalar faces under a namespace
593:prefix. The convenient bundle is assembled *downstream*, inside the graph, by an
594:ordinary component. That is legal by the read-side guideline, since the bundle
595:has a single producer and is consumed together.
596:
597:The guideline and the rule compose into one principle. A port's granularity is
598:set by the finest-grained party owning either end, producers on the read side
599:and external writers on the write side. Field-addressed staging (a lens into
600:struct slots) stays a recorded guarded addition, unbuilt.
601:
602:### 4.4 Function-valued signals: environment access
603:
604:Atmosphere and terrain are **query-shaped**. Consumers evaluate them at
605:arguments of their own choosing, such as each gear strut at its own contact
606:point, or airflow at the vehicle pose. Ordinary [ports](#g-port) therefore carry them as
607:**immutable query objects**, called [field handles](#g-field-handle).
608:
609:- An environment [component](#g-component) emits a field value (`ISAField(T_sl, p_sl, wind)`,
610:  `TerrainField(…)`), and consumers receive it through ordinary input ports.
611:  Inside their own [stage functions](#g-stage-function) (`y_state`/`y_direct`) they call
612:  query functions on it, such as `airdata(field, pos, vel)` and
613:  `ray_intersect(field, p, u)`.
614:- **Parametric models are isbits** (ISA, uniform wind, horizontal terrain).
615:  **Bulk-data models use the handle pattern.** The handle is an immutable struct
616:  combining isbits parameters with references to bulk data (heightmaps, wind
617:  grids, the geoid undulation grid) loaded at build time and frozen. Handles are
618:  rebuilt per evaluation without allocation, as immutable structs holding
619:  existing references. They are never `Ref`s, whose mutable cell allocates.
620:- **No mutable caches inside field objects**, such as memoizing interpolators or
621:  lazy loaders. Concurrent consumers and the GUI thread would race on them.
622:  Caches belong in the consumer's state, or the interpolant is restructured to
623:  be pure.
624:- Loggers treat field-handle signals specially. They skip or summarize them.
625:
626:**The [value-level constructor](#g-value-level-constructor).** Every field-emitting component must expose the
627:map (component, input values) → handle as a plain, pure, public function. For
628:the `SimpleAtmosphere` successor that function is `atmospheric_field(atm; T_sl,
629:p_sl, wind)`. The field-emitting component's swept output stage must be a
630:**one-line call to that function**, never the other way round. The other way
631:round puts the query math in the output stage, where only a [sweep](#g-sweep) can reach it.
632:
633:The reason is script-side. The condition math ([§14.1][s14-1]) must be able to construct,
634:outside any sweep, bit-for-bit the same handle the sweep would produce from the
635:same [root input](#g-root-input) values. One implementation serves two call sites, so there is no
636:drift. The drift avoided here is the silent-drift class that [§5.3][s5-3] exists to
637:kill. This is a *shipped component's obligation*, not something a consumer can
638:retrofit. The real component composes sub-models, and anyone else reconstructing
639:the map has re-created the drift class.
640:
641:For bulk-data components the obligation is only that the query math be reachable
642:as a plain function. They own their resource loading, so building a handle
643:outside a build may cost a load. That cost is acceptable, because condition
644:authoring is design-time code.
645:
646:**Example.** The sketch below shows the map as a plain function, and the stage
647:that does nothing but call it.
648:
649:```julia
650:#the map: plain, pure, public — callable outside any sweep
651:atmospheric_field(atm; T_sl, p_sl, wind) = ISAField(…)
652:
653:#the swept output stage: one line, nothing but the call
654:y_direct(atm, args) = (; … = atmospheric_field(atm; T_sl = …, p_sl = …, wind = …))
655:```
656:
657:Pre-sampling is an **idiom built on top**, used where natural, not a separate
658:mechanism. In it, a component consumes the field and a pose and emits plain
659:data, as `Airflow` emits `AirData` for the whole vehicle. Resource injection
660:(declare-and-resolve service registries) is closed for the first cut ([D-008][d-008]).
661:
662:The field-handle mechanism replaces threading `atmosphere`/`terrain` as
663:arguments through every update signature. It dovetails with the terrain
664:ray-query direction of the landing-gear redesign. Substitutability behind a
665:stable [face](#g-face) is declared with an abstract input entry, `terrain =
666:AbstractTerrainField`, which is structural substitutability ([§8.2][s8-2]). The consumer
667:wires to any concrete field type below the bound. That preserves today's
668:`AbstractTerrain` polymorphism at the declaration layer.
