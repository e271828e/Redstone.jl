## 11. Runtime periphery: the data plane

This chapter specifies the data plane, how data crosses between the loop (§10) and the periphery (GUI, input devices, network I/O and logging), taking root inputs (§8.6) as given. §11.1 covers the architecture that replaces FlightCore's shared mutable model; §11.2 the outbound data channel, snapshot publication; §11.3, §11.4 and §11.5 the inbound data channel, in turn its root inputs, claims and frozen roster, its per-device staging and drain, and its input trace; §11.6 the device authoring contract; §11.7 the GUI write path; and §11.8 the third cross-task channel, runtime diagnostics and liveness.

The machinery that drives the loop itself follows in §12.

### 11.1 No shared mutable model: staged writes, snapshot reads

Everything in the periphery (GUI, input devices, network I/O, logging) runs on tasks the loop does not control, and every one of them wants the data the loop is stepping. FlightCore's answer is one big lock. In FlightCore's `sim.jl`, `SimControl` and the live `Model` are guarded by `io_lock`, with one task per attached interface reading or mutating the model under it. That lock does enforce the boundary-visibility rule (§10.3), a boundary being a published consistency point, because the lock is only ever free between steps. Transplanting it here was nevertheless rejected, on three structural costs (D-022). One of the three is decisive for everything below. Under a lock, input timing is scheduler-determined and unrecorded. There is then no defined input trace (the primary record of a session), and bit-identical replay (the ordinary loop with its drain reading the trace, §12.7) is unachievable in principle for interactive runs. This section sets out the five planes that replace the lock, the two rules that bind their implementation, the task topology, and one consequence for execution modes.

The replacement has five planes. Its unit of account is the frame (one grid step, §10.1). Each frame is one iteration of the loop, which runs the drain (the frame-top swap that applies staged device writes to the root inputs), then integrates, then runs the boundary sequence, then publishes. A frame is what `step!` counts, and it is the ordinal that keys the trace (D-101). "Per frame" means this throughout the document. The kinematic reference frames of the aircraft domain are a different word, and they always appear compounded, as in the b frame and the ECEF frame. The b frame is the body frame, and ECEF stands for Earth-centered, Earth-fixed.

1. Staging is the inbound path (§11.4). Devices (attached participants in the periphery) submit pending input writes at any wall-clock moment, never touching live root inputs (the root component's own input faces). 2. The drain is exactly one point in each frame, at its top, where the loop takes the staged batches and applies them to the root inputs (D-022). It never happens at a `t` boundary (§10.4). Between drains the loop owns its data exclusively, and no lock is held during stepping, ever. 3. Publication is the outbound path. The loop publishes an immutable snapshot (a boundary-consistent signal table with its framework status) at the end of each boundary sequence (D-022). Readers observe it without coordinating with the loop (§11.2). 4. Control places pause, pace and stop on a separate few-word atomic surface (§12.1, D-022). 5. Task topology places one loop on the calling task (the task that invoked `run!`) and one spawned task per rostered device, all run-scoped.

Two rules bind the implementation.

- Every handoff is one atomic reference operation (D-022). The staging cells (where a device's pending write batch waits between drains) and the reference to the published snapshot reduce their mutable surface to single words, release/acquire `@atomic` fields. The GC is the reclamation mechanism, since an object a reader still holds is reachable and therefore never recycled. That dissolves the reclamation problem (hazard pointers, epochs, RCU grace periods) which makes these patterns hard in non-GC languages. Deep immutability of the exchanged objects is what makes this sound.

- No user code, no unbounded work, ever, inside a framework critical section (D-022). FlightCore's pathologies are all "arbitrary code under a shared lock". Here mappings run on device tasks (§11.4), rendering runs against snapshots, and the loop's frame contains framework and model code only. A stalled device produces stale snapshots and late staging. It cannot stall the loop. Two exposures are residual and pre-existing, GC pauses and OS scheduling, and the pacer's debt absorption (§10.7) is the mitigation for both.

The fifth plane carries the most machinery, and the paragraphs below spell it out.

Device tasks are run-scoped (D-093). `run!` spawns one task per entry of the roster (the list of attached device entries) after device `init!`, and §12.4 joins them all at every stop (§12.6). `attach!` never spawns. It registers, in a stopped-sim state only (§11.3), and the task appears at the next `run!`.

The loop runs on the calling task (D-310). The calling task runs the loop itself, and every rostered device runs on a spawned task. This is what the synchronous rethrow (§13.4) presupposes. It is also what lets parallel unattended sweeps thread `run!` inline with no nested task fan-out. One immutable `Build` (the artifact `build(world)` produces) is shared across the workers (§9.2, D-282), and each `Simulation` owns its own buffers (the framework-owned vectors backing continuous state, §9.4). Pre-materializing the sweep's activations (the build's typed products at a scalar type) with `build(world; activations = …)` (§9.4, D-135) then leaves no worker synchronizing on anything. `run!` blocks its caller until the run ends.

Which devices get a task is decided after initialization, from the frozen roster and the outcomes of device `init!`, never from `run!`'s keywords (D-310, D-138). A device whose `init!` failed gets no task (§12.4, D-138).

Spawn-inside-`run!` is the start gate (D-093). A task exists only once the run it serves exists. Any first-boundary synchronization a device needs is the counter-plus-condition predicate wait (§12.3), never a `Base.Event` latch.

One consequence is recorded here because it collapses an API axis. Interactive and unattended simulation stop being different execution modes (D-022). An unattended run is the same loop with empty staging and no snapshot readers. A replayed interactive session is the same loop with staging fed from a recording (§11.5, §12.7).
