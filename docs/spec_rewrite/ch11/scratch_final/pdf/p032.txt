Root inputs
The write surface is the set of faces the entries of a writer's batch (its staged set of writes, applied 
whole at the next drain) may reach. Its members are root inputs. A root input is the root component's 
own input face, an assembly's input_wires key or a primitive's u_types key ( §8.2, §8.6, D-208). A 
component is the unit of modeling, and a face is the name a port wears on its component's boundary. 
A root input is routed inward to consumers and produced by no component. At every non-root level 
an input face is fed by the parent's wire, and at the root there is no parent. No dedicated vocabulary 
is needed.
A root input is usefully read as the output face of the one producer the build never sees, the periphery 
and the services. On that reading, root-input exclusivity (below) is that producer's one-writer right, 
and the totality (§14.6) is its completeness obligation.
Root inputs are sources to the build-time ordering, and they are constants within a frame (one iter-
ation of the loop). They are the only thing the periphery may write (D-031). The GUI reaches them 
through port resolution ( §11.7), and control commands are not writes ( §12.1). Devices, mappings, 
the trace (the primary record of a session) and the GUI write path address root inputs by face name 
(§8.6). Structural slash paths never reach the periphery's writes. The write side speaks the names 
of the root's contract, the interface the root component declares, and no others ( D-129). The read 
side chooses per binding (the value passed at attach! that makes a device framework-legible). It 
uses slash paths in inspection reads, and face names in integration reads and in service reads (§11.2/
§13.5/§14.4).
Exclusivity and claims
Root-input exclusivity permits at most one writer per root input at any time  (D-044). A 
device claims its root inputs (stakes them as faces it may write) at attach, and claiming an already-
claimed root input is an attach-time error. Detaching releases the claims. A released root input's 
GUI widgets are live again from the next run (§11.7). Exclusivity replaces any cross-device conflict 
policy (D-044), such as attachment-order precedence at the drain (the frame-top swap that applies 
staged device writes to the root inputs). Per-device staging cells (where each device's pending batch 
waits between drains), the compare-and-swap (CAS) merge and the atomicswap drain all stay. They 
serve atomicity and coalescing (keeping one pending batch per device), not arbitration.
Exclusivity holds because a second live writer on one root input makes the applied value a timing 
artifact, as the worked example in §11.4 shows. The usual pair is a stream and its mirror, a joystick 
axis and the GUI slider showing it. Claiming the stream settles that pair with no concurrent writing.
A claim is what a device may write, not what it will. Data-dependent write-sets are ordinary. A UDP/
JSON peer writes whichever subset of faces the incoming message names, and map_input is arbitrary 
user code the framework never inspects. Such a device therefore claims the binding's enumerated 
allowed set, the faces the binding table lists, whether or not any given batch touches them. The 
claim is registered at attach exactly as a joystick's is. A broad claim costs liveness. Every enumerated
