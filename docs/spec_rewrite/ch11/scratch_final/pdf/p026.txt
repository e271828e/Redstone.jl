11. Runtime periphery: the data plane
This chapter specifies the data plane, how data crosses between the loop ( §10) and the periphery 
(GUI, input devices, network I/O and logging), taking root inputs ( §8.6) as given. §11.1 covers the 
architecture that replaces FlightCore's shared mutable model; §11.2 the outbound data channel, 
snapshot publication; §11.3, §11.4 and §11.5 the inbound data channel, in turn its root inputs, claims 
and frozen roster, its per-device staging, staged representation and drain, and its input trace; §11.6 
the device authoring contract; §11.7 the GUI write path; and §11.8 runtime diagnostics and liveness, 
a third channel between tasks beside the two data channels.
The machinery that drives the loop itself follows in §12.
11.1 No shared mutable model: staged writes, snapshot reads
Everything in the periphery (GUI, input devices, network I/O, logging) runs on tasks the loop does 
not control, and every one of them wants the data the loop is stepping. FlightCore's answer is one 
big lock. In FlightCore's sim.jl, SimControl and the live Model are guarded by io_lock, with one task 
per attached interface reading or mutating the model under it. That lock does enforce the boundary-
visibility rule (§10.3), because the lock is only ever free between steps. A boundary is a published 
consistency point. Transplanting the lock here was nevertheless rejected, on three structural costs 
(D-022). One of the three is decisive for everything below. Under a lock, input timing is scheduler-
determined and unrecorded. There is then no defined input trace (the primary record of a session), 
and bit-identical replay (the ordinary loop with its drain reading the trace, §12.7) is unachievable 
in principle for interactive runs. This section sets out the five planes that replace the lock, the two 
rules that bind their implementation, the task topology, and one consequence for execution modes.
The replacement's unit of account is the frame (one grid step, §10.1). Each frame is one iteration 
of the loop, which runs the drain (the frame-top swap that applies staged device writes to the root 
inputs), then integrates, then runs the boundary sequence, then publishes. A frame is what step! 
counts, and it is the ordinal that keys the trace ( D-101). "Per frame" means this throughout the 
document. The kinematic reference frames of the aircraft domain are a different word, and they 
always appear compounded, as in the b frame and the ECEF frame. The b frame is the body frame, 
and ECEF stands for Earth-centered, Earth-fixed.
The replacement has five planes.
1. Staging is the inbound path ( §11.4). Devices (attached participants in the periphery) submit 
pending input writes at any wall-clock moment, never touching live root inputs  (the root 
component's own input faces).
2. The drain is exactly one point in each frame, at its top , where the loop takes the staged 
batches (each device's set of pending writes) and applies them to the root inputs (D-022). It never 
happens at a t* boundary (§10.4). Between drains the loop owns its data exclusively, and no lock 
is held during stepping, ever.
