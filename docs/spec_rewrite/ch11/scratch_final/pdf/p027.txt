3. Publication is the outbound path. The loop publishes an immutable snapshot (a boundary-
consistent signal table with its framework status) at the end of each boundary sequence (D-022). 
Readers observe it without coordinating with the loop (§11.2).
4. Control places pause, pace and stop on a separate few-word atomic surface (§12.1, D-022).
5. Task topology places one loop on the calling task (the task that invoked run!) and one spawned 
task per rostered device, all run-scoped.
Two rules bind the implementation.
• Every handoff is one atomic reference operation (D-022). The staging cells (where a device's 
pending write batch waits between drains) and the reference to the published snapshot reduce 
their mutable surface to single words, release/acquire @atomic fields. The GC is the reclamation 
mechanism, since an object a reader still holds is reachable and therefore never recycled. That 
dissolves the reclamation problem (hazard pointers, epochs, read-copy-update grace periods) 
which makes lock-free handoffs hard in non-GC languages. Deep immutability of the exchanged 
objects is what makes this sound.
• No user code, no unbounded work, ever, inside a framework critical section  ( D-022). 
FlightCore's pathologies are all "arbitrary code under a shared lock". Here mappings run on device 
tasks (§11.4), rendering runs against snapshots, and the loop's frame contains framework and 
model code only. A stalled device produces stale snapshots and late staging. It cannot stall the 
loop. Two exposures are residual and pre-existing, GC pauses and OS scheduling, and the pacer's 
debt absorption (§10.7) is the mitigation for both.
The fifth plane carries the most machinery, and the paragraphs below spell it out.
Device tasks are run-scoped  (D-093). run! spawns one task per entry of the roster (the list of 
attached device entries) after device init!, and §12.4 joins them all at every stop ( §12.6). attach! 
never spawns. It registers, in a stopped-sim state only (§11.3), and the task appears at the next run!.
The loop runs on the calling task (D-310). This is what the synchronous rethrow (§13.4) presup-
poses. It is also what lets parallel unattended sweeps thread run! inline with no nested task fan-out. 
One immutable Build (the artifact build(world) produces) is shared across the workers (§9.2, D-282), 
and each Simulation owns its own Model, and with it the Model's buffers (the framework-owned 
vectors backing continuous state) (§9.4). Pre-materializing the sweep's activations (the build's typed 
products at a scalar type) with build(world; activations = …) (§9.4, D-135) then leaves no worker 
synchronizing on anything. run! blocks its caller until the run ends.
Which devices get a task is decided after initialization, from the frozen roster and the outcomes of 
device init!, never from run!'s keywords (D-310, D-138). A device whose init! failed gets no task 
(§12.4, D-138).
Spawn-inside-run! is the start gate (D-093). A task exists only once the run it serves exists. Any 
first-boundary synchronization a device needs is the counter-plus-condition predicate wait (§12.3), 
never a Base.Event latch.
One consequence is recorded here because it collapses an API axis. Interactive and unattended 
simulation stop being different execution modes (D-022). An unattended run is the same loop with 
empty staging and no snapshot readers. A replayed interactive session is the same loop with staging 
fed from a recording (§11.5, §12.7).
