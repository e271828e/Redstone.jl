11.4 Inbound: per-device staging, representation and the drain
A device (any attached participant in the periphery) produces writes on its own task, whenever 
its hardware or its peer hands it a datum. The loop consumes them at the top of each frame (one 
iteration of the loop). Between those two rates something has to hold each device's pending writes 
and hand the loop a value it can apply. That something is the staging cell (the per-device atomic 
holding place for pending writes), a compound term distinct from a table cell (D-121). Unlike a table 
cell it is mutated frame by frame, outside the table's publish-once discipline. This section first fixes 
the coalescing policy (the compare-and-swap, or CAS, merge that keeps one pending set of writes 
per device) under which a device writes into its staging cell. It then fixes the doctrine for staged 
values, the mappings that produce them, the shape the staging cell holds, the sites of the staging 
diagnostics, and the drain (the frame-top swap that applies staged device writes to the root inputs) 
that empties it. A worked example closes the section.
The coalescing policy
Staging keeps one atomic staging cell per attached device (D-024). Staging has one coalesc-
ing policy, CAS merge, newest wins per face (D-104). A device's staging cell has a single writer, 
its own device task. It holds that device's latest pending batch (a set of writes applied whole at the 
next drain). Each write in it targets a root input (the root component's own input face). Staging 
merges the incoming batch into the pending one. Untouched faces (the names ports wear on their 
component's boundary) survive, and re-staged faces take the newest level. That is the per-face zero-
order hold (ZOH). For a device's staging cell, the CAS can fail only because a drain intercepted the 
old batch, so the retry is bounded. The failure case is precisely correct as well. Intercepted writes 
are already applied, and must not be re-staged. The harness cell (the always-present staging cell 
of the harness writer) is the exception to the single writer, since several tasks may stage into it 
concurrently, and a CAS that fails because another stager merged first retries the same way (D-200).
Merge is the only policy because it is always correct. A complete writer covers every face in every 
batch it stages. A joystick delivering its full write-set every poll is the type case. For such a writer 
merge and overwrite are provably the same operation, which makes overwrite a degenerate fast 
path rather than a second semantics. A sparse writer stages only what was touched. The GUI and a 
JSON peer are sparse writers, and under overwrite they lose writes silently instead. Under overwrite, 
a pending flaps edit is clobbered by an unrelated gear message, undrained and undiagnosable. The 
worked example at the end of this section works that hazard through. A user-facing overwrite opt-
in (complete(binding)) is closed (D-104).
The levels doctrine
The levels doctrine says that staged values are levels, never deltas (D-024), as in press_count = 
17, never presses += 1. Levels are idempotent and survive coalescing. Edge logic follows the levels 
doctrine, and button edges ride as monotonic press counters, which devices stage. Accumulators 
(trim offsets, flap detents) are model state, not mapping state (D-045).
