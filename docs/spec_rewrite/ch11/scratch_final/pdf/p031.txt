Output-device bindings
Output-device bindings are snapshot bindings (D-083). A binding is the value passed at attach! 
that makes a device framework-legible. An output device consumes snapshots as §12.3 specifies. 
Examples are telemetry, disk streaming and the XPlane visualizer (FlightCore's XPlane12Control 
output device). An output device addresses what it reads with the selectors (the closed family of 
deferred reads resolving against a source, §14.4). They reach any cell, since inspection reads admit 
deep paths. A binding is resolved at attach against the Build with did-you-mean (the offending 
name plus the list-in-hand it should have matched), and compiled to one gather, the output half 
of the binding interface (§11.6). map_output therefore receives a labeled NamedTuple (§11.6) instead 
of performing its own path lookups. A model substitution that breaks a binding therefore fails at 
attach, not with silent garbage on the wire. Attach refuses such a binding with ReadBindingUnresolved 
(D-130). An exporting logger treats field-handle signals specially. It skips or summarizes them.
An output device's read of the snapshot is inspection ( §13.5, D-083). It is human-facing, with no 
effect on run semantics. It is observation of the same sort as the log retaining the full table and the 
GUI's deep-reading panels. Every cell is reachable, because the table is public throughout (§8.3).
A binding chooses its side (D-129). A deep path is an inspection read. It makes zero promises, gives 
free access, and is right for looking at this build. An exported output face, spelled get_face(name) 
(§14.4), is an integration read. It is named, curated and meaning-stable under substitution, and right 
for consumers that outlive the build they were configured against. What makes a face meaning-
stable is writer-independent semantics (§11.4, D-045).
The choice matters because of drift. Attach validation converts structural drift to loud errors on 
both sides (D-083). Only faces protect against semantic drift. In semantic drift, a substituted aircraft 
publishes the same path at the same type with a different meaning, such as a center-of-gravity 
velocity under a name read as body-origin velocity. Nothing else can protect against it, because 
meaning is not in the schema.
Semantically generic consumers should therefore bind faces ( D-083). A visualizer needs pose, and 
every aircraft has one. Aircraft families should export the conventional surface such consumers 
need, a library/migration deliverable (the migration outline companion). Wrapper types make face 
semantics structurally checkable. An example is VelocityData, an illustrative wrapper type, with its 
v_eb_b defined at the type as body-origin velocity. A bare vector does not wire, and wrapping the 
wrong quantity is a deliberate lie, not a drift.
