11.2 Outbound: snapshot publication
Every consumer of model state needs a picture of the model that holds still while it is read. GUI 
panels and output devices (attached participants in the periphery) are such consumers. So is the log 
(the retained sequence of published snapshots). None of them should have to make the loop wait 
to get one. Publication is the answer. One immutable value is published per boundary (a published 
consistency point), handed out through a single atomic reference. Three things follow from it. In 
order, they are how a snapshot (the immutable per-boundary publication) is built and published, 
how the log retains published snapshots under a bound, and how an output device addresses what 
it reads.
The snapshot and its publication
The loop builds each snapshot in private memory, then publishes it with a single release-
store (D-023) to an @atomic latest reference (the single handout point for published snapshots). 
A snapshot carries the boundary-consistent signal table (the cells holding every produced signal) 
and t. It carries the index of its frame (one iteration of the loop) and its published-boundary ordinal 
(§12.3). It also carries the framework status (the run's diagnostics and liveness record, §11.8). The 
frame index is what places a t* snapshot in its frame, since a t* publication counts an ordinal of 
its own (D-261). Readers acquire-load that reference and then work with an immutable, coherent 
world for as long as they like. The calling task (the task that invoked run!) reads the same value 
through latest(sim), an inspection read (§12.6).
The exchange is wait-free in both directions (D-023). A wedged reader cannot delay publication by a 
nanosecond, and the loop cannot tear a reader's view. Publication happens only after the boundary 
sequence completes (§10.3, D-293).
The binding rule states that nothing reachable from a published snapshot is ever written 
again (D-023). The soundness of lock-free reading rests on this rule. The table's immutable values 
(§4.1, §7) make the compiler enforce most of it.
The framework status is a concrete frozen value, not a window onto live bookkeeping (D-136). §11.8 
lists what it carries. The binding rule forces that shape. A status referencing an accumulator its 
writers are still filling would be a snapshot whose contents change after publication.
The captured table is the whole table. It holds the declared ports (the addressable unit, one declared 
name with one cell), every one of them public ( §8.3). No presentation layer has anything to filter. 
Undeclared intermediates are not in it, because only declared ports are cells (the signal table's typed 
value holders, one per output port, §8.3). The inspection path for one is promotion to a declared 
output (D-194). Add a line in y_types, and the value appears in the snapshot, the log, the GUI and 
the wiring alike. Its visibility is then an authored fact like every other.
The captured table also includes the root inputs (D-047). Root inputs are the root component's 
own input faces (the names ports wear on their component's boundary). They are source cells of 
the table, not state stores, so they ride along. That is essential, not incidental. The peek (showing 
a widget's own pending write, else the snapshot value, §11.7) falls back to the snapshot, and that 
fallback is what an idle live widget displays. Read-only mirrors of claimed root inputs, such as the 
axis sliders under joystick claim (the set of faces a device may write), show the applied root-input 
value from the snapshot. Root input values in the log are derived data, recomputable from the trace 
(the primary record of a session). That is consistent, because snapshots are derived wholesale.
