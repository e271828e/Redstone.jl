The snapshot deliberately does not carry the state stores  x, s and m (D-038). There are two 
reasons. The state trajectory is derived data, recomputable from the trace header (the trace's fixed 
preamble) plus the batches of staged device writes (§11.5). The recomputation is bit-identical replay 
(the ordinary loop re-driven from the trace). And per-boundary capture would systematically record 
derived data, the same asymmetry the trace-default decision (D-029) refuses in the other direction.
"What was the private state at t = 37.2?" is answered by replaying to 37.2 and inspecting the live 
stores (D-038). A state field wanted in logs or GUI has the honest remedy of being declared public 
and returned from y_state (§5.3, D-252). It costs one cell per sweep (one pass through the execution 
order). Post-run continuation reads the live stores directly. Periodic full-state checkpoints are a 
guarded addition (a capability the design admits but does not build), shaped as an opt-in log policy 
(D-038). They would allow warm restart without replay from zero. Each would retain a checkpoint 
(the Model's state at a frame top as one value), the value checkpoint(sim) returns (§12.6). A dev-mode 
flag that reads every state field out of the stores is a possible future diagnostic. It would be a reader 
over the stores, never a port class (D-252).
Event firings are not recorded  (D-309). The log holds boundary snapshots and the trace holds 
staged inputs (§11.5). Neither carries a per-event record. Replay plus the published modes recovers 
which events fired at which boundary. The honest remedy is again to declare the mode field public 
and return it from y_state (D-252). A mode field so exposed is in every snapshot. An event-firing 
stream is a guarded addition.
The log: retained snapshots under a bound
The log is a vector of retained snapshot references (D-023). Logging thus dissolves into publi-
cation. The references are the same objects, with zero extra copies. The per-step deepcopy detour 
of FlightCore's SavingCallback disappears. The cost is one snapshot allocation per boundary. It falls 
on the framework side of the allocation scope §9.8 sets, which already carved out logging. Logged 
snapshots are not garbage at all, and unlogged ones die young. Preallocated snapshot buffers are 
rejected (D-023).
Log retention is the trace's kill switch, plus decimation (D-038). The log takes the same plain 
on/off switch the trace has ( §11.5). Decimation is the log's additional keep-every-kth retention 
policy, log_every (Appendix B).
The derived/primary split ( D-038) decides why decimation is admissible here and not there. The 
log is recomputable from the trace by replay, so a thinned log costs resolution in a view, never in a 
record. Thinning the trace would destroy the only primary account of a session (D-029). Decimation 
is a retention policy only. Every boundary still runs, is still published to live readers, and still enters 
the trace (D-038).
Decimation slows the log's growth. It does not stop it. The default configuration is log = true, 
log_every = 1 alongside t_end = Inf, init!'s and run!'s defaults (Appendix B). Under it the log grows 
for as long as the session lasts. At the scale of the C172X (FlightApps' Cessna 172X model) and 50 
Hz, that is gigabytes per hour. It ends in an out-of-memory nobody was warned about.
The log takes a retention bound beside its switch and its stride (D-137). The bound is log_max, 
the maximum number of retained snapshot references. Its default is 65536 (2¹⁶), with Inf the explicit 
opt-out (D-137). The four recording keywords appear on init! with their defaults (Appendix B).
