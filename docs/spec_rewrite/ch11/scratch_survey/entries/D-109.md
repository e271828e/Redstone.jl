3372	### D-109 — Fix device identity, roster admission and calling-task topology at attach
3373	
3374	**Status.** superseded → [D-310][d-310]
3375	
3376	**Position.** Device identity, roster admission and calling-task topology:
3377	identity is the instance (`===`, one roster entry each; two instances of one
3378	type are two devices), the stable device id is assigned at `attach!` (monotonic
3379	per `Simulation`, never reused, lives with the entry across runs); admission is
3380	a three-part check at attach — identity (`AlreadyAttached`; rebinding =
3381	`detach!` + `attach!`), affinity (at most one `needs_calling_task` holder,
3382	`CallerTaskConflict`), claims (`ClaimConflict`, now always between distinct
3383	devices).
3384	
3385	**Spec.** [§11.1][s11-1], [§11.3][s11-3], [§11.6][s11-6], [§12.4][s12-4], [§12.6][s12-6], [Appendix B][sB]
3386	
3387	**Rationale.** Calling-task affinity is a device-contract trait (default
3388	`false`, the shipped GUI's CImGui constraint made declarable), task topology is
3389	derived from the frozen roster alone, never from `run!` keywords — with an
3390	affine device rostered the loop moves to a spawned task and the calling task
3391	runs that device's loop body inline in the identical [§11.6][s11-6] wrapper, else the
3392	loop runs on the calling task; the affine device is outside [§12.4][s12-4]'s join and
3393	abandonment (nothing can abandon the task `run!` stands on — its authoring
3394	obligation is a loop body that never blocks between `running` checks); `gui =
3395	true` becomes idempotent attach sugar (ensure-rostered, attach only if absent,
3396	never detaches), so a persisted GUI renders on every later run without the
3397	flag.
3398	
3399	Annotation (from the R3(a) adjudication, 2026-08-13): the derivation point and
3400	its `init!`-outcomes term were sharpened after this entry was written —
3401	topology is derived *after initialization*, from the roster **plus `init!`
3402	outcomes**, not from the frozen roster alone. [§11.1][s11-1] and [§12.4][s12-4] carry the
3403	canonical statement, and the looser "roster-derived" shorthand elsewhere
3404	([D-093][d-093], [§12.6][s12-6]) stands as shorthand for it.
3405	
3406	**Rejected.**
3407	- *Sugar-only idempotency guard:* leaves explicit double-attach of the GUI
3408	  undefined — two render loops contending for the calling task would falsify
3409	  [§11.1][s11-1]'s topology by user action.
3410	- *Idempotent no-op on re-`attach!` of a rostered device:* silently discards
3411	  the binding the caller handed over — the warn-but-continue pattern.
3412	- *Flag-derived loop placement:* contradicts roster persistence on the second
3413	  run: a rostered GUI must render without the flag.
3414	- *Special-casing the shipped GUI type instead of a trait:* a user-authored
3415	  calling-task device — another renderer — would get no admission check and no
3416	  topology treatment.
3417	- *Silent double-rostering of claim-free readers:* two tasks racing on one
3418	  device instance's own state, double `init!`/`shutdown!` on one OS resource.
3419
