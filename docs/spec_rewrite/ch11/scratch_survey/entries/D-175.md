6400	### D-175 — Re-scope `gui = true` to a run-scoped attachment
6401	
6402	**Status.** superseded → [D-310][d-310]
6403	
6404	**Position.** `gui = true` is re-scoped from persistent attach sugar to a
6405	run-scoped attachment: at run entry the flag attaches the shipped GUI device
6406	under the greedy binding with `should_abort = true` iff no GUI is rostered, and
6407	at run exit it detaches what it attached — the detach sitting in [§12.4][s12-4]'s
6408	shutdown tail, so it is taken on the error path too. A persistent GUI session
6409	is spelled manual `attach!`, and against a manually attached GUI the flag does
6410	nothing and detaches nothing.
6411	
6412	**Spec.** [§11.6][s11-6], [§12.4][s12-4], [§12.6][s12-6], [Appendix B][sB]
6413	
6414	**Rationale.** Motivation: under [D-174][d-174]'s computed claims a persisted greedy
6415	claim is a **stale-claim trap** — the everything-claim staked on run 1 survives
6416	into run 2, where a joystick attached between runs collides with it
6417	(`ClaimConflict`) although nothing in the user's model of the flag says a GUI
6418	is holding those faces; run-scoping dissolves it without introducing a second
6419	claim-staking point in the lifecycle, since the flag's attach happens at a
6420	stopped-sim instant like any other.
6421	
6422	Cost accepted: per-run device-id churn for the flag-attached GUI (ids exist to
6423	be read across roster changes, and each run's trace header carries its own
6424	schemas, so nothing that reads a completed run is affected).
6425	
6426	**Rejected.**
6427	- *The prior [§12.6][s12-6] semantics — an idempotent flag that never detaches:* hidden
6428	  roster state accumulated by a convenience argument, plus the `ClaimConflict`
6429	  trap above, whose only remedy is a `detach!` the user never issued an
6430	  `attach!` for.
