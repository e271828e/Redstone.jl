9125	### D-240 — Read the heartbeat at publication, beside the task state
9126	
9127	**Status.** ratified
9128	
9129	**Position.** The loop acquire-loads each device's heartbeat timestamp when
9130	it assembles the published status, beside the `task_state` it reads off the
9131	device's `Task` handle. The drain does not touch it.
9132	
9133	**Spec.** [§11.8][s11-8], [§12.2][s12-2]
9134	
9135	**Rationale.** [§11.8][s11-8] said the loop acquire-loads the heartbeat at the drain
9136	and, twelve lines on, that it rides in the status beside the task state read
9137	at publication. The implementation reads at publication, and that is the
9138	site with a reason. A status published at a `t*` boundary has no drain before
9139	it, so a drain-side read would hand it the previous frame top's timestamp.
9140	The value is advisory ([§12.2][s12-2]), a staleness display against a 2 s threshold,
9141	so freshness at the moment of publication is the whole of what it is for.
9142	
9143	**Rejected.**
9144	- *Acquire-load at the drain, copy into the status:* one more field on the
9145	  per-writer account, carried across the frame to publish an older
9146	  timestamp; the `t*` publication would report the drain's reading rather
9147	  than its own moment.
9148
