6956	### D-189 — Unify `report!` on a single `(address, diagnostic)` shape
6957	
6958	**Status.** ratified
6959	
6960	**Position.** `report!` regains a single shape, `report!(address, diagnostic)`:
6961	the diagnostic is always a constructed value and the first argument is the cell
6962	address — the device handle inside the task, the roster entry in [§12.4][s12-4]'s
6963	pre-spawn init bracket, where no handle exists yet.
6964	
6965	**Spec.** [§11.6][s11-6], [§11.8][s11-8], [§12.4][s12-4], [Appendix B][sB], [Appendix C][sC]
6966	
6967	**Rationale.** The address supplies the device identity, which is why no call
6968	passes a device id even though [Appendix C][sC] lists it in both payloads; [D-160][d-160]'s
6969	definition and [Appendix B][sB]'s handle-capability listing stand unchanged.
6970	
6971	**Rejected.**
6972	- *Renaming the framework-internal form:* treats one operation — write a
6973	  device-attributed diagnostic into that device's [§11.8][s11-8] cell — as two, when only
6974	  the addressing differs.
6975	- *Keeping the kind-first positional form `report!(DeviceCrash, dev, e)`:* a
6976	  bare type in argument position beside the constructed-value form every other
6977	  site uses, and one name owning two unrelated signatures — the polysemy [D-122][d-122]
6978	  legislates against.
