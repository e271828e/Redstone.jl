7605	### D-206 — Rename root slots to root inputs
7606	
7607	**Status.** ratified
7608	
7609	**Position.** The write surface's member term is renamed: "slot" / "root
7610	slot" / "root input slot" → **root input** ("the model's root inputs" where
7611	prose flow wants it), sweeping the spec and its companions per the standing
7612	rename rule — forward, never the log. Four API spellings follow:
7613	
7614	- the condition fragment keyword `slots` → `inputs`
7615	  (`fragment(; x, s, m, inputs)`);
7616	- the table selector `get_slot(face)` → `get_input(face)`;
7617	- the diagnostic kind `UninitializedSlots` → `UninitializedInputs`;
7618	- the diagnostic kind `RootSlotTypeConflict` → `RootInputTypeConflict`.
7619	
7620	**Spec.** [§4.1][s4-1], [§11.3][s11-3], [§14.2][s14-2], [§14.4][s14-4], [§14.6][s14-6], [Appendix C][sC]
7621	
7622	**Rationale.** "Slot" was opaque coinage: it demanded a recall step on every
7623	read, where "root input" decodes itself — and under [D-208][d-208] the definition
7624	collapses to near-tautology (a root input is the root component's input
7625	face), which is what vocabulary should do. The qualifier "root" carries the
7626	real distinction against the input ports, faces and entries that exist at
7627	every level. The bare spellings `inputs` and `get_input` are safe in their
7628	scopes — nothing else in a fragment payload or the selector family could be
7629	meant — and `get_input`/`get_output` gain symmetry, with the inherent
7630	addressing asymmetry (face name vs structural path, [§11.3][s11-3]'s write-surface
7631	rule) accepted.
7632	
7633	**Rejected.**
7634	- *Keeping "slot":* brevity was its only virtue; it never carried its
7635	  meaning.
7636	- *`get_root_input`:* precise but heavy in the selector family's naming.
7637
