5102	### D-146 — Rename `faces`/`selectors` to `claims`/`reads` on the binding interface
5103	
5104	**Status.** ratified
5105	
5106	**Position.** Binding-interface enumeration renames: `faces(b)` → `claims(b)`
5107	and `selectors(b)` → `reads(b)`; signatures, semantics and
5108	detection-by-method-presence unchanged. Rows ≤ [D-145][d-145] are historical and stay
5109	unamended. `claims(b)`: what the declaration does is stake the claim set ([§11.3][s11-3])
5110	— the enumerated faces become the device's claimed write surface — so the name
5111	plugs straight into [§11.3][s11-3]'s central claim vocabulary (claim set, claim
5112	partition, `ClaimedFaceEntry`, claims orphaned to run end) and retires the last
5113	method-name use of the spec's most polysemous noun, "face" ([D-144][d-144] dissolved the
5114	other one, leaving this the sole survivor). `reads(b)`: the declaration
5115	establishes the binding's declared read set — a tuple of [§14.4][s14-4] selectors,
5116	validated at attach and compiled to one per-boundary gather whose labeled
5117	NamedTuple `map_output` receives — and [§14.7][s14-7]'s `TrimProblem` already carries
5118	that exact concept under that exact name, with the identical declared-set →
5119	validated-at-mount → compiled → materialized lifecycle (its `reads` field
5120	resurfacing as the `reads` argument of `residuals(reads, d)`): same concept,
5121	same name. The interface thereby gains a clean sim-centric write/read pair,
5122	`claims(b)`/`reads(b)`, sitting over the existing sim-centric
5123	`map_input`/`map_output` pair. Scope fence: the vocabulary "selector(s)" is
5124	untouched wherever it names the `get_*` values or their families (table
5125	selectors, store selectors, path selectors, [§14.10][s14-10]'s tap selectors, "[§14.4][s14-4]
5126	selectors"); only the binding method renames, and `reads(b)` still returns
5127	[§14.4][s14-4] selectors.
5128	
5129	**Spec.** [§8.1][s8-1], [§11.3][s11-3], [§11.6][s11-6], [§14.4][s14-4], [§14.7][s14-7], [§14.10][s14-10], [Appendix B][sB], [Appendix C][sC],
5130	[Appendix D][sD] (swept)
5131	
5132	**Rationale.** This is the first application of [D-144][d-144]'s four-class
5133	convention on its semantic axis: both names sat in the right class —
5134	bare-noun declarations the author defines and the framework calls — but were
5135	content-named where the spec's own `exports` precedent is consequence-named,
5136	naming the role the declaration plays rather than the material it returns. The
5137	side-detection prose improves in the same stroke: "`claims` defined ⇒
5138	enumerated write side, claims staked". The client difference (trim's `reads`
5139	service, a device read binding inspection) is no obstacle — [D-130][d-130] made the
5140	client an internal framework fact, never user-facing API.
5141	
5142	Annotation (2026-10-02): [D-301][d-301] settles the semantic axis the other way: a
5143	declaration names what it returns, not the role it plays. The renames stand
5144	on this entry's other grounds, [§11.3][s11-3]'s claim vocabulary and [§14.7][s14-7]'s shared
5145	`reads`, and each new name also names the set it returns.
5146	
5147	**Rejected.**
5148	- *Keeping `selectors(b)`:* defensible status quo — content-accurate and
5149	  unambiguous — but it names the material rather than the role, and forgoes the
5150	  [§14.7][s14-7] unification a shared `reads` buys.
5151	- *`taps(b)`:* spoken for by [§14.10][s14-10]'s linearization vocabulary — the
5152	  `x`/`u`/`y` tap sets — so importing it here would manufacture the very
5153	  polysemy this rename retires.
5154	- *`gather(b)`:* names the compiled artifact, not the declaration — the gather
5155	  is what the framework builds from the declared read set, and a declaration
5156	  named after its downstream product is the class error one level over.
5157	- *Direction words such as `outputs(b)`:* invite the writer/reader direction
5158	  confusion `selectors` was originally chosen to avoid — a device's "output" is
5159	  the sim's input.
5160	- *Renaming the selector vocabulary itself instead of the method:* it names the
5161	  `get_*` values, which is precisely what it is good at — the ambiguity was
5162	  only ever in the method name.
