2562	### D-085 — Unpack `Tuple`/`NamedTuple` fields as container children
2563	
2564	**Status.** ratified
2565	
2566	**Position.** Container children: `Tuple`/`NamedTuple` fields with
2567	all-component elements unpack as children (`"field/1"`/`"field/key"` path
2568	segments, declaration-order layout); containers are transparent grouping — no
2569	contract, no `connections`, no rate scope.
2570	
2571	**Spec.** [§8.5][s8-5], [§8.6][s8-6], [§8.7][s8-7], [§8.8][s8-8], [§14.9][s14-9]
2572	
2573	**Rationale.** Elements are the *parent's* children, wired/exported/rated by
2574	element name; parametric rosters (`Formation{NT <: NamedTuple}`) compose per
2575	instantiation via [§8.8][s8-8] generic holding, wires generated by comprehension
2576	(arity-via-computed-contracts at structure scale; [§14.9][s14-9] swarms and
2577	`at`-mounting consume directly); mixed component/non-component elements = build
2578	error, zero-component containers = inert data, no container nesting (first
2579	cut), empty containers legal, `rates` keys = element names with bare-field-name
2580	uniform-`K` sugar.
2581	
2582	**Rejected.**
2583	- *One-field-per-child + programmatic struct generation:* roster frozen in
2584	  source text; fights the no-macros stance.
2585	- *Homogeneous-`NTuple`-only:* the per-element complexity objection was hollow
2586	  — element types are static either way; named and mixed rosters are the [§14.9][s14-9]
2587	  case, user call.
2588	- *`Vector{C}` children:* runtime-sized, mutable — breaks the immutable tree
2589	  and the type-stable layout.
2590	- *Containers as anonymous assemblies:* a second composition boundary without a
2591	  type — wiring must stay with the parent.
