Redstone.jl

Redstone is a Julia framework for modeling and simulating hierarchical hybrid systems. A model is written as a tree of components that exchange values through directed ports, mixing continuous dynamics, multi-rate periodic discrete dynamics and events. Its home domain is aircraft guidance, navigation and control, but the formalism is domain-neutral.

Features

  • Continuous dynamics on a fixed step, with events located by root-finding or checked at step boundaries.
  • Multi-rate periodic discrete dynamics, held zero-order between ticks.
  • An execution order derived from declared feedthrough. Algebraic loops are build errors that name the cycle.
  • Zero-allocation stepping and type stability, both asserted by the test suite.
  • A runtime data plane for devices, GUIs and scripts, with staged writes, snapshot reads and no shared mutable model.
  • Bit-identical replay from a recorded input trace.
  • Initialization, trim and linearization, with exact automatic-differentiation Jacobians.
  • Real-time pacing against the wall clock, with pause and resume.
  • A standard block library: integrators and limited integrators, lags, linear systems in s and z, relays, delays, noise, and PID and LQR tracking controllers with anti-windup, hold and bumpless engage.
  • Structured diagnostics from a closed set of kinds, reported where the mistake was made.

The browser inspector and cockpit are designed but not yet built.

Status

Redstone is under active development and is not yet registered. Its API may change without notice. The module exports nothing yet, so every name is imported explicitly. Redstone requires Julia 1.13 or later.

Quick start

A continuous plant under a discrete PI controller running at 50 Hz:

using Redstone
import Redstone: AbstractComponent, x_init, s_init, u_types, y_types,
    y_state, y_direct, x_deriv, s_update,
    Absolute, Hz, Simulation, init!, run!, set, port, state, build
import Redstone.Blocks: Group

struct Plant <: AbstractComponent
    ω::Float64
    ζ::Float64
end

x_init(::Plant) = (q = 0.0, v = 0.0)
u_types(::Plant) = (u = Float64,)
y_types(::Plant) = (y = Float64, power = Float64)

y_state(::Plant, (; x)) = (y = x.q,)                 # stage 1: state only
y_direct(::Plant, (; x, u)) = (power = u.u * x.v,)   # stage 2: reads inputs
x_deriv(p::Plant, (; x, u)) =
    (q = x.v, v = -p.ω^2 * x.q - 2p.ζ * p.ω * x.v + u.u)

struct PI <: AbstractComponent
    k_p::Float64
    k_i::Float64
end

s_init(::PI) = (integral = 0.0,)
u_types(::PI) = (ref = Float64, y = Float64)
y_types(::PI) = (u = Float64,)

y_direct(c::PI, (; s, u)) = (u = c.k_p * (u.ref - u.y) + s.integral,)
s_update(c::PI, (; s, u, Δt)) = (integral = s.integral + c.k_i * Δt * (u.ref - u.y),)

loop(feedback) = Group((plant = Plant(2.0, 0.3), ctl = PI(3.0, 2.0));
    local_wires = ("ctl/u" => "plant/u", "plant/$feedback" => "ctl/y"),
    input_wires = "ref" => "ctl/ref",
    output_wires = "plant/y" => "y",
    sample_times = (ctl = Absolute(Hz(50)),))

sim = Simulation(loop("y"); h = 1//1000)
init!(sim, set(u = (ref = 1.0,)))
run!(sim; t_end = 10.0)

port(sim, "plant", :y)    # 0.9654…
state(sim, "plant")       # (q = 0.9654…, v = 0.0120…)

The import list is part of authoring. A component extends the framework's functions rather than calling them, and Julia allows that only for names imported explicitly.

Each component has two output stages. y_state sees only the state, and y_direct also sees the inputs. The build derives the execution order from that split. Feeding back the plant's stage-2 power port instead of y closes an algebraic loop, and the build refuses the tree:

julia> build(loop("power"))
ERROR: DiagnosticError: 1 diagnostics
  AlgebraicCycle: algebraic loop among `plant`, `ctl`: plant/power → ctl/y, ctl/u → plant/u — real: a loop survives the trace (`ctl` structurally, the rest globally); break it with a state, a stage-1 (`y_state`) port, or a `UnitDelay`, which moves the signal onto the discrete tier and inserts a Δt_base-scale zero-order hold (§5.5)

Documentation

Redstone has no user manual yet. Its design is written down in full:

  • design/spec.md is the normative specification.
  • design/decisions.md records every design decision and the alternatives it rejected.
  • design/companions/ holds worked explainers, among them library_inventory.md, the block library and its admission rule.
  • design/pending.md is the work order toward the first release.
