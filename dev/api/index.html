Authoring

Redstone.AbstractComponent — Type
AbstractComponent

The abstract type every component subtypes, primitive and assembly alike.

A component, the unit of modeling, is a plain struct, MyComp <: AbstractComponent, whose fields are inert parameters or child components. Its class (a component's primitive-vs-assembly status) is read off which declarations its type defines. Defining local_wires makes it an assembly (a component of pure composition), whose component-typed fields are its children. Defining any leaf declaration, such as x_init, u_types or the stage y_direct, makes it a primitive. There is no separate assembly type, so a field typed by a domain supertype accepts a primitive and an assembly alike.

A component's module extends the declarations it defines, importing each one by name, as in import Redstone: x_init, y_types, y_direct, and defines them at module top level.

The build refuses a type that defines neither family as ClassUnreadable, and one that defines both as ClassMixed. A module that binds a declaration name to a function of its own, the sign of a missing import, is refused as DeclarationShadowed.

Redstone.x_init — Function
x_init(c) -> NamedTuple

Return the component's initial continuous state, as a NamedTuple of named values.

A continuous leaf declares its state by value, written with Float64 values, as in x_init(::Engine) = (ω = 0.0,). The state's type is derived from the value, and its real values follow the scalar of each activation (the build's typed products at a given scalar type). Each field is one Float64 or one static array of Float64. Integers, Bools and enums belong in m_init.

Every leaf defines exactly one of x_init and s_init, and the one it defines makes it continuous or discrete. A stateless continuous leaf declares x_init(::C) = (;). A non-empty state needs an x_deriv method.

The build refuses a value that is not a NamedTuple as StoreNotNamedTuple, and a field outside the state vocabulary as IllegalStateLeaf. A non-empty state with no x_deriv is refused as StoreWithoutUpdate, a leaf that defines neither x_init nor s_init as TierUnreadable, and one that defines both as DeclarationOnWrongTier.

Redstone.m_init — Function
m_init(c) -> NamedTuple

Return the component's initial modes, as a NamedTuple of named values.

A continuous leaf declares its modes by value, as in m_init(::Engine) = (phase = off,). Every field is isbits or a Symbol, as for s_init. Event handlers write the modes, and nothing else may. A leaf may declare modes that no event of its own changes.

Modes are continuous-only, because the event system is continuous-side only. The build refuses a non-empty m_init on a discrete leaf as DeclarationOnWrongTier, a value that is not a NamedTuple as StoreNotNamedTuple, and a field that is neither isbits nor a Symbol as IllegalStoreField.

Redstone.ws_init — Function
ws_init(c, ::Type{T})

Allocate the component's workspace (component-declared mutable scratch) at the scalar type T.

The framework calls the allocator and hands its result to the component's functions as the ws field of their bundle (the NamedTuple of views a component function receives). Declaring is allocating, so ws_init is the one declaration that takes the scalar. Sizes come from the instance and eltypes from T, as in ws_init(c::KF, ::Type{T}) where {T} = (P = Matrix{T}(undef, c.n, c.n),).

The allocator takes T on both tiers (the continuous and the discrete side of the hybrid formalism). A continuous allocator is called at the scalar of each activation (the build's typed products at a given scalar type), and a discrete one always receives Float64. The contents at each call are unspecified, and the framework never reads or writes them. A component that needs no scratch defines no method.

Redstone.u_types — Function
u_types(c) -> NamedTuple

Return the types the component accepts on its inputs, a NamedTuple of input name => type.

The entries are written at Float64 and take the component alone on both tiers (the continuous and the discrete side of the hybrid formalism), as in u_types(::Engine) = (throttle = Float64, starter = Bool). On a continuous leaf every Float64 position follows the scalar of each activation (the build's typed products at a given scalar type), and an entry wrapped in Pinned does not. On a discrete leaf every entry stays as written. The default declares no inputs.

An entry states what the component allows to arrive. An unwrapped Float64 leaf tolerates both the activation scalar and a frozen Float64, and a Pinned entry demands an arriving value that never carries partials.

The build refuses a wire whose producer type does not fit the entry as WireTypeMismatch, and a producer that follows the scalar at a Pinned entry as WalkingFaceAtFrozenEntry. A Pinned marker below the top of an entry is refused as IllegalPortType, and a Pinned entry on a discrete leaf as DeclarationOnWrongTier.

Redstone.y_types — Function
y_types(c) -> NamedTuple

Return the types of the component's output ports, a NamedTuple of port name => type.

The entries are written at Float64 and take the component alone on both tiers (the continuous and the discrete side of the hybrid formalism), as in y_types(::Engine) = (M_shaft = Float64, P = Float64). The declaration is read literally. On a continuous leaf, a port's value at each activation (the build's typed products at a given scalar type) has the declared type with every Float64 position, alone or as a type parameter, at that activation's scalar. An entry wrapped in Pinned keeps its type at every activation. On a discrete leaf every entry stays as written.

One declaration covers both output stages, y_state and y_direct, and no port names its stage. The build finds which stage produces each port by its probe (the build's checking evaluation of a user function), and checks each return against this declaration.

A leaf with an empty state and no y_types is refused as StatelessWithoutOutputs. A declared port no stage returns is refused as DeclaredNotProduced, a returned name the declaration lacks as UndeclaredReturnField, and a port both stages return as ProducedByTwoStages.

Redstone.state_events — Function
state_events(c) -> NamedTuple

Return the component's events, a NamedTuple of name => StateEvent, in priority order.

A continuous leaf declares its events as named entries, state_events(::Engine) = (start = StateEvent(start_guard, start_handler),). Order is semantics. At a boundary a component fires at most one event per round, the first eligible one in declaration order, and the rounds repeat until none fires, so the guards are decided again after each firing. Nothing here is inferred, and the default declares no events.

Events are continuous-only, like m_init, because the event system is continuous-side only. The build refuses a non-empty state_events on a discrete leaf as DeclarationOnWrongTier, and an entry that is not a StateEvent as EventHalfMissing.

Redstone.y_state — Function
y_state(c, bundle) -> NamedTuple

Return the component's stage-1 outputs, the ports it computes from its state alone.

y_state is the first of a leaf's two output stages, defined by a method for the component's type, as in y_state(::Engine, (; x)) = (; ω = x.ω). Its bundle (the NamedTuple of views a component function receives) carries no inputs, so a stage-1 port never depends instantly on an input and breaks would-be feedback loops. A leaf sits on one tier, the continuous or the discrete side of the hybrid formalism. On the continuous tier the bundle may carry x, m, t and ws, and on the discrete tier s, t, Δt and ws, each only if the component has it.

The stage returns a NamedTuple of port values at their y_types types. y_direct receives the return as y_x, or y_s on the discrete tier, so an intermediate both stages need is computed once. A component exposes a state or mode field by returning it here. A discrete leaf's stages run only at its ticks (the instants at which a discrete component runs), and its ports hold their values in between.

The stage is optional, and a component with no stage-1 ports defines no method. The build refuses a read outside the bundle as BundleFieldError, a return of bare (;) as DeadStage, and a returned name y_types lacks as UndeclaredReturnField.

source
Redstone.y_direct — Function
y_direct(c, bundle) -> NamedTuple

Return the component's stage-2 outputs, the ports that need its inputs.

y_direct is the second of a leaf's two output stages, as in y_direct(eng::Engine, (; x, m, u)) = (; M_shaft = ..., P = ...). Beside the state, its bundle (the NamedTuple of views a component function receives) carries the inputs u and the return of y_state as y_x. A leaf sits on one tier, the continuous or the discrete side of the hybrid formalism, and a discrete leaf receives that return as y_s. On the continuous tier the bundle may carry x, m, u, y_x, t and ws, and on the discrete tier s, u, y_s, t, Δt and ws, each only if the component has it.

Every stage-2 port is taken to depend on every wired input. The stage returns a NamedTuple of port values at their y_types types, and the two stages together produce each declared port exactly once.

The stage is optional. The build refuses a read outside the bundle as BundleFieldError, a port that both stages return as ProducedByTwoStages, and a returned name y_types lacks as UndeclaredReturnField.

Redstone.x_deriv — Function
x_deriv(c, bundle) -> NamedTuple

Return the time derivative of the component's continuous state.

x_deriv is the continuous leaf's update law, its flow (the continuous derivative function), as in x_deriv(eng::Engine, (; x, y, u)) = (ω = (y.M_shaft - u.M_load) / eng.J,). It runs after the output stages, when every port is fresh, so it reads the component's own outputs y instead of computing them again. Its bundle (the NamedTuple of views a component function receives) may carry x, m, y, u, t and ws, each only if the component has it.

The return has exactly the fields of x_init, each at the state's type. A continuous leaf with a non-empty state must define it.

The build refuses a non-empty x_init with no x_deriv as StoreWithoutUpdate, a return whose fields or types differ from the state's as ConformanceFailure, and a read outside the bundle as BundleFieldError. A leaf that also defines s_update or s_init is refused as DeclarationOnWrongTier.

Redstone.StateEvent — Type
StateEvent(guard, handler) -> StateEvent

One event of a state_events declaration: a guard and its handler, and nothing else.

The guard (the declared function defining an event's predicate) and the handler both take the component and its bundle. The bundle (the NamedTuple of views a component function receives) may carry x, m, y, u, t and ws. There is no detection keyword, because the guard's return type declares the policy. A Bool guard is boundary-detected, checked for a false-to-true edge at step boundaries only. A guard returning a Float64 is localized: the event holds where the value is ≥ 0, and root-finding brackets the instant it crosses.

The handler returns a NamedTuple of the stores it writes, such as (; m = (; phase = running)). A present x replaces the whole continuous state, and a present m merges into the modes.

The build refuses a guard that returns neither form as GuardForm, a missing guard or handler method as EventHalfMissing, and a handler key that names no store of the component as HandlerReturnKey.

Redstone.x_projection — Function
x_projection(c, x) -> NamedTuple

Return the continuous state x projected back onto the component's manifold.

x_projection takes the state alone, not a bundle: one store in, the same store out, which is why it alone stays positional. An attitude model might declare x_projection(c::Attitude, x) = (; q = normalize(x.q)). It runs after each integration step and after each event handler fires. Its return replaces the whole continuous state, so it carries every state field at the state's type.

The method is optional and continuous-only. The build refuses it on a discrete leaf, or on one with an empty state, as DeclarationOnWrongTier, and a return whose fields or types differ from the state's as ConformanceFailure.

Redstone.s_init — Function
s_init(c) -> NamedTuple

Return the component's initial discrete state, as a NamedTuple of named values.

A discrete leaf declares its state by value, as in s_init(::Counter) = (n = 0,). Every field is isbits or a Symbol, and the field types stay as written at every activation (the build's typed products at a given scalar type). Text and bulk data belong on the component instance.

Every leaf defines exactly one of x_init and s_init, and the one it defines makes it continuous or discrete. A stateless discrete leaf declares s_init(::C) = (;), and holds its outputs between its ticks (the instants at which a discrete component runs). A non-empty state needs an s_update method.

The build refuses a value that is not a NamedTuple as StoreNotNamedTuple, and a field that is neither isbits nor a Symbol as IllegalStoreField. A non-empty state with no s_update is refused as StoreWithoutUpdate, and a leaf that also defines x_init as DeclarationOnWrongTier.

Redstone.s_update — Function
s_update(c, bundle) -> NamedTuple

Return the component's discrete state after one tick.

s_update is the discrete leaf's update law, as in s_update(::Counter, (; s)) = (n = s.n + 1,). It runs at each of the component's ticks (the instants at which a discrete component runs), once the boundary's outputs and events have settled. Its bundle (the NamedTuple of views a component function receives) may carry s, y, u, t, Δt and ws, each only if the component has it, and Δt is the component's own tick period.

The return replaces the whole state, so it has exactly the type of the value s_init returns. A discrete leaf with a non-empty state must define it.

The build refuses a non-empty s_init with no s_update as StoreWithoutUpdate, a return of another type as ConformanceFailure, and a read outside the bundle as BundleFieldError. A leaf that also defines x_deriv or x_init is refused as DeclarationOnWrongTier.

Redstone.local_wires — Function
local_wires(c)

Return the assembly's internal wires, an ordered collection of "child/face" => "child/face" pairs.

Every pair runs from a child's output face to a child's input face, and its arrow reads along the signal flow. A face is the name a port wears on its component's boundary. Both endpoints are relative to the declaring assembly (a component of pure composition), each one an immediate child and one of its faces, so "aircraft/2/face" names a container element's face in one level.

Defining local_wires is what makes a component an assembly, so an assembly defines it even with no wires, as local_wires(::A) = (). The assembly's own boundary is declared by input_wires and output_wires.

The build refuses an endpoint whose port has the wrong direction as FaceDirectionConflict, an input fed twice as TwoProducers, and a component that defines local_wires beside any leaf declaration as ClassMixed.

Redstone.input_wires — Function
input_wires(c)

Return the assembly's inward boundary, an ordered collection of input name => internal endpoint path pairs.

Each input name is a face (the name a port wears on its component's boundary), and it routes inward to an input of an immediate child, as in "throttle" => "engine/throttle". A face that feeds several children takes a tuple of paths, "trn" => ("left/trn", "right/trn"), fanning out through the boundary. The default declares no input face. At the root of a build these faces are the root inputs (the root component's own input faces, produced by no component).

Face names contain no /, and are unique across input_wires and output_wires together. The build refuses a face name holding / as FaceNameIllegal, a name declared twice as FaceNameCollision, an endpoint that resolves to an output as FaceDirectionConflict, and an empty tuple of paths as UnknownPort.

source
Redstone.output_wires — Function
output_wires(c)

Return the assembly's outward boundary, an ordered collection of internal source path => output name pairs.

Each output name is a face (the name a port wears on its component's boundary), and it exposes an output of an immediate child, as in "aircraft/pose" => "view_pose". The source comes first, so the pairs read along the signal flow, like every pair of local_wires and input_wires. The default declares no output face.

The build refuses a face name holding / as FaceNameIllegal, a name declared twice across the two boundary declarations as FaceNameCollision, and a source that resolves to an input as FaceDirectionConflict.

Redstone.sample_times — Function
sample_times(c) -> NamedTuple

Return the assembly's sample times, a NamedTuple of immediate child name => Relative or Absolute.

A rate scope (an assembly's sample_times declaration against the enclosing scope) schedules the assembly's discrete children and sub-assemblies, as in sample_times(::A) = (nav = Relative(5), gnss = Absolute(Hz(10))). The declaration is optional, and so is every key: an unlisted discrete child defaults to Relative(1), so only multiplied, phased or anchored children appear. A container field's bare name keys one entry for all its elements.

The rates belong to the assembly type, as design ratios or a modeled instrument's own rate. A rate that is a deployment preference is exposed as a constructor parameter, and read off the instance here.

The build refuses a value that is not such a NamedTuple, a bare number in place of a wrapper, a key that names no immediate child, and a key on a continuous child, each as RatesViolation.

Redstone.transparent_container — Function
transparent_container(c) -> Union{Symbol,Nothing}

Return the name of the one container field whose children go by bare key, or nothing.

A container field is a Tuple or NamedTuple field whose elements are all components. Its elements are children of the component, named "field/key" or "field/1". Returning that field's Symbol names them "key" and "1" instead, everywhere a child name appears: wiring endpoints, sample_times keys, read paths, at prefixes and diagnostics. Naming is the only thing it changes, and the container still has no wires, faces or rate of its own.

The declaration is optional, and a component may name at most one field. The default, nothing, keeps every container's key segment. The build refuses a name that matches no container field as TransparentContainerUnknown, and a bare key that collides with a sibling child's name as ChildNameCollision.

Redstone.Relative — Type
Relative(K, φ) -> Relative
Relative(K::Integer) -> Relative

A sample time in ticks of the enclosing scope: every K-th tick, starting from the φ-th.

A sample_times entry Relative(K, φ) runs its child at every K-th tick (an instant at which a discrete component runs) of the enclosing rate scope, starting from its φ-th, and φ defaults to 0. A rate scope is an assembly's sample_times declaration against the enclosing scope. Scope ticks are the unit system, so relative entries compose affinely down the tree. Under a scope that ticks every D_s base ticks at phase Φ_s, the child ticks every K·D_s base ticks at phase Φ_s + φ·D_s. A base tick is the period Δt_base that every discrete period is a multiple of.

K = 1 admits no stagger. Two same-rate siblings are staggered one level down instead: declare their scope at twice their rate, and give them Relative(2, 0) and Relative(2, 1).

The constructor checks nothing. The build refuses K < 1, or a φ outside 0 ≤ φ < K, as RatesViolation.

source
Redstone.Absolute — Type
Absolute(q::Period, τ::Union{Integer,Rational{<:Integer}} = 0) -> Absolute

A sample time in exact rational seconds, with ticks at t = τ + k·T.

q is a period T, built with Period or Hz, and τ is the offset in seconds. The entry is an anchor (the exact period and offset an Absolute entry establishes). It severs its child from the enclosing scope's grid, so the child may tick faster than its scope. The child's ticks (the instants at which a discrete component runs) are counted in base ticks only once a Deployment fixes Δt_base. Δt_base is the base tick period every discrete period is a multiple of. Anchor periods and nonzero offsets constrain that grid together, and an offset of T/1000 can cost a grid 1000 times finer.

A float offset is refused as ArgumentInvalid, and so is a bare number in place of a Period: write Absolute(Hz(50), 1//500). The build refuses a period that is not positive, or an offset outside 0 ≤ τ < T, as RatesViolation.

Redstone.Period — Type
Period(T::Union{Integer,Rational{<:Integer}}) -> Period

A time period T, in exact rational seconds.

A Period is what Absolute and the Δt_base keyword of Deployment take. Period(1//50) and Hz(50) are the same value, a spelling choice: both are normalized to the exact rational period at construction. See Hz for the frequency spelling.

A float is refused as ArgumentInvalid, because the base grid is derived by GCD arithmetic, which is ill-defined over floats. Write Period(1//50), not Period(0.02).

source
Redstone.Hz — Function
Hz(frequency::Union{Integer,Rational{<:Integer}}) -> Period

Return the Period of a frequency, 1 // frequency seconds.

Hz(50) and Period(1//50) are the same value, and either may be given to Absolute or as the Δt_base keyword of Deployment. A float is refused as ArgumentInvalid, because the grid arithmetic is exact: write Hz(1//2) for 0.5 Hz, not Hz(0.5).

Redstone.stop_reason — Function
stop_reason(c) -> String

Return the reason the component's stop requests report, "" by default.

A stop request (a port that ends the run when it reads STOP_REQUESTED) is an output port of type StopFlag. The build reads stop_reason for every component that publishes such a port, and all of the component's requests share the reason. It is instance data, never a port value. A run that a request ends carries the reason on its ModelRequestedStop source.

Redstone.Pinned — Type
Pinned{P}

The marker that keeps one u_types or y_types entry at type P, whatever scalar the model runs at.

Pinned wraps a whole entry of u_types or y_types, as in Pinned{Float64} or Pinned{SVector{3,Float64}}, to say the leaf never follows the scalar of an activation (the build's typed products at a given scalar type). On an output the port's value is a P at every activation. On an input the entry demands an arriving value that never carries partials. The build strips the marker at Float64, so no value, layout or message carries the wrapper itself. It is a type-level marker, never instantiated.

A marker below the top of an entry, in a type parameter, is refused as IllegalPortType on both tiers (the continuous and the discrete side of the hybrid formalism). The marker is continuous-only: a discrete leaf's entries never follow the scalar, so a Pinned entry there is refused as DeclarationOnWrongTier.

Redstone.build — Function
build(root::AbstractComponent; activations::Tuple = ()) -> Build

Check a component tree and return its Build, with no grid chosen yet.

build runs the structure step, the nominal evaluation and the eager activations. The structure step flattens the tree, classifies its components and type-checks the wires into the Structure. The nominal evaluation (the build's one probing pass at Float64) probes every user function. It returns the Outputs, the Events and the nominal activation (the build's typed products at one scalar type). Nothing here needs h, N_base or Δt_base, which are the Deployment's.

Keywords

  • activations: the scalar types whose activations are made at once instead of at first request, such as (Float64, ProbeDual) in a test that checks the tree types at a dual number. See ProbeDual.

A tree the build rejects is refused as one DiagnosticError that carries every diagnostic the failing step found, and the warnings raised so far. A build that succeeds logs each warning once and keeps it, read with warnings.

See also descriptor, Model, Simulation.

Redstone.Build — Type
Build

The artifact build produces, the checked contract of a component tree before any grid is fixed.

A build holds the Structure, the Outputs and the Events, which the build's steps produce, then its activations (the build's typed products at one scalar type) and the warnings its construction raised, read with warnings. The first three do not depend on the scalar type, by construction. The nominal Float64 activation is made by the build, and any other is derived at first request and kept.

Everything in a build is settled before Δt_base exists: h, N_base and Δt_base are the Deployment's. A build is immutable apart from its activation cache, whose insertion is safe across tasks. One build backs any number of deployments and Models, concurrently, each materializing its own stores and buffers.

See also descriptor.

source
Redstone.Structure — Type
Structure

The structure step's product, the declared facts the component tree alone fixes, held as rows.

Structure is read off a Build as build.structure. Nothing in it depends on a scalar type. Its rows hold the component instances, and paths, names and rationals the REPL prints as they are.

  • components: one entry per leaf, in the order the build walks the tree.
  • anchors: one entry per Absolute declaration, the exact (T, τ) pair (period and offset in rational seconds) with the declaring scope and key.
  • scopes: one entry per assembly a sample_times key names, with its path, the key and the timing the build derived for it.
  • root_inputs and root_types: the root inputs (the root component's own input faces), in order, with the types the wire check fixed for them.
  • levels: one entry per assembly, in pre-order with the root first, holding its children and the wires it declares. A leaf root's entry has no children and no wires.

No table of resolved faces is stored. A face at any level is resolved over the levels wires when it is read.

source
Redstone.Outputs — Type
Outputs

The output port names each component's stages produce, and the order the components run in.

Outputs is a product of the nominal evaluation (the build's one probing pass at Float64), read off a Build as build.outputs. Its components field holds one entry per component, in the order the build walks the tree. Each entry carries the component's path, the ports y_state returns as stage1, in the return's order, and the declared remainder, in y_types order, as stage2. Their concatenation is the order of the component's products. The order field is the execution order (the order the stage functions run in) over the indices of components.

Outputs holds names only and does not depend on the scalar type, so a reader that wants a list of port names takes it from here rather than from an activation (the build's typed products at one scalar type). The feedthrough graph the order was computed over is not carried. Where it is shown, it is derived from the Structure's connections and the producers' stage2.

source
Redstone.Events — Type
Events

The detection policy of each component's events, and the field names of its event bundle.

Events is the other product of the nominal evaluation (the build's one probing pass at Float64), read off a Build as build.events. Its components field holds one entry per component, in the order the build walks the tree, so one index addresses it and Outputs alike. Each entry carries the component's path, its policies and its bundle.

  • policies: a NamedTuple from each event name, in declaration order, to the detection policy its guard's return form fixes, :boundary for a Bool guard checked at step boundaries only, or :localized for a guard returning a Float64, whose crossing is located in time.
  • bundle: the field names of the event bundle (the NamedTuple of views a guard or handler receives), () where the component declares no events.

Like Outputs, Events holds names only and does not depend on the scalar type.

Redstone.descriptor — Function
descriptor(build::Build) -> NamedTuple
descriptor(deployment::Deployment) -> NamedTuple

Return the artifact's descriptor, its rendering to data under the published format.

The descriptor (a serialized projection of the artifact under a published format) is an envelope with the fields format_version, redstone_version and kind, and the body under the key the kind names, build or deployment. A deployment's body embeds the build's whole. The artifact, a Build or a Deployment, is an immutable pure function of its inputs.

The value is a tree of NamedTuples and vectors, ready for any JSON encoder, and conforms to the schema the package ships as schema/descriptor.json. Encoding it is the caller's job.

See also Build, Deployment.

Redstone.ProbeDual — Type
ProbeDual

The framework's public canonical probe scalar, the concrete ForwardDiff.Dual{ProbeTag,Float64,1}.

ProbeDual is the one concrete Dual a test lists to check that a component tree types at a dual number, as in build(root; activations = (Float64, ProbeDual)). An activation (the build's typed products at one scalar type) is keyed by a concrete scalar, and the bare Dual, a UnionAll, can key none.

Its width is one because the check pins genericity, the tree's types following the scalar, and not any particular Jacobian. linearize sets its own width with its width keyword.

Redstone.resolve — Function
resolve(assembly, path::AbstractString) -> AbstractComponent

Return the immediate child of an assembly that path names.

resolve walks the assembly's declared fields along the / segments of path. The path names one child: its field's name, plus a key segment where the child is an element of a container field (a Tuple or NamedTuple field whose elements are all components), as in "units/1" or "units/left". The elements of a container declared name-transparent with transparent_container go by their bare keys, "1" or "left". Declaration bodies such as input_wires call it to compute entries from a child's contract.

Resolution goes one level only. A path that reaches past the child it names is refused as PathResolution, naming that child. An empty path, and a segment that names no child, are refused as PathResolution too.

Redstone.input_faces — Function
input_faces(comp) -> Vector{String}

Return the component's input face names, in declaration order.

A face is the name a port wears on its component's boundary. For a leaf the input faces are the keys of its u_types, which do not depend on the scalar type. For an assembly they are the face names its input_wires declares. Declaration order is kept, so printouts are deterministic and diagnostics stable.

Called from a declaration body during a build, input_faces reuses the build's evaluation of the child's declaration rather than evaluating it again. Either way the vector returned is a fresh one, the caller's to change.

See output_faces for the output side, and input_passthrough for the helper built on it.

Redstone.output_faces — Function
output_faces(comp) -> Vector{String}

Return the component's output face names, in declaration order.

A face is the name a port wears on its component's boundary. For a leaf the output faces are the keys of its y_types. For an assembly they are the face names its output_wires declares.

Called from a declaration body during a build, output_faces reuses the build's evaluation of the child's declaration rather than evaluating it again. Either way the vector returned is a fresh one, the caller's to change.

See input_faces, the mirror on the input side, and output_passthrough for the helper built on it.

Redstone.frame! — Function
frame!(model::Model, k::Int, hooks::FrameHooks = NoHooks()) -> Bool

Advance the model through frame k, from tₖ₋₁ to tₖ, and settle its frame-top boundary.

A frame (one iteration of the loop) starts with frame_top!(hooks), before the model touches any state, and then integrates. A localized event (one whose crossing instant is root-found inside the frame) adds a boundary at its time t*. The clock is then set to the frame top tₖ, computed from k and never accumulated, and the boundary there runs. When k is a multiple of N_base it is a base tick (an instant of the base grid). The discrete components due there, those whose sample time admits that tick, run their stages and updates in it. Any other k runs an off-tick boundary, with no discrete update. settled!(hooks) follows every boundary, each t*'s and the frame top's.

frame! returns whether settled! asked to abandon the frame. A true at a t* boundary leaves the rest of the frame unrun, with the clock at t* where the stores are, and the frame top never reached. See FrameHooks for the hooks, and NoHooks for a model stepped on its own.

A model claimed by a Simulation is refused as ArgumentInvalid. A throw inside the frame writes the status :inconsistent and arrives as a StepError with host :loop. Its pointer is k - 1, the boundary the frame started from. An InterruptException is never wrapped and writes no status.

Redstone.attach! — Function
attach!(sim::Simulation, dev::AbstractDevice, new_binding::AbstractBinding;
        should_abort::Bool = false) -> DeviceHandle

Add a device to the roster under a binding, and return the device's handle.

The roster (the list of attached device entries) is fixed for each run. attach! is therefore a stopped-sim operation (legal only on a simulation that is not running). It registers the device and spawns nothing: the device's task starts with the next run!.

The binding (the value passed at attach! that makes a device framework-legible) declares the device's sides. On the input side, the device's claim (the set of faces a device may write) is what the binding's claims returns, or, for a binding declaring is_greedy, every face no other device has claimed at this moment. Attach a greedy device last: a second one gets an empty claim, which is legal and warns EmptyGreedyClaim, into the device's diagnostic cell (the per-writer cell holding runtime diagnostics) and once as a logged warning. The faces stage!(sim, …) may write shrink to what is left unclaimed. On the output side, the binding's reads resolve against the build here, so a binding that no longer matches its model fails at attach rather than sending wrong values. An output-only binding claims nothing, and stage!(sim, …) keeps every face.

The returned DeviceHandle is named by the device's stable id, and carries what the device may do: read snapshots (the immutable per-boundary publications), stage writes and control the run. The device's loop receives the same handle.

Keywords

  • should_abort: whether the device's departure also stops the run. Set, the device's loop returning, a crash or a failed init! requests a stop. Clear, the run continues without the device's task, and its claim holds until the run ends.

attach! is refused as ServiceLifecycle while running, and once errored, since no run follows an errored simulation. A binding or device that breaks its contract is refused as BindingContractMismatch or DeviceContractMismatch, and a device instance already on the roster as AlreadyAttached; to rebind one, detach! it first. A claimed name that is not a root input face is refused as AttachUnknownFace. A face another device already claims is refused as ClaimConflict, and reads that do not resolve as ReadResolution.

A device type defines loop(dev::MyDevice, handle). Each run calls it once, on a task of its own, after every device's init! has returned, and passes it the DeviceHandle that attach! returned. The body is the device's own code: it reads, waits and stages through the handle, and loops while running returns true, checking it between blocking calls. A throw is reported as DeviceCrash into the device's diagnostic cell (the per-writer cell holding runtime diagnostics), and the run goes on without the device's task.   • Control: running says whether the run goes on, and stop! requests a stop.

The handle also carries the attachment's binding (the value passed at attach! that makes a device framework-legible), read back with binding. The loop's map_input and map_output calls take it from the handle, so the device need not carry its configuration. The reads a GUI device uses to show its widgets, port_views, pending and peek, take the handle too.

A handle outlives its roster entry (the device's record in the list of attached devices) as an object only. After detach!, the two write primitives, stage! and report!, are refused as DeviceContractMismatch instead of landing in a cell nothing reads. The reads stay legal.

The handle's type carries the binding's type and the type of its compiled reads, so binding(handle) and gather(handle, snapshot) are type-stable inside a device's loop and allocate nothing.

init!(sim::Simulation, condition = set(); t0::Real = 0.0, trace = true,
      log = true, log_every = 1, log_max = 65536) -> Nothing

Initialize the simulation from a condition on the declared defaults, and run boundary zero at t0.

init! resets the state to the declared defaults, applies the condition's overrides, sets the clock to t0 and runs boundary zero (the initialization boundary, an ordinary one with an empty integrate). The condition (the datum that says "set this build to this state") is a sparse overlay addressed by component path, built with set and its combinators. Root inputs (the root component's own input faces) have no declared default, so the condition must give every one of them a value.

Boundary zero derives every output's value from the state. Every event starts as not holding, so an event that already holds in the initialized state fires at t0. Calling init! again resets the state and the events from scratch, and such an event fires again at the new t0.

init! opens a fresh run, with a new log and a new trace rather than cleared ones, and the input mode (where the frame's inputs come from) back at :live. It clears the stop word (the control plane's stop command). It also drops every batch (a staged set of face ⇒ value writes) still waiting, so nothing staged earlier reaches the new trajectory. Stage after init! and before run!, and the batch waits for the first frame (one iteration of the loop). The diagnostic cells (the per-writer cells holding runtime diagnostics) are not cleared. A rejection recorded while stopped therefore still reaches the status of the next run's first snapshot (the immutable per-boundary publication). The trace header (the trace's fixed preamble, a checkpoint) is the checkpoint taken after boundary zero publishes, and replay! restores it rather than running boundary zero again.

init! is the only call that runs boundary zero, and a completed boundary zero is what run! and step! need. restore! and replay! are the alternatives, which start from a checkpoint in the condition's place. To start again from a saved state, call checkpoint, then restore!, then run!.

Keywords

  • t0: the start time, any real, held as a Float64 origin. Time is a keyword, never a condition entry.
  • trace: record the input trace (the primary record of a session) of this run. Turn it off only to save memory in a long session, since an untraced session can never be reproduced.
  • log: keep the snapshot log (the retained sequence of published snapshots) of this run.
  • log_every: keep every log_every-th published boundary in the log, an integer of at least 1.
  • log_max: the most snapshots the log keeps between its first and latest, an integer of at least 1, or Inf for no bound. The first and the latest snapshots are always kept, and at the bound the log thins its middle by doubling its stride.

The four recording keywords never change the trajectory: two runs that differ only in them produce bitwise-identical trajectories. Each configures the run this call opens, and the next run follows whatever its own call declares. overlay!, restore! and replay! take the same four.

init! is refused as ServiceLifecycle while the simulation is running, and once it is errored. A recording keyword out of range is refused as ArgumentInvalid, a condition that does not resolve against the build as ConditionResolution, and a root input the condition leaves without a value as UninitializedInputs. Every refusal comes before any write, so a refused init! leaves the simulation exactly as it was. A throw inside boundary zero arrives as a StepError with pointer 0 and leaves the simulation built, with no trace, and init!, restore! and replay! legal again. init! under the same condition reproduces it.

Redstone.trim! — Function
trim!(model::Model{Float64}, problem::TrimProblem; baseline, t0::Real = 0.0,
      backend = LevenbergMarquardt()) -> TrimReport

Solve a trim problem on the model, and commit the solution through init!.

trim! searches the TrimProblem's decisions for a point where every residual sits within its tolerance. Every evaluation runs on scratch stores (working storage the call creates and discards), so the search never writes the model. Setup layers the problem's condition (the datum that says "set this build to this state") at the guess over the baseline, as override(baseline, problem.condition(guess)). It then runs one establishment round: the sweep of boundary zero (the initialization boundary), with every discrete output stage run and no projection, events or discrete update. Each iteration then writes the decisions, sweeps the continuous chain and reads the residuals, with no boundaries and no events. The discrete tier (the discrete side of the hybrid model) does not run during the search, so its outputs hold the values the establishment round gave them. The Jacobian is exact, carried by dual numbers through the same evaluation.

The verdict is trim!'s own. After the backend returns, trim! evaluates once more at the returned point and tests each residual against its tolerance, in the residuals' own units. That test sets the report's converged, whatever status the backend gave. A solve that does not converge commits nothing and leaves the model as it was, its status included: a :built model stays :built. Non-convergence is reported in the TrimReport, never thrown.

A converged solve commits through the model's own init!, as init!(model, override(baseline, problem.condition(solution)); t0). Boundary zero can then move the committed stores off the solved point, through x_projection or an event whose guard already holds. trim! surfaces both: the events fired, in the report's fired_events with a TrimCommitEvents warning, and the residuals read again at the committed state, with a TrimCommitResiduals warning when they leave their tolerances. The checks are read from the same boundary-zero sweep, and TrimCommitChecks warns of those outside their tolerances.

A problem with no decisions, guess = (;), is legal. It skips the backend, its establishment round is its one evaluation, and the ordinary tolerance test decides. It answers whether the operating point is already an equilibrium, and commits as usual when it is.

Keywords

  • baseline: the baseline (a full-coverage condition, layered under tweaks) the problem's condition is layered over, at setup and at the commit. Required. Together with the problem's condition at the guess, it must give every root input (the root component's own input faces) a value.
  • t0: the start time of the committing boundary zero, any real, held as a Float64 origin.
  • backend: the solver, any value with a solve method. LevenbergMarquardt is the default.

The problem is checked in two collecting passes, each refused as TrimProblemInvalid. The first runs before any evaluation, with the read set's own ReadResolution failures beside the problem's faults. The second checks the residual and check returns at the guess evaluation, and again at the first seeded one. A root input the baseline and the guess's condition leave without a value is refused as UninitializedInputs. A model a Simulation has claimed is refused as ArgumentInvalid, before any check. So is a second argument that is not a TrimProblem, and a model at a scalar type other than Float64.

Redstone.TrimProblem — Type

            checks = _no_checks, check_tolerances = (;)) -> TrimProblem

The value a trim solves: the decisions to vary, the condition they set, and the equations to satisfy.

A trim problem is a condition (the datum that says "set this build to this state") given implicitly, as a function of decisions. trim! searches the decisions for the point where every residual sits within its tolerance, and commits the condition at that point. The first seven keywords are required, and the two check keywords default to no checks.

Keywords

  • guess, lower, upper: the decisions' starting point and bounds, as NamedTuples of Float64 with one set of names. The names pair them, and setup reorders the bounds to guess's order, so their spelling order does not matter.
  • condition: a function of the decisions d that returns a condition. Everything fixed for the problem is closed over, and d is the one argument.
  • reads: the read set (a Reads value, built by reads) gathered after each evaluation.
  • residuals: residuals(reads::NamedTuple, d::NamedTuple) -> NamedTuple, the residual system as named equations, never a scalar cost.
  • tolerances: a NamedTuple of Float64 with the residuals' names, each finite and positive. The problem carries its own convergence test, so the test moves with it when at scopes it.

Redstone.LevenbergMarquardt — Type
LevenbergMarquardt(; maxiter::Integer = 100,
                   λ₀::Real = 1e-3) -> LevenbergMarquardt

The default trim backend, a dense Levenberg–Marquardt solver that stops on the problem's own tolerances.

Each iteration solves (JᵀJ + λ·diag(JᵀJ)) δ = −Jᵀr for a step, and projects the step onto the bounds. A step is accepted when it lowers the normalized residual norm ‖r ./ tol‖. λ then shrinks by a factor of 10, and a rejected step grows it by 10. The descent test and the stopping rule both measure the residuals in their tolerances' units, the test trim! applies to the result.

The solver stops with status :converged when every residual is within its tolerance, all(abs.(r) .≤ tol). It stops with :maxiter after maxiter iterations. It stops with :stalled when no step lowers the residual norm: the step is not finite, it falls below the rounding scale of the decisions it would move, or every trial is rejected until the damping passes its ceiling.

Keywords

  • maxiter: the most iterations the solver runs.
  • λ₀: the starting damping factor.

See also solve.

Redstone.run! — Function
run!(sim::Simulation; pace = Inf, margin = 0.002, t_end = Inf,
     ignore_stop_requests = ()) -> Nothing

Advance the simulation frame by frame until a termination source ends the run.

A frame (one iteration of the loop: drain, integrate, boundary sequence, publication) applies the staged inputs at its top, integrates one step and settles every boundary it reaches. It publishes a snapshot (the immutable per-boundary publication) at each. The run ends when one of three sources fires. The first is t_end, when the frame that reaches it completes. The second is an honoured stop request holding in a published snapshot. A stop request is a StopFlag output port reading STOP_REQUESTED. The third is a stop through the control plane (the separate few-word atomic surface carrying pause, pace and stop), seen at a frame top. A frame top is the start of a frame. A stop request ends the run at the boundary that published it, an event boundary inside a frame included, and that snapshot is the final one. t_end ends the run at the first frame top at or past it, in whole frames from t₀. run! blocks its caller until the run ends.

Each rostered device is initialized and given a task of its own as the run starts, and shut down as it ends; the loop itself runs on the calling task. The run leaves the simulation stopped, with the record that says why readable through termination. In the :replay input mode (where the frame's inputs come from) the recording also bounds the run. A run that consumes the last record halts there initialized, with no termination record, and the mode turns :live. A failure inside the loop leaves it errored instead, the cause kept on the record. With no device rostered, run! then rethrows the failure; with one or more, it logs the failure and returns. Ctrl-C is a stop, never a failure: caught at a frame top or during a pause, it ends the run stopped with ControlRequestedStop(:interrupt).

Keywords

  • pace: simulated seconds per wall-clock second, a positive real. Inf, the default, never waits, and 1 is real time. pace! retunes it during the run.
  • margin: the seconds of each pacing wait spent spinning rather than sleeping, a non-negative real. margin! retunes it during the run.

It is allowed, and the loop reports UnboundedRun into its own diagnostic cell (the per-writer cell holding runtime diagnostics). The pace inserts wall time between frames and nothing else, so a paced run is bit-identical to an unpaced one. Redstone.step! — Function
step!(sim::Simulation; frames = nothing, t_plus = nothing, t_end = Inf,
      ignore_stop_requests = ()) -> Int

Advance the simulation by whole frames, synchronously, and return the number of frames advanced.

Each frame (one iteration of the loop) runs exactly as under run!, so a stepped simulation is bit-identical to the same frames under run!. The staged inputs still apply at each frame's top, so stage!(sim, …), then step!, then latest(sim) drives a model and checks its response one step at a time. step! never waits for the pacer, and the pacer record of its snapshots (the immutable per-boundary publications) reads Inf and zeros. It spawns no device task and initializes no device, but a batch (a staged set of face ⇒ value writes) staged into a rostered device's cell while stopped is applied as usual.

Between calls the simulation stays initialized, so attach! is legal there and run! may follow, continuing from the current boundary. A termination source that fires inside the call ends the run there: the simulation is left stopped with its termination record (the value naming how the run ended) set, and step! returns the frames advanced before the stop. A return below the frames requested is how a caller detects the stop without reading the clock. A failure inside the loop leaves the simulation errored, and step! always rethrows it.

In the :replay input mode (where the frame's inputs come from) the frames take their inputs from the recording, which bounds the advance. A step! past its end advances only to the last recorded frame, returns fewer frames than asked and turns the mode :live.

Keywords

  • frames: the number of frames to advance, an integer of at least 1. One frame when neither frames nor t_plus is given.
  • t_plus: the duration to advance, a positive finite real, in whole frames until the boundary time first covers it. Mutually exclusive with frames.
  • t_end, ignore_stop_requests: this advance's stop policy, as for run!, with the same defaults, validated per call.

step! needs an initialized simulation, as run! does: it is refused as MissingInit when built, and as ServiceLifecycle otherwise. Both frames and t_plus, or either out of range, is refused as ArgumentInvalid, and an ignored path that names no requester as StopRequestInvalid.

Redstone.replay! — Function
replay!(sim::Simulation, trc::Trace; to_boundary = nothing, to_time = nothing,
        pace = Inf, margin = 0.002, t_end = Inf, ignore_stop_requests = (),
        trace = true, log = true, log_every = 1, log_max = 65536,
        restore = true) -> Nothing

Re-drive a recorded session through the ordinary loop, with the recording supplying every frame's inputs.

Replay (the ordinary loop with one substitution: the drain reads the trace) differs from run! in two places only. It starts from the trace's header (the checkpoint the recording opened from) as restore! does. No boundary zero (the initialization boundary) runs, so nothing is applied twice. At each frame top (the start of a frame), it applies the recording's batches for that frame verbatim. A batch is a staged set of face ⇒ value writes. It drops whatever sits in the live staging cells (the per-device holding places where pending writes wait) with a ReplayDiscardedStaging warning. The replayed trajectory is bit-identical to the recorded one.

The replay halts at the recording's end, or earlier at to_boundary or to_time, always at a frame top. A replay that halts there ends initialized, never stopped, so it can be inspected, stepped with step! or continued with run!. A termination source that fires first ends it stopped, like any run. A failure inside the loop ends it errored, rethrown when no device is rostered and logged when one is, as under run!.

The recording stays attached after the call, in the :replay input mode (where the frame's inputs come from). A later step! or run! goes on consuming the records from the halt, and no advance runs past the recording's last frame. The mode returns to :live, the recording detaching with it, when an advance halts at that last frame; live! detaches it earlier.

Replay records a new trace that inherits the old header, so its replayed prefix is bit-identical to the recording and a live continuation appends to it. Rostered devices initialize, run and read snapshots as in any run, but their writes are dropped.

restore = false attaches the recording to the simulation as it stands, and restores nothing. The simulation must be initialized, at the recording's t₀, and at a frame from the header's up to one short of the recording's last; the records apply from the frame after its own. This form replays a modified model initialized under the authored condition, or seeks: restore! a checkpoint the recording passed through, then replay from the next frame. The new trace's header is then this simulation's own checkpoint, the state the replay starts from.

Keywords

  • to_boundary: halt after the frame that publishes boundary k, a whole number from the frame the replay starts at up to the recording's length. An event boundary localized inside a frame is reproduced, but a replay cannot halt there.
  • to_time: the same halt by time, at the last frame top at or before it, k = ⌊(to_time − t₀)/h⌋ against the header's t₀. A time between two frame tops halts at the earlier one. Mutually exclusive with to_boundary.
  • pace, margin: as for run!. A paced replay is bit-identical to an unpaced one.
  • t_end, ignore_stop_requests: this replay's stop policy, as for run!, with the same defaults. When neither binds, the recording bounds the replay. A live run that ignored some requests replays under the same ignore_stop_requests.
  • trace, log, log_every, log_max: as for init!, with the same defaults. Under trace = false nothing is re-recorded.
  • restore: false to attach the recording without restoring its header.

replay! is refused as ServiceLifecycle while running, and once errored, as init! is. Under restore = false it needs an initialized simulation, and is refused as MissingInit when built and as ServiceLifecycle otherwise. A keyword out of range, or both to_boundary and to_time, is refused as ArgumentInvalid, and an ignored path that names no requester as StopRequestInvalid. A header that does not match this simulation is refused as CheckpointMismatch or ReplaySchemaMismatch before any record is read, and the records' own mismatches, such as ReplayUnknownFace, are then collected into one throw. Every refusal comes before any write.

Redstone.Blocks.Group — Type
Group

The library's on-the-fly assembly, whose values are the ad-hoc topologies.

A Group is an assembly (a component of pure composition) that holds its children and its declarations as field values. The elements of its children field, a NamedTuple of components, are its children. Its local_wires, input_wires, output_wires and sample_times are ordinary functions of the instance, which return its fields.

Redstone.Blocks.Step — Type
Step(; t_step, before = 0.0, after = 1.0, localized::Bool = true) -> Step

The block that publishes one value before a given time and another from then on.

out publishes before until t_step and after from then on. The block is a mode-only leaf with no inputs. The mode fired picks the value, and one state event, fire, sets it once t reaches t_step. out is pinned at V: it keeps that type whatever scalar the model runs at. The value depends on neither state nor an input that follows the scalar, so it carries zero partials under every activation (the build's typed products at a given scalar type), as a Constant's does.

A prior is each event's sample of its guard at the previous boundary. Boundary zero (the initialization boundary at t₀) sets every prior to not-holding. A t_step at or before t₀ therefore fires there, and out publishes after from the start.

Keywords

  • t_step: the time of the step, any time.
  • before: the value before t_step.
  • after: the value from t_step on. before and after are promoted to one V, Float64 or a static array of Float64, and taken by float, so integer values qualify.

Redstone.Blocks.LimitedIntegrator — Type
LimitedIntegrator(; lower, upper, x0 = zero(lower), localized::Bool = true) -> LimitedIntegrator

The block that publishes the time integral of its input, held between two limits.

The block holds one continuous state q, with q̇ = in while free and q̇ = 0 while saturated, and out publishes q from stage 1 (y_state, the output stage that reads no input). It is not a clamp. The mode saturation is read by the derivative, and four state events move it. It is a signed Int8 code, the sign of the limit in force: -1 at lower, 0 free and +1 at upper. hit_upper and hit_lower fire when q reaches a limit, and their handlers write q to the limit exactly and saturate. leave_upper and leave_lower fire when in turns strictly back into the range, and free it. An input of exactly zero at a limit keeps the mode saturated. The hit events are localized, their crossing instant found by root-finding.

A second output, also saturation, publishes the code from stage 1, so it has no feedthrough (instantaneous dependence of an output on an input). It serves an anti-windup consumer, such as a controller that gates its integrator on the code. The code flips only when an event fires, and so only on a declared boundary.

localized picks the detection policy of the leave events. Localized, the guards (the functions that define the events' predicates) are sign forms gated by the mode, and the departure ends the step at the input's zero crossing. Boundary-detected, checked at boundaries only, the guards are the Bool predicates. The departure then fires at the end of the step in which in first pointed back into the range, so q is held on the limit for the rest of that step. It carries an offset of at most a h² / 2 from then on, a the input's slope at its zero crossing. What the cheap form buys is that a departure costs no root-finding and splits no step, where a localized one pays about 22 trial sweeps (passes through the execution order) and a boundary. The policy is the type parameter L rather than a field because the build reads it off the guard's return type.

Over a static vector, the limits and the codes are componentwise, and saturation publishes a static vector of Int8. The block declares N copies of the scalar events, one per component, named hit_upper_1 to hit_upper_N, then hit_lower_i, leave_upper_i and leave_lower_i. Each guard reads its one component and each handler writes it.

A prior is each event's sample of its guard at the previous boundary. Boundary zero (the initialization boundary at t₀) sets every prior to not-holding. An x0 outside the limits is therefore clamped there, and the initial mode agrees with the initial input.

Keywords

  • lower: the lower limit, below upper, componentwise over a vector.
  • upper: the upper limit.
  • x0: the initial value of q. x0, lower and upper are promoted to one V, which is Float64 or a static array of Float64, and taken by float, so integer values qualify.
  • localized: true for localized leave events, false for boundary-detected ones.

See also DiscreteLimitedIntegrator, Integrator.

Redstone.Blocks.TransferFunction — Type
TransferFunction(; num, den, u0 = 0.0) -> TransferFunction

The block that runs a single-input, single-output linear system given by its transfer function in s.

The transfer function is

G(s) = (num[1] sᵐ + … + num[end]) / (den[1] sⁿ + … + den[end])

with in and out both Float64. The block keeps the coefficients and holds their realization in controllable canonical form, a StateSpace whose stages it shares.

There is no x0, because a realization's state means nothing to a user who knows only G(s). The block starts at rest, or, with u0 given, at the steady state for the constant input u0, where out is G(0) u0.

The type parameter FT is the feedthrough class of LinearBlock, and the degrees pick it. A numerator of lower degree than the denominator publishes out from stage 1 (y_state, the output stage that reads no input). The block then breaks an algebraic loop (a cycle of instantaneous dependences). One of equal degree publishes it from stage 2 (y_direct, the output stage that reads the inputs).

Keywords

  • num: the numerator's coefficients, highest power first, as a tuple or a vector of reals.
  • den: the denominator's coefficients, highest power first, likewise.
  • u0: the constant input whose steady state the block starts at, 0.0 for rest.

Four spellings are refused as an ArgumentError: a denominator of fewer than two coefficients, whose order of zero makes a gain; a numerator longer than the denominator, which is improper; a leading denominator coefficient of zero; and a nonzero u0 over a denominator whose constant coefficient is zero, a pole at the origin, which has no steady state.

Redstone.Blocks.PID — Type
PID(; Kp, Ki = 0.0, Kd = 0.0, τd = 0.1, Tt = Inf, u_min = -Inf, u_max = Inf,

The block that runs a PID controller with anti-windup.

The inputs are r and y, with the error e = r - y. The two outputs come from stage 2 (y_direct, the output stage that reads the inputs): u_raw = Kp (b r - y) + q - Kd (w - yf) / τd, and u, its clamp to [u_min, u_max]. The block holds two continuous states: q, the integral term, and yf, the weighted measurement w = y - c r through a lag, ẏf = (w - yf) / τd. One law moves the integral term,

q̇ = Ki ε + (ref - u_raw) / Tt

and two independent type parameters, each adding inputs, fill its slots ε and ref over the error e by the table of ControllerBlock.

hold = true, the parameter Hold, adds two inputs. saturation is an Int8 code such as a LimitedIntegrator publishes for the path downstream, and gates the error by sign: gate(e) = saturation == sign(e) ? 0 : e. engaged is a Bool that reads true while the block is in command; not engaged, the error is gated to zero whatever the code. Without tracking, a block not engaged freezes: q holds while the own clamp is free and back-calculates against it otherwise.

tracking = true, the parameter Track, adds the input v, a value the path delivered or the selected command, as the correction's reference in place of the own u. With the hold, v is the reference only while the block is limited or not engaged, and u while it is free, so a block not in command follows the selected command at rate 1/Tt and engages without a bump. It chases a moving v with lag Tt, so a block out of command wants a short Tt. The default Tt = Inf follows nothing, so tracking = true with a Tt given as a value and infinite in any channel is refused as an ArgumentError: tracking needs Tt spelled, or given as AsPort(), which leaves it to the model to keep finite.

q holds the integral term in output units, with Ki inside the integral, so a change in Ki alters only future accumulation. The setpoint weights b and c multiply r alone, b in the proportional term and c in the derivative's weighted measurement, and the integral's error stays e. Their defaults, b = 1 and c = 0, put the derivative on the measurement, so a step in r makes no kick; c = 1 puts it on the error. The defaults make the plain spelling a P controller: Ki = Kd = 0, Tt = Inf, which switches the correction off, and infinite limits.

V is Float64 or a static array of Float64. Over a static vector the law is componentwise: the parameters, r, y, v, the outputs and the states are each a V, and saturation and engaged are static vectors of Int8 and of Bool. The nine keywords given as values broadcast to one V, whose shape is the sum of their zeros, so a scalar pairs with a vector and integer values qualify. A vector PID with uniform gains spells at least one keyword as a vector, Kp = @SVector fill(2.0, 3).

Any of the nine parameters may be an input port in place of a field, spelled Kp = AsPort() with AsPort. The port is named for the parameter and typed V, and it takes no part in the shape, so when every value-carrying keyword is a port, V is Float64. Under a Dual activation (the build's typed products at a given scalar type), a scheduled parameter carries partials, so a linearization sees the coupling through the schedule. A model that wants it frozen at its plain Float64 value routes the port through Freeze.

u is a stage-2 output, so every input makes a feedthrough edge (an instantaneous dependence of an output on an input), whether y_direct reads it or not. A tracking input wired from a memoryless clamp of the block's own u is refused as an AlgebraicCycle classified artificial (acyclic between ports but cyclic between stages). That is why the limits live inside the block. v serves a value published from state, such as a stateful actuator's position. A scheduled parameter computed memorylessly from u closes a cycle too, artificial for Ki and Tt, which only the derivative reads, and real for the others. One read from a state is fine.

  • Ki: the integral gain, inside the integral.
  • Kd: the derivative gain.
  • τd: the time constant of the derivative's lag, positive.
  • Tt: the time constant of the correction, Inf to switch it off.
  • u_min: the lower limit of u.

The discrete block that runs a PID controller with anti-windup.

The block takes the parameters, defaults, ports and law of PID to the discrete tier (the discrete side of the hybrid formalism). Two store fields stand in for its continuous states: q, the integral term, and yf, the weighted measurement w = y - c r through a lag. A third, saturated, holds its code.
