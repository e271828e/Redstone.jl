API

The entry points, grouped as the specification's Appendix B groups them.

Authoring

Redstone.AbstractComponent — Type
AbstractComponent

The abstract type every component subtypes, primitive and assembly alike.

A component is a plain struct, MyComp <: AbstractComponent, whose fields are inert parameters or child components. There is no separate assembly type, so a field typed by a domain supertype accepts a primitive and an assembly alike.

The declarations a type defines fix its class. Defining local_wires makes it an assembly, whose component-typed fields are its children. Defining any primitive declaration, such as x_init, u_types or the stage y_direct, makes it a primitive.

A component's module extends the declarations it defines, importing each one by name, as in import Redstone: x_init, y_types, y_direct, and defines them at module top level.

The build refuses a type that defines neither family as ClassUnreadable, and one that defines both as ClassMixed. A module that binds a declaration name to a function of its own, the sign of a missing import, is refused as DeclarationShadowed.

Redstone.x_init — Function
x_init(c) -> NamedTuple, value or nothing

Return the component's initial continuous state, as a NamedTuple of named values or as one bare value.

A continuous primitive declares its state by value, written with Float64 values, as in x_init(::Engine) = (ω = 0.0,). The value fixes the state's type, and its real values follow the scalar of each activation. Each field, or the bare value, is one Float64 or one SArray of Float64. Integers, Bools and enums belong in m_init.

A state of one leaf may be that leaf alone, as in x_init(c::Integrator) = c.x0. This bare state's one field is named x, and the component's functions then receive it bare.

Every primitive defines exactly one of x_init and s_init, and the one it defines makes it continuous or discrete. A stateless continuous primitive declares x_init(::C) = nothing. A non-empty state needs an x_deriv method.

The build refuses (;) as EmptyStore, and a field or bare value outside the state vocabulary as IllegalStateLeaf. A non-empty state with no x_deriv is refused as StoreWithoutUpdate, a primitive that defines neither x_init nor s_init as TierUnreadable, and one that defines both as DeclarationOnWrongTier.

Redstone.m_init — Function
m_init(c) -> NamedTuple, value or nothing

Return the component's initial modes, as a NamedTuple of named values or as one bare value.

A continuous primitive declares its modes by value, as in m_init(::Engine) = (phase = off,), or m_init(::Switch) = false for the bare form, whose one field is named m. Every field, or the bare value, is isbits or a Symbol, as for s_init.

Event handlers write the modes, and nothing else may. A primitive may declare modes that no event of its own changes. A primitive without modes defines no method.

Modes are continuous-only, because the event system is continuous-side only. The build refuses modes declared on a discrete primitive as DeclarationOnWrongTier, (;) as EmptyStore, and a field or bare value that is neither isbits nor a Symbol as IllegalStoreField.

Redstone.ws_init — Function
ws_init(c, ::Type{T}) -> Any

Allocate the component's workspace at the scalar type T.

The framework calls the allocator and hands its result to the component's functions as the ws field of their bundle. The declaration allocates, so ws_init is the one declaration that takes the scalar. Sizes come from the instance and eltypes from T, as in ws_init(c::KF, ::Type{T}) where {T} = (P = Matrix{T}(undef, c.n, c.n),).

The allocator takes T on both tiers. The framework calls a continuous allocator at the scalar of each activation, and a discrete one always receives Float64. The contents at each call are unspecified, and the framework never reads or writes them. A component that needs no scratch defines no method.

Redstone.u_types — Function
u_types(c) -> NamedTuple or Type

Return the types the component accepts on its inputs, as a NamedTuple by input name or as one type.

The entries are written at Float64. The declaration takes the component alone on both tiers, as in u_types(::Engine) = (throttle = Float64, starter = Bool). The default declares no inputs.

A component with one input may declare it bare, as in u_types(::Integrator{V}) where {V} = V. The input's face is then u, a wire names it "integrator/u", and the bundle's u is its value.

On a continuous primitive every Float64 position follows the scalar of each activation, and an entry wrapped in Pinned does not. On a discrete primitive every entry stays as written.

An entry states what the component allows to arrive. An unwrapped Float64 leaf tolerates both the activation scalar and a frozen Float64, and a Pinned entry demands an arriving value that never carries partials.

The build refuses a wire whose producer type does not fit the entry as WireTypeMismatch, and a producer that follows the scalar at a Pinned entry as WalkingFaceAtFrozenEntry. A Pinned marker below the top of an entry is refused as IllegalPortType, and a Pinned entry on a discrete primitive as DeclarationOnWrongTier. An empty entry name is refused as FaceNameIllegal.

Redstone.y_types — Function
y_types(c) -> NamedTuple or Type

Return the types of the component's output ports, as a NamedTuple by port name or as one type.

The entries are written at Float64. The declaration takes the component alone on both tiers, as in y_types(::Engine) = (M_shaft = Float64, P = Float64).

The build reads the declaration literally. On a continuous primitive, a port's value at each activation has the declared type with every Float64 position, alone or as a type parameter, at that activation's scalar. An entry wrapped in Pinned keeps its type at every activation. On a discrete primitive every entry stays as written.

A component with one output may declare it bare, as in y_types(::Integrator{V}) where {V} = V. The port's face is then y. A wire names it "integrator/y", a reader by that name or by the path alone, and the stage that produces it returns its value rather than a NamedTuple.

One declaration covers both output stages, y_state and y_direct, and no port names its stage. The build finds which stage produces each port by its probe, and checks each return against this declaration.

A primitive with an empty state and no y_types is refused as StatelessWithoutOutputs. A declared port no stage returns is refused as DeclaredNotProduced, a returned name the declaration lacks as UndeclaredReturnField, and a port both stages return as ProducedByTwoStages. An empty entry name is refused as FaceNameIllegal.

Redstone.state_events — Function
state_events(c) -> NamedTuple

Return the component's events, a NamedTuple of name => StateEvent, in priority order.

A continuous primitive declares its events as named entries, state_events(::Engine) = (start = StateEvent(start_guard, start_handler),). Nothing here is inferred, and the default declares no events.

The order of the entries decides which event fires. At a boundary a component fires at most one event per round, the first eligible one in declaration order. The rounds repeat until none fires, so the guards are decided again after each firing.

Events are continuous-only, like m_init, because the event system is continuous-side only. The build refuses a non-empty state_events on a discrete primitive as DeclarationOnWrongTier, and an entry that is not a StateEvent as EventHalfMissing.

Redstone.y_state — Function
y_state(c, bundle) -> NamedTuple or value

Return the component's stage-1 outputs.

y_state is the first of a primitive's two output stages, defined by a method for the component's type, as in y_state(::Engine, (; x)) = (; ω = x.ω). Its bundle carries no inputs, so a stage-1 port never depends instantly on an input and breaks would-be feedback loops.

A primitive sits on one tier. On the continuous tier the bundle may carry x, m, t and ws, and on the discrete tier s, t, Δt and ws, each only if the component has it.

The stage returns a NamedTuple of port values at their y_types types, or the port's value itself under a bare y_types, the port y, as in y_state(::Integrator, (; x)) = x. y_direct receives the return as y_x, or y_s on the discrete tier, so an intermediate both stages need is computed once. A component exposes a state or mode field by returning it here.

A discrete primitive's stages run only at its ticks, and its ports hold their values in between.

The stage is optional, and a component with no stage-1 ports defines no method. The build refuses a read outside the bundle as BundleFieldError, a return of bare (;) as DeadStage, and a returned name y_types lacks as UndeclaredReturnField.

source
Redstone.y_direct — Function
y_direct(c, bundle) -> NamedTuple or value

Return the component's stage-2 outputs.

y_direct is the second of a primitive's two output stages, as in y_direct(eng::Engine, (; x, m, u)) = (; M_shaft = ..., P = ...). Beside the state, its bundle carries the inputs u and the return of y_state as y_x. Under a bare u_types the bundle's u is the value of the one input, the face u.

A primitive sits on one tier, and a discrete primitive receives that return as y_s. On the continuous tier the bundle may carry x, m, u, y_x, t and ws, and on the discrete tier s, u, y_s, t, Δt and ws, each only if the component has it.

The build takes every stage-2 port to depend on every wired input.

The stage returns a NamedTuple of port values at their y_types types, or the port's value itself under a bare y_types, the port y, as in y_direct(g::Gain, (; u)) = g.k * u. The two stages together produce each declared port exactly once.

The stage is optional. The build refuses a read outside the bundle as BundleFieldError, a port that both stages return as ProducedByTwoStages, and a returned name y_types lacks as UndeclaredReturnField.

source
Redstone.x_deriv — Function
x_deriv(c, bundle) -> NamedTuple or value

Return the time derivative of the component's continuous state.

x_deriv is the continuous primitive's update law, its flow, as in x_deriv(eng::Engine, (; x, y, u)) = (ω = (y.M_shaft - u.M_load) / eng.J,). It runs after the output stages, when every port is fresh, so it reads the component's own outputs y instead of computing them again. Its bundle may carry x, m, y, u, t and ws, each only if the component has it.

The return has exactly the fields of x_init, each at the state's type. For a bare state, the field x, it is one value at the state's type, as in x_deriv(::Integrator, (; u)) = u. There a bare u_types makes u the value of the one input, the face u. A continuous primitive with a non-empty state must define it.

The build refuses a non-empty x_init with no x_deriv as StoreWithoutUpdate, a return whose fields or types differ from the state's as ConformanceFailure, and a read outside the bundle as BundleFieldError. A primitive that also defines s_update or s_init is refused as DeclarationOnWrongTier.

Redstone.StateEvent — Type
StateEvent(guard, handler) -> StateEvent

One state event of a state_events declaration, a guard and its handler and nothing else.

The guard and the handler both take the component and its bundle. The bundle may carry x, m, y, u, t and ws.

There is no detection keyword, because the guard's return type declares the policy. A Bool guard is boundary-detected. A guard returning a Float64 is localized, and its event holds where the value is ≥ 0.

The handler returns a NamedTuple of the stores it writes, such as (; m = (; phase = running)). A present x replaces the whole continuous state, and a present m merges into the modes. Against a bare mode store, m is one value at its type and replaces it whole.

The build refuses a guard that returns neither form as GuardForm, a missing guard or handler method as EventHalfMissing, and a handler key that names no store of the component as HandlerReturnKey.

source
Redstone.x_projection — Function
x_projection(c, x) -> NamedTuple or value

Return the continuous state x projected back onto the component's manifold.

x_projection takes the state alone, not a bundle. One store goes in and the same store comes out, which is why it alone stays positional. An attitude model might declare x_projection(c::Attitude, x) = (; q = normalize(x.q)).

It runs after each integration step and after each event handler fires. Its return replaces the whole continuous state, so it carries every state field at the state's type, or for a bare state one value at its type.

The method is optional and continuous-only. The build refuses it on a discrete primitive, or on one with an empty state, as DeclarationOnWrongTier, and a return whose fields or types differ from the state's as ConformanceFailure.

source
Redstone.s_init — Function
s_init(c) -> NamedTuple, value or nothing

Return the component's initial discrete state, as a NamedTuple of named values or as one bare value.

A discrete primitive declares its state by value, as in s_init(::Counter) = (n = 0,), or s_init(::Counter) = 0 for the bare form, whose one field is named s. Every field, or the bare value, is isbits or a Symbol, and its type stays as written at every activation. Text and bulk data belong on the component instance.

Every primitive defines exactly one of x_init and s_init, and the one it defines makes it continuous or discrete. A stateless discrete primitive declares s_init(::C) = nothing, and holds its outputs between its ticks. A non-empty state needs an s_update method.

The build refuses (;) as EmptyStore, and a field or bare value that is neither isbits nor a Symbol as IllegalStoreField. A non-empty state with no s_update is refused as StoreWithoutUpdate, and a primitive that also defines x_init as DeclarationOnWrongTier.

source
Redstone.s_update — Function
s_update(c, bundle) -> NamedTuple or value

Return the component's discrete state after one tick.

s_update is the discrete primitive's update law, as in s_update(::Counter, (; s)) = (n = s.n + 1,). It runs at each of the component's ticks, once the boundary's outputs and events have settled. Its bundle may carry s, y, u, t, Δt and ws, each only if the component has it, and Δt is the component's own tick period.

The return replaces the whole state, so it has exactly the type of the value s_init returns, the one leaf itself for a bare state, the field s. A discrete primitive with a non-empty state must define it.

The build refuses a non-empty s_init with no s_update as StoreWithoutUpdate, a return of another type as ConformanceFailure, and a read outside the bundle as BundleFieldError. A primitive that also defines x_deriv or x_init is refused as DeclarationOnWrongTier.

Redstone.local_wires — Function
local_wires(c) -> collection of Pair

Return the assembly's internal wires, an ordered collection of "child/face" => "child/face" pairs.

Every pair runs from a child's output face to a child's input face, and its arrow reads along the signal flow. Both endpoints are relative to the declaring assembly, each one an immediate child and one of its faces, so "aircraft/2/face" names a container element's face in one level.

Defining local_wires is what makes a component an assembly, so an assembly defines it even with no wires, as local_wires(::A) = (). input_wires and output_wires declare the assembly's own boundary.

The build refuses an endpoint whose port has the wrong direction as FaceDirectionConflict, an input fed twice as TwoProducers, and a component that defines local_wires beside any primitive declaration as ClassMixed.

source
Redstone.input_wires — Function
input_wires(c) -> collection of Pair

Return the assembly's inward boundary, an ordered collection of input name => internal endpoint path pairs.

Each input name is a face, and it routes inward to an input of an immediate child, as in "throttle" => "engine/throttle". A face that feeds several children takes a tuple of paths, "trn" => ("left/trn", "right/trn"), fanning out through the boundary. The default declares no input face. At the root of a build these faces are the root inputs.

Face names contain no /, and are unique across input_wires and output_wires together. The build refuses a face name holding / as FaceNameIllegal, a name declared twice as FaceNameCollision, an endpoint that resolves to an output as FaceDirectionConflict, and an empty tuple of paths as UnknownPort.

source
Redstone.output_wires — Function
output_wires(c) -> collection of Pair

Return the assembly's outward boundary, an ordered collection of internal source path => output name pairs.

Each output name is a face, and it exposes an output of an immediate child, as in "aircraft/pose" => "view_pose". The source comes first, so the pairs read along the signal flow, like every pair of local_wires and input_wires. The default declares no output face.

The build refuses a face name holding / as FaceNameIllegal, a name declared twice across the two boundary declarations as FaceNameCollision, and a source that resolves to an input as FaceDirectionConflict.

Redstone.sample_times — Function
sample_times(c) -> NamedTuple

Return the assembly's sample times, a NamedTuple of immediate child name => Relative or Absolute.

A rate scope schedules the assembly's discrete children and sub-assemblies, as in sample_times(::A) = (nav = Relative(5), gnss = Absolute(Hz(10))). The declaration is optional, and so is every key. An unlisted discrete child defaults to Relative(1), so only multiplied, phased or anchored children appear. A container field's bare name keys one entry for all its elements.

The rates belong to the assembly type, as design ratios or a modeled instrument's own rate. Expose a rate that is a deployment preference as a constructor parameter, and read it off the instance here.

The build refuses a value that is not such a NamedTuple, a bare number in place of a wrapper, a key that names no immediate child, and a key on a continuous child, each as RatesViolation.

source
Redstone.transparent_container — Function
transparent_container(c) -> Union{Symbol,Nothing}

Return the name of the one container field whose children go by bare key, or nothing.

Its elements are children of the component, named "field/key" or "field/1". Returning that field's Symbol names them "key" and "1" instead, everywhere a child name appears, in wiring endpoints, sample_times keys, read paths, at prefixes and diagnostics. Naming is the only thing it changes, and the container still has no wires, faces or rate of its own.

The declaration is optional, and a component may name at most one field. The default, nothing, keeps every container's key segment.

The build refuses a name that matches no container field as TransparentContainerUnknown, and a bare key that collides with a sibling child's name as ChildNameCollision.

Redstone.Relative — Type
Relative(K, φ) -> Relative
Relative(K::Integer) -> Relative

A sample time in ticks of the enclosing scope, every K-th tick starting from the φ-th.

A sample_times entry Relative(K, φ) runs its child at every K-th tick of the enclosing rate scope, starting from its φ-th, and φ defaults to 0. Relative entries count scope ticks, so they compose affinely down the tree. Under a scope that ticks every D_s base ticks at phase Φ_s, the child ticks every K·D_s base ticks at phase Φ_s + φ·D_s.

K = 1 admits no stagger. Stagger two same-rate siblings one level down instead. Declare their scope at twice their rate, and give them Relative(2, 0) and Relative(2, 1).

The constructor checks nothing. The build refuses K < 1, or a φ outside 0 ≤ φ < K, as RatesViolation.

source
Redstone.Absolute — Type
Absolute(q::Period, τ::Union{Integer,Rational{<:Integer}} = 0) -> Absolute

A sample time in exact rational seconds, with ticks at t = τ + k·T.

q is a period T, built with Period or Hz, and τ is the offset in seconds.

The entry is an anchor. It severs its child from the enclosing scope's grid, so the child may tick faster than its scope. The child's ticks count in base ticks only once a Deployment fixes Δt_base. Anchor periods and nonzero offsets constrain that grid together, and an offset of T/1000 can cost a grid 1000 times finer.

A float offset is refused as ArgumentInvalid, and so is a bare number in place of a Period. Write Absolute(Hz(50), 1//500). The build refuses a period that is not positive, or an offset outside 0 ≤ τ < T, as RatesViolation.

source
Redstone.Period — Type
Period(T::Union{Integer,Rational{<:Integer}}) -> Period

A time period T, in exact rational seconds.

A Period is what Absolute and the Δt_base keyword of Deployment take. Period(1//50) and Hz(50) are the same value, so the spelling is a choice. Each normalizes to the exact rational period at construction. See Hz for the frequency spelling.

A float is refused as ArgumentInvalid. GCD arithmetic derives the base grid, and it is ill-defined over floats. Write Period(1//50), not Period(0.02).

source
Redstone.Hz — Function
Hz(frequency::Union{Integer,Rational{<:Integer}}) -> Period

Return the Period of a frequency, 1 // frequency seconds.

Hz(50) and Period(1//50) are the same value, and either may be given to Absolute or as the Δt_base keyword of Deployment.

A float is refused as ArgumentInvalid, because the grid arithmetic is exact. Write Hz(1//2) for 0.5 Hz, not Hz(0.5).

Redstone.stop_reason — Function
stop_reason(c) -> String

Return the reason the component's stop requests report, "" by default.

A component publishes a stop request as an output port of type StopFlag. The build reads stop_reason for every component that publishes such a port, and all of the component's requests share the reason. It is instance data, never a port value. A run that a request ends carries the reason on its ModelRequestedStop source.

Redstone.Pinned — Type
Pinned{P}

The marker that keeps one u_types or y_types entry at type P, whatever scalar the model runs at.

Pinned wraps a whole entry of u_types or y_types, as in Pinned{Float64} or Pinned{SVector{3,Float64}}, to say the entry never follows the scalar of an activation. On an output the port's value is a P at every activation. On an input the entry demands an arriving value that never carries partials.

The build strips the marker at Float64, so no value, layout or message carries the wrapper itself. It is a type-level marker, never instantiated.

A marker below the top of an entry, in a type parameter, is refused as IllegalPortType on both tiers. The marker is continuous-only. A discrete primitive's entries never follow the scalar, so a Pinned entry there is refused as DeclarationOnWrongTier.

Redstone.build — Function
build(root::AbstractComponent; activations::Tuple = ()) -> Build

Check a component tree and return its Build, with no grid chosen yet.

build runs the structure step, the nominal evaluation and the eager activations. The structure step flattens the tree, classifies its components and type-checks the wires into the Structure. The nominal evaluation probes every user function. It returns the Outputs, the Events and the nominal activation. Nothing here needs h, N_base or Δt_base, which are the Deployment's.

A tree the build rejects is refused as one DiagnosticError that carries every diagnostic the failing step found, and the warnings raised so far. A build that succeeds logs each warning once and keeps it, read with warnings.

Keywords

  • activations: the scalar types whose activations are made at once instead of at first request, such as (Float64, ProbeDual) in a test that checks the tree types at a dual number.

See also ProbeDual, descriptor, Model, Simulation.

Redstone.Build — Type
Build

The artifact build produces, the checked contract of a component tree before any grid is fixed.

A build holds these fields, which the build's steps produce. They do not depend on the scalar type, by construction.

  • structure: the Structure.
  • outputs: the Outputs.
  • events: the Events.

A build also holds its activations and the warnings its construction raised, read with warnings. build makes the nominal Float64 activation, and a build derives any other at first request and keeps it.

Everything in a build is settled before Δt_base exists. h, N_base and Δt_base are the Deployment's.

A build is immutable apart from its activation cache, whose insertion is safe across tasks. One build backs any number of deployments and Models, concurrently, each materializing its own stores and buffers.

See also descriptor.

source
Redstone.Structure — Type
Structure

The structure step's product, the declared facts the component tree alone fixes, held as rows.

Read it off a Build as build.structure. Nothing in it depends on a scalar type. Its rows hold the component instances, and paths, names and rationals the REPL prints as they are.

A Structure holds these fields.

  • components: one entry per primitive, in the order the build walks the tree.
  • anchors: one entry per Absolute declaration, the exact (T, τ) pair (period and offset in rational seconds) with the declaring scope and key.
  • scopes: one entry per assembly a sample_times key names, with its path, the key and the timing the build derived for it.
  • root_inputs: the root inputs, in order.
  • root_types: the types the wire check fixed for the root inputs, in order.
  • levels: one entry per assembly, in pre-order with the root first, holding its children and the wires it declares.

A primitive root's levels entry has no children and no wires.

A Structure stores no table of resolved faces. A face at any level resolves over the levels wires when it is read.

source
Redstone.Outputs — Type
Outputs

The output port names each component's stages produce, and the order the components run in.

Outputs is a product of the nominal evaluation. Read it off a Build as build.outputs. It holds names only and does not depend on the scalar type, so a reader that wants a list of port names takes it from here rather than from an activation.

An Outputs holds these fields.

  • components: one entry per component, in the order the build walks the tree.
  • order: the execution order over the indices of components.

Each entry holds these fields.

  • path: the component's path.
  • stage1: the ports y_state returns, in the return's order.
  • stage2: the declared remainder, in y_types order.

The concatenation of stage1 and stage2 is the order of the component's products.

source
Redstone.Events — Type
Events

The detection policy of each component's events, and the field names of its event bundle.

Events is the other product of the nominal evaluation. Read it off a Build as build.events. Like Outputs, it holds names only and does not depend on the scalar type.

An Events holds this field.

  • components: one entry per component, in the order the build walks the tree, so one index addresses it and Outputs alike.

Each entry holds these fields.

  • path: the component's path.
  • policies: a NamedTuple from each event name, in declaration order, to the detection policy its guard's return form fixes, :boundary for a Bool guard checked at step boundaries only, or :localized for a guard returning a Float64, whose crossing is located in time.
  • bundle: the field names of the event bundle, () where the component declares no events.

Redstone.descriptor — Function
descriptor(build::Build) -> NamedTuple
descriptor(deployment::Deployment) -> NamedTuple
descriptor(err::DiagnosticError) -> NamedTuple

Return the artifact's descriptor, its rendering to data.

The descriptor is an envelope with the fields format_version, redstone_version and kind, and the body under the key the kind names, build, deployment or failure. A deployment's body embeds the build's whole.

A failure's body holds the diagnostics and warnings of the carrier exception, DiagnosticError, each as its kind, severity, path and rendered message. It also holds the complete Structure when the build failed past the structure step, so a client can draw the model with the error marked on it.

The value is a tree of NamedTuples and vectors, ready for any JSON encoder, and conforms to the schema the package ships as src/descriptor.json. Encoding it is the caller's job.

See also Build, Deployment.

Redstone.ProbeDual — Type
ProbeDual

The framework's public canonical probe scalar, the concrete ForwardDiff.Dual{ProbeTag,Float64,1}.

ProbeDual is the one concrete Dual a test lists to check that a component tree types at a dual number, as in build(root; activations = (Float64, ProbeDual)). A concrete scalar keys an activation, and the bare Dual, a UnionAll, can key none.

Its width is one because the check tests that the tree's types follow the scalar, not any particular Jacobian. linearize sets its own width with its width keyword.

Redstone.resolve — Function
resolve(assembly, path::AbstractString) -> AbstractComponent

Return the immediate child of an assembly that path names.

resolve walks the assembly's declared fields along the / segments of path. The path names one child, by its field's name, plus a key segment where the child is an element of a container field, as in "units/1" or "units/left". The elements of a container declared name-transparent with transparent_container go by their bare keys, "1" or "left".

Declaration bodies such as input_wires call it to compute entries from a child's contract.

Resolution goes one level only. A path that reaches past the child it names is refused as PathResolution, naming that child. An empty path, and a segment that names no child, are refused as PathResolution too.

Redstone.input_faces — Function
input_faces(comp) -> Vector{String}

Return the component's input face names, in declaration order.

For a primitive the input faces are the keys of its u_types, which do not depend on the scalar type, and a bare u_types lists as its face u. For an assembly they are the face names its input_wires declares. The list keeps declaration order, so printouts are deterministic and diagnostics stable.

The vector returned is a fresh one, the caller's to change.

See output_faces for the output side, and input_passthrough for the helper built on it.

output_faces(comp) -> Vector{String}

Redstone.input_passthrough — Function
input_passthrough(assembly, child_path::AbstractString; sep::AbstractString = ".",
                  prefix::AbstractString = replace(child_path, "/" => sep),
                  except::Tuple = (), only::Tuple = (), select = nothing) -> Tuple

Return input wire entries that expose a child's input faces on the assembly's own boundary.

The helper serves the pass-through case, where an assembly hands up the inputs of a child it does not feed itself. The binding declares the device's sides. On the input side, the device's claim is what the binding's claims returns, or, for a binding declaring is_greedy, every face no other device has claimed at this moment. The faces stage!(sim, …) may write shrink to what is left unclaimed.

Initialize the simulation from a condition on the declared defaults, and run boundary zero at t0.

init! resets the state to the declared defaults, applies the condition's overrides, sets the clock to t0 and runs boundary zero. The condition is a sparse overlay addressed by component path, built with set and its combinators. Root inputs have no declared default, so the condition must give every one of them a value.

Boundary zero derives every output's value from the state. Every event starts as not holding, so an event that already holds in the initialized state fires at t0. Calling init! again resets the state and the events from scratch, and such an event fires again at the new t0.

init! opens a fresh run, with a new log and a new trace rather than cleared ones, and the input mode back at :live. It clears the stop word. The trace header is the checkpoint taken after boundary zero publishes, and replay! restores it rather than running boundary zero again.

init! also drops every batch still waiting, so nothing staged earlier reaches the new trajectory. Stage after init! and before run!, and the batch waits for the first frame.

The diagnostic cells are not cleared. A rejection recorded while stopped therefore still reaches the status of the next run's first snapshot.

init! is the only call that runs boundary zero, and a completed boundary zero is what run! and step! need. restore! and replay! are the alternatives, which start from a checkpoint in the condition's place. To start again from a saved state, call checkpoint, then restore!, then run!.

Time is a keyword, never a condition entry.

Turn trace off only to save memory in a long session, since an untraced session can never be reproduced.

The first and the latest snapshots are always kept, and at log_max the log thins its middle by doubling its stride.

The four recording keywords never change the trajectory. Two runs that differ only in them produce bitwise-identical trajectories. Each configures the run this call opens, and the next run follows whatever its own call declares. overlay!, restore! and replay! take the same four.

Every refusal comes before any write, so a refused init! leaves the simulation exactly as it was.

A throw inside boundary zero arrives as a StepError with pointer 0. It leaves the simulation built, with no trace, and init!, restore! and replay! legal again. init! under the same condition reproduces it.

Redstone.trim! — Function
trim!(model::Model{Float64}, problem::TrimProblem; baseline, t0::Real = 0.0,
      backend = LevenbergMarquardt()) -> TrimReport

Solve a trim problem on the model, and commit the solution through init!.

trim! searches the TrimProblem's decisions for a point where every residual sits within its tolerance. Every evaluation runs on scratch stores, so the search never writes the model. The Jacobian is exact, carried by dual numbers through the same evaluation.

Setup layers the problem's condition at the guess over the baseline, as override(baseline, problem.condition(guess)). It then runs the sweep of boundary zero once, with every discrete output stage run and no projection, events or discrete update. Each iteration then sweeps only the continuous chain, with no boundaries and no events. The discrete tier does not run during the search, so its outputs hold the values that first sweep gave them.

The verdict is trim!'s own. After the backend returns, trim! evaluates once more at the returned point and tests each residual against its tolerance, in the residuals' own units. That test sets the report's converged, whatever status the backend gave. A solve that does not converge commits nothing and leaves the model as it was, its status included, so a :built model stays :built. Non-convergence is reported in the TrimReport, never thrown.

A converged solve commits through the model's own init!, as init!(model, override(baseline, problem.condition(solution)); t0). Boundary zero can then move the committed stores off the solved point, through x_projection or an event whose guard already holds. trim! surfaces both. It lists the events fired in the report's fired_events, with a TrimCommitEvents warning. It reads the residuals again at the committed state, with a TrimCommitResiduals warning when they leave their tolerances. The checks are read from the same boundary-zero sweep, and TrimCommitChecks warns of those outside their tolerances.

A problem with no decisions, guess = (;), is legal. It skips the backend. The first sweep is its one evaluation, and the ordinary tolerance test decides. It answers whether the operating point is already an equilibrium, and commits as usual when it is.

trim! checks the problem in two collecting passes, and each refuses it as TrimProblemInvalid. The first runs before any evaluation, with the read set's own ReadResolution failures beside the problem's faults. The second checks the residual and check returns at the guess evaluation, and the residual return again at the first seeded one.

The baseline and the problem's condition at the guess must give every root input a value, and one left without a value is refused as UninitializedInputs. A model a Simulation has claimed is refused as ArgumentInvalid, before any check. So is a second argument that is not a TrimProblem, and a model at a scalar type other than Float64.

Keywords

  • baseline: the required baseline the problem's condition is layered over, at setup and at the commit.
  • t0: the start time of the committing boundary zero, any real, held as a Float64 origin.
  • backend: the solver, any value with a solve method, by default LevenbergMarquardt.

Redstone.LevenbergMarquardt — Type
LevenbergMarquardt(; maxiter::Integer = 100,
                   λ₀::Real = 1e-3) -> LevenbergMarquardt

The default trim backend, a dense Levenberg–Marquardt solver that stops on the problem's own tolerances.

Each iteration solves (JᵀJ + λ·diag(JᵀJ)) δ = −Jᵀr for a step, and projects the step onto the bounds. A step is accepted when it lowers the normalized residual norm ‖r ./ tol‖. λ then shrinks by a factor of 10, and a rejected step grows it by 10. The descent test and the stopping rule both measure the residuals in their tolerances' units, the test trim! applies to the result.

The solver stops with status :converged when every residual is within its tolerance, all(abs.(r) .≤ tol). It stops with :maxiter after maxiter iterations. It stops with :stalled when no step lowers the residual norm. That happens when the step is not finite, when it falls below the rounding scale of the decisions it would move, or when every trial is rejected until the damping passes its ceiling.

Keywords

  • maxiter: the most iterations the solver runs.
  • λ₀: the starting damping factor.

See also solve.

Redstone.solve — Function
solve(backend, eval!, d0, lower, upper, tol) -> NamedTuple

Run the backend's search over packed decision vectors, and return the point it reaches.

solve is the one method a trim solver implements. A new backend type adds one method, solve(backend::MyBackend, eval!, d0, lower, upper, tol), and trim! calls it with vectors, never names. The decisions are packed in guess's order and the residuals in tolerances' order, and the returned point unpacks by that order.

eval!(r, J, d) evaluates the problem at the decisions d, in place. It always fills the residual vector r, and fills the Jacobian J only when J !== nothing. A backend that needs no Jacobian always passes nothing.

d0, lower and upper are Vector{Float64}s in guess's order, with ±Inf for an unbounded side, and d0 already lies within the bounds. Redstone.linearize — Function
linearize(model::Model{Float64}, tap_set::Taps; about = nothing, t0 = nothing,
          width::Int = 8) -> Linearization

Return the linearization of the model at an operating point.

linearize returns the Jacobians A, B, C and D of the model about an operating point, as a Linearization. It is a pure query. It works on scratch stores and commits nothing. It runs no boundary zero and never writes the model. A model a Simulation has claimed still answers, since the query only reads it.

By default the operating point is checkpoint(model), the model's state at the frame top its clock rests on, at that clock's time. about, a condition, places the operating point anywhere else, at time t0. The condition is applied over the declared defaults, and one sweep with every discrete output stage run then sets the discrete outputs.

The tap set, built by taps, names the axes. It is three lists of selectors, declaring what linearization seeds and reads. linearize seeds one direction per x tap and per u tap, and evaluates the model with dual numbers. The value parts give ẋ₀ and y₀. The partials give A and B read at the state derivative, and C and D read at the y taps. States and root inputs that no tap names sit constant at the operating point. The discrete tier is held.

The width changes the grouping, never the answer. The default width's scalar is LinearizeDual, so a build that lists it in activations linearizes any tap set with no compile at the call.

The default form is legal only while the model's status is :consistent, and is refused as ServiceLifecycle otherwise. It is refused as CheckpointMidFrame with the clock off a frame top, as checkpoint is. A root input whose value does not convert to the seeded scalar is refused as ConditionResolution.

The about form is legal at any status. Under it, a condition that does not resolve is refused as ConditionResolution, PathResolution, DuplicateConditionLeaf or ConditionNodeMisuse, the diagnostics resolution raises. A root input it leaves without a value is refused as UninitializedInputs.

linearize resolves the taps in one collecting pass, and refuses their faults together as TapResolution, beside the selectors' own ReadResolution failures. The faults are a member in the wrong list, a discrete state in x, a tap that is not one scalar, a root input that cannot be seeded, and a second tap on one seeded site.

A t0 without about, a width below 1, a second argument that is not a tap set, and a model at a scalar type other than Float64 are refused as ArgumentInvalid.

Keywords

  • about: a condition placing the operating point, or nothing for checkpoint(model).
  • t0: the time of the about operating point, 0.0 when nothing, allowed only beside about.
  • width: how many directions one evaluation seeds, at least 1, by default 8.

Redstone.run! — Function
run!(sim::Simulation; pace = Inf, margin = 0.002, t_end = Inf,
     ignore_stop_requests = ()) -> Nothing

Advance the simulation frame by frame until a termination source ends the run.

run! blocks its caller until the run ends. A frame applies the staged inputs at its top, integrates one step and settles every boundary it reaches. It publishes a snapshot at each.

The run ends when one of three sources fires. The first is t_end, when the frame that reaches it completes. The second is an honoured stop request holding in a published snapshot. The third is a stop through the control plane, seen at a frame top. A stop request ends the run at the boundary that published it, an event boundary inside a frame included, and that snapshot is the final one. t_end ends the run at the first frame top at or past it, in whole frames from t₀.

Each rostered device is initialized and given a task of its own as the run starts, and shut down as it ends. The loop itself runs on the calling task. The run leaves the simulation stopped, with the record that says why readable through termination.

In the :replay input mode the recording also bounds the run. A run that consumes the last record halts there initialized, with no termination record, and the mode turns :live.

A failure inside the loop leaves the simulation errored instead, the cause kept on the record. With no device rostered, run! then rethrows the failure. With one or more, it logs the failure and returns. Ctrl-C is a stop, never a failure. Caught at a frame top or during a pause, it ends the run stopped with ControlRequestedStop(:interrupt).

A pace of Inf, the default, never waits, and 1 is real time. pace! and margin! retune the pace and the margin during the run.

t_end and ignore_stop_requests declare this call's stop policy alone, validated per call. The default ignore_stop_requests = () honours every request. A live run with t_end = Inf and no honoured request ends only through the control plane, Ctrl-C included. It is allowed, and the loop reports UnboundedRun into its own diagnostic cell.

The pace inserts wall time between frames and nothing else, so a paced run is bit-identical to an unpaced one. A frame that overruns leaves debt, and debt past five frames' budget is forgiven with a DebtReanchor warning in the loop's cell. Every snapshot's status carries the pacer's record.

With fewer threads than rostered devices plus one, the loop reports ThreadBudget into its cell.

run! needs an initialized simulation. It is refused as MissingInit when built, since init! or another call that opens a run must come first, and as ServiceLifecycle when running, stopped or errored. A keyword out of range is refused as ArgumentInvalid, and an ignored path that names no requester as StopRequestInvalid.

Keywords

  • pace: simulated seconds per wall-clock second, a positive real.
  • margin: the seconds of each pacing wait spent spinning rather than sleeping, a non-negative real.
  • t_end: the time at which this advance ends the run, a non-negative real or Inf.
  • ignore_stop_requests: the stop requests this advance does not honour, :all or the paths of the requesting components.

Redstone.replay! — Function
replay!(sim::Simulation, trc::Trace; to_boundary = nothing, to_time = nothing,
        pace = Inf, margin = 0.002, t_end = Inf, ignore_stop_requests = (),
        trace = true, log = true, log_every = 1, log_max = 65536,
        restore = true) -> Nothing

Re-drive a recorded session through the ordinary loop, with the recording supplying every frame's inputs.

Replay differs from run! in two places only. It starts from the trace's header as restore! does. No boundary zero runs, so nothing is applied twice. At each frame top, it applies the recording's batches for that frame verbatim. It drops whatever sits in the live staging cells with a ReplayDiscardedStaging warning. The replayed trajectory is bit-identical to the recorded one.

The replay halts at the recording's end, or earlier at to_boundary or to_time, always at a frame top. A replay that halts there ends initialized, never stopped, so it can be inspected, stepped with step! or continued with run!. A termination source that fires first ends it stopped, like any run. A failure inside the loop ends it errored, rethrown when no device is rostered and logged when one is, as under run!.

The recording stays attached after the call, in the :replay input mode. A later step! or run! goes on consuming the records from the halt, and no advance runs past the recording's last frame. The mode returns to :live, the recording detaching with it, when an advance halts at that last frame. live! detaches it earlier.

Replay records a new trace that inherits the old header, so its replayed prefix is bit-identical to the recording and a live continuation appends to it. Rostered devices initialize, run and read snapshots as in any run, but their writes are dropped.

restore = false attaches the recording to the simulation as it stands, and restores nothing. The simulation must be initialized, at the recording's t₀, and at a frame from the header's up to one short of the recording's last. The records apply from the frame after its own. The new trace's header is then this simulation's own checkpoint, the state the replay starts from.

This form replays a modified model initialized under the authored condition, or seeks. To seek, restore! a checkpoint the recording passed through, then replay from the next frame.

An event boundary localized inside a frame is reproduced, but a replay cannot halt there. A to_time between two frame tops halts at the earlier one. to_time and to_boundary are mutually exclusive.

A paced replay is bit-identical to an unpaced one. When neither t_end nor ignore_stop_requests binds, the recording bounds the replay. A live run that ignored some requests replays under the same ignore_stop_requests. Under trace = false nothing is re-recorded.

replay! is refused as ServiceLifecycle while running, and once errored, as init! is. Under restore = false it needs an initialized simulation, and is refused as MissingInit when built and as ServiceLifecycle otherwise. A keyword out of range, or both to_boundary and to_time, is refused as ArgumentInvalid, and an ignored path that names no requester as StopRequestInvalid.

A header that does not match this simulation is refused as CheckpointMismatch or ReplaySchemaMismatch before any record is read. The records' own mismatches, such as ReplayUnknownFace, are then collected into one throw. Every refusal comes before any write.

Keywords

  • to_boundary: halt after the frame that publishes boundary k, a whole number from the frame the replay starts at up to the recording's length.
  • to_time: the same halt by time, at the last frame top at or before it, k = ⌊(to_time − t₀)/h⌋ against the header's t₀.
  • pace, margin: as for run!.
  • t_end, ignore_stop_requests: this replay's stop policy, as for run!, with the same defaults.
  • trace, log, log_every, log_max: as for init!, with the same defaults.
  • restore: false to attach the recording without restoring its header.

Redstone.Blocks.Junction — Type
Junction{In, Out, N}(f) -> Junction{In, Out, N}

A continuous primitive that publishes a fold of its N inputs as its one output.

The inputs in1 to inN are typed In. The one output, y, is typed Out, and a wire names it as in "sum/y". It publishes y = f(in1, …, inN), the fold applied in positional order.

The block is stateless. The fold f is instance data. A model writes a custom fold, such as a weighted blend or a mass-properties composition, at the site.

So is a branch on a Bool that flips at a boundary, as a saturation code does. A branch on a continuous quantity makes a mode silently, and the moded blocks such as Relay exist to declare one.

See also SumJunction, Or, And, Pack.

A discrete primitive that runs a continuous transfer function through a zero-order hold at each tick.

The block takes the transfer function in s of TransferFunction, with its keywords, its refusals and its start at rest or at G(0) u0. It runs it on the discrete tier through the zero-order hold of DiscretizedStateSpace. The hold is taken at each tick. It spans Δt, the component's own period. The block keeps the coefficients and holds the realization wrapped for the hold, and the degrees pick the feedthrough class of DiscreteLinearBlock as for TransferFunction.

The hold keeps the feedthrough class and matches the step response at the samples, where Tustin's method would give every block feedthrough. A design that wants Tustin's frequency response discretizes externally and uses DiscreteTransferFunction.

Keywords

  • num: the numerator's coefficients, highest power of s first, as a tuple or a vector of reals.
  • den: the denominator's coefficients, highest power of s first, likewise.
  • u0: the constant input whose steady state the block starts at, 0.0 for rest.

Redstone.Blocks.PID — Type
PID(; Kp, Ki = 0.0, Kd = 0.0, τd = 0.1, Tt = Inf, u_min = -Inf, u_max = Inf,
      b = 1.0, c = 0.0, hold::Bool = false, tracking::Bool = false) -> PID

A continuous primitive that runs a PID controller with anti-windup.

The inputs are r and y, with the error e = r - y. Two outputs come from stage 2, u_raw and u, its clamp to [u_min, u_max]:

u_raw = Kp (b r - y) + q - Kd (w - yf) / τd

The block holds two continuous states. q is the integral term. yf is the weighted measurement w = y - c r through a lag, ẏf = (w - yf) / τd. One law moves the integral term:

q̇ = Ki ε + (ref - u_raw) / Tt

Two independent type parameters, each adding inputs, fill the slots ε and ref over the error e by the table of ControllerBlock.

hold = true, the parameter Hold, adds two inputs. saturation is an Int8 code such as a LimitedIntegrator publishes for the path downstream. It gates the error by sign, gate(e) = saturation == sign(e) ? 0 : e. engaged is a Bool that reads true while the block is in command. Not engaged, the error is gated to zero whatever the code. Without tracking, a block not engaged freezes. q then holds while the own clamp is free and back-calculates against it otherwise.

tracking = true, the parameter Track, adds the input v, a value the path delivered or the selected command. It takes the place of the own u as the correction's reference. With the hold, v is the reference only while the block is limited or not engaged, and u while it is free. A block not in command therefore follows the selected command at rate 1/Tt and engages without a bump. It chases a moving v with lag Tt, so a block out of command wants a short Tt.

The default Tt = Inf follows nothing. tracking = true with a Tt given as a value and infinite in any channel is therefore refused as an ArgumentError. Tracking needs Tt spelled, or given as AsPort(), which leaves it to the model to keep finite.

A u_min above u_max, both given as values, is refused as an ArgumentError.

q holds the integral term in output units, with Ki inside the integral, so a change in Ki alters only future accumulation.

The setpoint weights b and c multiply r alone, and the integral's error stays e. b acts in the proportional term and c in the derivative's weighted measurement. Their defaults, b = 1 and c = 0, put the derivative on the measurement, so a step in r makes no kick. c = 1 puts it on the error.

The defaults make the plain spelling a P controller, with Ki = Kd = 0 and infinite limits. They also set Tt = Inf, which switches the correction off.

The parameters, the inputs r, y and v, the outputs u and u_raw and the states share one type, the parameter V, Float64 or an SArray of Float64, the broadcast of the nine keywords given as values. Over an SVector the law is componentwise, and saturation is an SVector of Int8 and engaged one of Bool.

The nine keywords given as values broadcast to one V, whose shape is the sum of their zeros, so a scalar pairs with a vector and integer values qualify. A vector PID with uniform gains spells at least one keyword as a vector, Kp = @SVector fill(2.0, 3).

Any of the nine parameters may be an input port in place of a field, spelled Kp = AsPort() with AsPort. The port is named for the parameter and typed V, and it takes no part in the shape, so when every value-carrying keyword is a port, V is Float64. Under a Dual activation, a scheduled parameter carries partials, so a linearization sees the coupling through the schedule. A model that wants it frozen at its plain Float64 value routes the port through Freeze.

u is a stage-2 output, so every input makes a feedthrough edge, whether y_direct reads it or not. A tracking input wired from a memoryless clamp of the block's own u is refused as an AlgebraicCycle classified artificial. That is why the limits live inside the block. v serves a value published from state, such as a stateful actuator's position. A scheduled parameter computed memorylessly from u closes a cycle too, artificial for Ki and Tt, which only the derivative reads, and real for the others. One read from a state is fine.

Keywords

  • Kp: the proportional gain.
  • Ki: the integral gain, inside the integral.
  • Kd: the derivative gain.
  • τd: the time constant of the derivative's lag, positive.
  • Tt: the time constant of the correction, Inf to switch it off.
  • u_min: the lower limit of u.
  • u_max: the upper limit of u.
  • b: the setpoint weight in the proportional term.
  • c: the setpoint weight in the derivative's weighted measurement.
  • hold: true to add the inputs saturation and engaged, the parameter Hold.
  • tracking: true to add the input v, the parameter Track.

See also DiscretePID, PIDBlock, LQRTracker.

Redstone.Blocks.DiscretePID — Type
DiscretePID(; Kp, Ki = 0.0, Kd = 0.0, τd = 0.1, Tt = Inf, u_min = -Inf, u_max = Inf,
              b = 1.0, c = 0.0, hold::Bool = false, tracking::Bool = false) -> DiscretePID

A discrete primitive that runs a PID controller with anti-windup.

The block takes the parameters, defaults, ports and law of PID to the discrete tier. Two store fields stand in for its continuous states. q is the integral term, and yf is the weighted measurement w = y - c r through a lag. A third, saturated, holds its code. Δt is the component's own period.

The inputs are r and y, with the error e = r - y. Two outputs come from stage 2, u_raw and u, its clamp to [u_min, u_max]:

u_raw = Kp (b r - y) + q - Kd (w - yf) / (τd + Δt)

Each tick moves the lag by backward Euler, yf⁺ = yf + Δt (w - yf) / (τd + Δt). It moves the integral term by forward Euler and the correction's exact step:

q⁺ = q + Δt Ki ε + β (ref - u_raw),    β = 1 - exp(-Δt / Tt)

The two anti-windup axes fill the slots ε and ref by the table of ControllerBlock.

hold adds the inputs saturation and engaged, and a block not engaged without tracking freezes. tracking adds the input v. With the hold, the reference falls back to u while the block is free. All of this is as in PID. The setpoint weights b and c multiply r alone, as in PID, and the integral's error stays e.

tracking = true with a Tt given infinite in any channel is refused as an ArgumentError, as in PID. So is a u_min above u_max, both given as values.

The parameters, the inputs, the outputs u and u_raw and the states share one type, the parameter V, Float64 or an SArray of Float64, and over an SVector the law is componentwise, as in PID. The nine keywords given as values broadcast to one V by the rule of PID, the shape the sum of their zeros. A scalar therefore pairs with a vector, and a uniform vector gain spells one keyword as a vector, Kp = @SVector fill(2.0, 3).

Any parameter may be an input port, spelled Kp = AsPort() with AsPort, typed V and outside the shape. It carries partials under a Dual activation, and Freeze holds it at its plain Float64 value, as in PID.

The backward Euler lag is stable at every period, and τd = 0 is legal. yf is then the previous weighted measurement, and the D term the backward difference (w - yf) / Δt.

β is the exact step of the correction's relaxation over one period, so every Tt is stable. Tt = Inf switches the correction off. Tt = 0 is legal and brings u_raw to the reference by the next tick, the clamping scheme as the limit of tracking. Not engaged with tracking, Tt = 0 follows v exactly.

A third output, saturated, publishes the Int8 code of the block's own clamp, an SVector of Int8 over a vector. The code is 1 with u_raw at or above u_max, -1 at or below u_min and 0 between. s_update writes it to the store from u_raw at the tick, and y_state publishes it from stage 1 at the next. It is therefore one tick stale, and flips only on a tick boundary.

The code serves the hold of an outer block in a cascade, wired to its input saturation. The outer block's integrator takes one extra step before the hold engages. As a stage-1 port the code closes no cycle through the outer block's u. The block never reads its own code, since its own windup is the correction's.

A tracking input wired from a memoryless clamp of the block's own u is refused as an AlgebraicCycle, as for PID, but classified real. A discrete member's dependences are traced from its structure, so no hop is named dead. A scheduled parameter computed memorylessly from u closes a cycle likewise.

Keywords

  • Kp: the proportional gain.
  • Ki: the integral gain, inside the integral.
  • Kd: the derivative gain.
  • τd: the time constant of the derivative's lag, 0 for the backward difference.
  • Tt: the time constant of the correction, Inf to switch it off and 0 to correct within one tick.
  • u_min: the lower limit of u.
  • u_max: the upper limit of u.
  • b: the setpoint weight in the proportional term.
  • c: the setpoint weight in the derivative's weighted measurement.
  • hold: true to add the inputs saturation and engaged, the parameter Hold.
  • tracking: true to add the input v, the parameter Track.

A continuous primitive that runs an LQR tracker about a trim point, with anti-windup.

The inputs are x, the plant state, z, the command variables, and z_ref, their reference. Two outputs come from stage 2, u_raw and u, its clamp to [u_min, u_max] per channel:

u_raw = u_trim + K_fwd (z_ref - z_trim) - K_fbk (x - x_trim) + q

The block holds one continuous state, the field x, written q below, the integral term in output units, one channel per control input. One law moves it:

q̇ = ε + (ref - u_raw) / Tt

The two anti-windup axes of PID, each adding inputs, fill the slots ε and ref over the integrator input e = K_int (z_ref - z). They fill them channel by channel, by the table of ControllerBlock.

hold = true, the parameter Hold, adds two inputs. saturation, a code per channel from the path downstream, gates each channel whose code agrees with the sign of its integrator input, gate(e) = saturation == sign(e) ? 0 : e. engaged, a flag per channel that reads true in command, zeroes the integrator input of a channel not engaged whatever its code. Without tracking, a channel not engaged freezes, its own clamp's correction alone moving it.

tracking = true, the parameter Track, adds the input v as the correction's reference in place of the own u. With the hold, v is the reference in a channel only while it is limited or not engaged. A channel not engaged therefore converges to v at rate 1/Tt and engagement is bumpless. The own clamp is the correction's, and Tt = Inf switches it off.

Tracking with a Tt given as a value and infinite in any channel is refused as an ArgumentError, as for PID. A u_min above u_max, both given as values, is refused as an ArgumentError.

The ports are each an SVector at every size. x is an SVector{NX, Float64}, z and z_ref are SVector{NZ, Float64}, and u, u_raw and v are SVector{NU, Float64}. saturation is an SVector{NU, Int8} and engaged an SVector{NU, Bool}.

Any of the nine parameters may be an input port in place of a field, spelled K_fbk = AsPort() with AsPort and typed as the field would be, an SMatrix{NU, NX, Float64, NU * NX} for K_fbk. That is how a gain schedule reaches the block. Under a Dual activation, the port carries partials, and a model that wants it frozen at its plain Float64 value routes it through Freeze.

The first form reads NX, NU and NZ off the values given, K_fbk first, then K_fwd, K_int and the trims. It passes every keyword on to the second, the explicit spelling, which takes the sizes and the same keywords. A matrix or a vector that does not fit the sizes read is refused as an ArgumentError. A size no value carries, every carrier a port or left at its default, is refused likewise, naming the explicit spelling.

u is a stage-2 output, so every input makes a feedthrough edge, whether y_direct reads it or not. An x assembled from what the plant publishes from state, and a z selected from the same, close no loop. A z_ref computed memorylessly from the block's own u closes an AlgebraicCycle classified real, since the direct law reads it. A tracking input wired from a memoryless clamp of u closes one classified artificial, since only the derivative reads it. That is why the limits live inside the block. A scheduled parameter computed memorylessly from u closes a cycle too, artificial for K_int and Tt and real for the others.

The block publishes no saturation code. The gains are designed outside, from trim! and linearize.

K_int and the trims default to zero. Tt, u_min and u_max are each a real broadcast to an SVector{NU, Float64}, or a vector of length NU. Integer entries qualify.
