API

The entry points, grouped as the specification's Appendix B groups them.

Authoring

Redstone.AbstractComponent — Type
AbstractComponent

The abstract type every component subtypes, primitive and assembly alike.

A component is a plain struct, MyComp <: AbstractComponent, whose fields are inert parameters or child components. Its class is read off which declarations its type defines. Defining local_wires makes it an assembly, whose component-typed fields are its children. Defining any primitive declaration, such as x_init, u_types or the stage y_direct, makes it a primitive. There is no separate assembly type, so a field typed by a domain supertype accepts a primitive and an assembly alike.

A component's module extends the declarations it defines, importing each one by name, as in import Redstone: x_init, y_types, y_direct, and defines them at module top level.

The build refuses a type that defines neither family as ClassUnreadable, and one that defines both as ClassMixed. A module that binds a declaration name to a function of its own, the sign of a missing import, is refused as DeclarationShadowed.

Redstone.x_init — Function
x_init(c) -> NamedTuple

Return the component's initial continuous state, as a NamedTuple of named values.

A continuous primitive declares its state by value, written with Float64 values, as in x_init(::Engine) = (ω = 0.0,). The state's type is derived from the value, and its real values follow the scalar of each activation. Each field is one Float64 or one static array of Float64. Integers, Bools and enums belong in m_init.

Every primitive defines exactly one of x_init and s_init, and the one it defines makes it continuous or discrete. A stateless continuous primitive declares x_init(::C) = (;). A non-empty state needs an x_deriv method.

The build refuses a value that is not a NamedTuple as StoreNotNamedTuple, and a field outside the state vocabulary as IllegalStateLeaf. A non-empty state with no x_deriv is refused as StoreWithoutUpdate, a primitive that defines neither x_init nor s_init as TierUnreadable, and one that defines both as DeclarationOnWrongTier.

Redstone.m_init — Function
m_init(c) -> NamedTuple

Return the component's initial modes, as a NamedTuple of named values.

A continuous primitive declares its modes by value, as in m_init(::Engine) = (phase = off,). Every field is isbits or a Symbol, as for s_init. Event handlers write the modes, and nothing else may. A primitive may declare modes that no event of its own changes.

Modes are continuous-only, because the event system is continuous-side only. The build refuses a non-empty m_init on a discrete primitive as DeclarationOnWrongTier, a value that is not a NamedTuple as StoreNotNamedTuple, and a field that is neither isbits nor a Symbol as IllegalStoreField.

Redstone.ws_init — Function
ws_init(c, ::Type{T})

Allocate the component's workspace at the scalar type T.

The framework calls the allocator and hands its result to the component's functions as the ws field of their bundle. Declaring is allocating, so ws_init is the one declaration that takes the scalar. Sizes come from the instance and eltypes from T, as in ws_init(c::KF, ::Type{T}) where {T} = (P = Matrix{T}(undef, c.n, c.n),).

The allocator takes T on both tiers. A continuous allocator is called at the scalar of each activation, and a discrete one always receives Float64. The contents at each call are unspecified, and the framework never reads or writes them. A component that needs no scratch defines no method.

Redstone.u_types — Function
u_types(c) -> NamedTuple

Return the types the component accepts on its inputs, a NamedTuple of input name => type.

The entries are written at Float64 and take the component alone on both tiers, as in u_types(::Engine) = (throttle = Float64, starter = Bool). On a continuous primitive every Float64 position follows the scalar of each activation, and an entry wrapped in Pinned does not. On a discrete primitive every entry stays as written. The default declares no inputs.

An entry states what the component allows to arrive. An unwrapped Float64 leaf tolerates both the activation scalar and a frozen Float64, and a Pinned entry demands an arriving value that never carries partials.

The build refuses a wire whose producer type does not fit the entry as WireTypeMismatch, and a producer that follows the scalar at a Pinned entry as WalkingFaceAtFrozenEntry. A Pinned marker below the top of an entry is refused as IllegalPortType, and a Pinned entry on a discrete primitive as DeclarationOnWrongTier.

source
Redstone.y_types — Function
y_types(c) -> NamedTuple

Return the types of the component's output ports, a NamedTuple of port name => type.

The entries are written at Float64 and take the component alone on both tiers, as in y_types(::Engine) = (M_shaft = Float64, P = Float64). The declaration is read literally. On a continuous primitive, a port's value at each activation has the declared type with every Float64 position, alone or as a type parameter, at that activation's scalar. An entry wrapped in Pinned keeps its type at every activation. On a discrete primitive every entry stays as written.

One declaration covers both output stages, y_state and y_direct, and no port names its stage. The build finds which stage produces each port by its probe, and checks each return against this declaration.

A primitive with an empty state and no y_types is refused as StatelessWithoutOutputs. A declared port no stage returns is refused as DeclaredNotProduced, a returned name the declaration lacks as UndeclaredReturnField, and a port both stages return as ProducedByTwoStages.

source
Redstone.state_events — Function
state_events(c) -> NamedTuple

Return the component's events, a NamedTuple of name => StateEvent, in priority order.

A continuous primitive declares its events as named entries, state_events(::Engine) = (start = StateEvent(start_guard, start_handler),). Order is semantics. At a boundary a component fires at most one event per round, the first eligible one in declaration order, and the rounds repeat until none fires, so the guards are decided again after each firing. Nothing here is inferred, and the default declares no events.

Events are continuous-only, like m_init, because the event system is continuous-side only. The build refuses a non-empty state_events on a discrete primitive as DeclarationOnWrongTier, and an entry that is not a StateEvent as EventHalfMissing.

source
Redstone.y_state — Function
y_state(c, bundle) -> NamedTuple

Return the component's stage-1 outputs.

y_state is the first of a primitive's two output stages, defined by a method for the component's type, as in y_state(::Engine, (; x)) = (; ω = x.ω). Its bundle carries no inputs, so a stage-1 port never depends instantly on an input and breaks would-be feedback loops. A primitive sits on one tier. On the continuous tier the bundle may carry x, m, t and ws, and on the discrete tier s, t, Δt and ws, each only if the component has it.

The stage returns a NamedTuple of port values at their y_types types. y_direct receives the return as y_x, or y_s on the discrete tier, so an intermediate both stages need is computed once. A component exposes a state or mode field by returning it here. A discrete primitive's stages run only at its ticks, and its ports hold their values in between.

The stage is optional, and a component with no stage-1 ports defines no method. The build refuses a read outside the bundle as BundleFieldError, a return of bare (;) as DeadStage, and a returned name y_types lacks as UndeclaredReturnField.

source
Redstone.y_direct — Function
y_direct(c, bundle) -> NamedTuple

Return the component's stage-2 outputs.

y_direct is the second of a primitive's two output stages, as in y_direct(eng::Engine, (; x, m, u)) = (; M_shaft = ..., P = ...). Beside the state, its bundle carries the inputs u and the return of y_state as y_x. A primitive sits on one tier, and a discrete primitive receives that return as y_s. On the continuous tier the bundle may carry x, m, u, y_x, t and ws, and on the discrete tier s, u, y_s, t, Δt and ws, each only if the component has it.

Every stage-2 port is taken to depend on every wired input. The stage returns a NamedTuple of port values at their y_types types, and the two stages together produce each declared port exactly once.

The stage is optional. The build refuses a read outside the bundle as BundleFieldError, a port that both stages return as ProducedByTwoStages, and a returned name y_types lacks as UndeclaredReturnField.

source
Redstone.x_deriv — Function
x_deriv(c, bundle) -> NamedTuple

Return the time derivative of the component's continuous state.

x_deriv is the continuous primitive's update law, its flow, as in x_deriv(eng::Engine, (; x, y, u)) = (ω = (y.M_shaft - u.M_load) / eng.J,). It runs after the output stages, when every port is fresh, so it reads the component's own outputs y instead of computing them again. Its bundle may carry x, m, y, u, t and ws, each only if the component has it.

The return has exactly the fields of x_init, each at the state's type. A continuous primitive with a non-empty state must define it.

The build refuses a non-empty x_init with no x_deriv as StoreWithoutUpdate, a return whose fields or types differ from the state's as ConformanceFailure, and a read outside the bundle as BundleFieldError. A primitive that also defines s_update or s_init is refused as DeclarationOnWrongTier.

Redstone.StateEvent — Type
StateEvent(guard, handler) -> StateEvent

One event of a state_events declaration: a guard and its handler, and nothing else.

The guard and the handler both take the component and its bundle. The bundle may carry x, m, y, u, t and ws. There is no detection keyword, because the guard's return type declares the policy. A Bool guard is boundary-detected. A guard returning a Float64 is localized, and its event holds where the value is ≥ 0.

The handler returns a NamedTuple of the stores it writes, such as (; m = (; phase = running)). A present x replaces the whole continuous state, and a present m merges into the modes.

The build refuses a guard that returns neither form as GuardForm, a missing guard or handler method as EventHalfMissing, and a handler key that names no store of the component as HandlerReturnKey.

source
Redstone.x_projection — Function
x_projection(c, x) -> NamedTuple

Return the continuous state x projected back onto the component's manifold.

x_projection takes the state alone, not a bundle: one store in, the same store out, which is why it alone stays positional. An attitude model might declare x_projection(c::Attitude, x) = (; q = normalize(x.q)). It runs after each integration step and after each event handler fires. Its return replaces the whole continuous state, so it carries every state field at the state's type.

The method is optional and continuous-only. The build refuses it on a discrete primitive, or on one with an empty state, as DeclarationOnWrongTier, and a return whose fields or types differ from the state's as ConformanceFailure.

Redstone.s_init — Function
s_init(c) -> NamedTuple

Return the component's initial discrete state, as a NamedTuple of named values.

A discrete primitive declares its state by value, as in s_init(::Counter) = (n = 0,). Every field is isbits or a Symbol, and the field types stay as written at every activation. Text and bulk data belong on the component instance.

Every primitive defines exactly one of x_init and s_init, and the one it defines makes it continuous or discrete. A stateless discrete primitive declares s_init(::C) = (;), and holds its outputs between its ticks. A non-empty state needs an s_update method.

The build refuses a value that is not a NamedTuple as StoreNotNamedTuple, and a field that is neither isbits nor a Symbol as IllegalStoreField. A non-empty state with no s_update is refused as StoreWithoutUpdate, and a primitive that also defines x_init as DeclarationOnWrongTier.

source
Redstone.s_update — Function
s_update(c, bundle) -> NamedTuple

Return the component's discrete state after one tick.

s_update is the discrete primitive's update law, as in s_update(::Counter, (; s)) = (n = s.n + 1,). It runs at each of the component's ticks, once the boundary's outputs and events have settled. Its bundle may carry s, y, u, t, Δt and ws, each only if the component has it, and Δt is the component's own tick period.

The return replaces the whole state, so it has exactly the type of the value s_init returns. A discrete primitive with a non-empty state must define it.

The build refuses a non-empty s_init with no s_update as StoreWithoutUpdate, a return of another type as ConformanceFailure, and a read outside the bundle as BundleFieldError. A primitive that also defines x_deriv or x_init is refused as DeclarationOnWrongTier.

Redstone.local_wires — Function
local_wires(c)

Return the assembly's internal wires, an ordered collection of "child/face" => "child/face" pairs.

Every pair runs from a child's output face to a child's input face, and its arrow reads along the signal flow. Both endpoints are relative to the declaring assembly, each one an immediate child and one of its faces, so "aircraft/2/face" names a container element's face in one level.

Defining local_wires is what makes a component an assembly, so an assembly defines it even with no wires, as local_wires(::A) = (). The assembly's own boundary is declared by input_wires and output_wires.

The build refuses an endpoint whose port has the wrong direction as FaceDirectionConflict, an input fed twice as TwoProducers, and a component that defines local_wires beside any primitive declaration as ClassMixed.

source
Redstone.input_wires — Function
input_wires(c)

Return the assembly's inward boundary, an ordered collection of input name => internal endpoint path pairs.

Each input name is a face, and it routes inward to an input of an immediate child, as in "throttle" => "engine/throttle". A face that feeds several children takes a tuple of paths, "trn" => ("left/trn", "right/trn"), fanning out through the boundary. The default declares no input face. At the root of a build these faces are the root inputs.

Face names contain no /, and are unique across input_wires and output_wires together. The build refuses a face name holding / as FaceNameIllegal, a name declared twice as FaceNameCollision, an endpoint that resolves to an output as FaceDirectionConflict, and an empty tuple of paths as UnknownPort.

source
Redstone.output_wires — Function
output_wires(c)

Return the assembly's outward boundary, an ordered collection of internal source path => output name pairs.

Each output name is a face, and it exposes an output of an immediate child, as in "aircraft/pose" => "view_pose". The source comes first, so the pairs read along the signal flow, like every pair of local_wires and input_wires. The default declares no output face.

The build refuses a face name holding / as FaceNameIllegal, a name declared twice across the two boundary declarations as FaceNameCollision, and a source that resolves to an input as FaceDirectionConflict.

Redstone.sample_times — Function
sample_times(c) -> NamedTuple

Return the assembly's sample times, a NamedTuple of immediate child name => Relative or Absolute.

A rate scope schedules the assembly's discrete children and sub-assemblies, as in sample_times(::A) = (nav = Relative(5), gnss = Absolute(Hz(10))). The declaration is optional, and so is every key: an unlisted discrete child defaults to Relative(1), so only multiplied, phased or anchored children appear. A container field's bare name keys one entry for all its elements.

The rates belong to the assembly type, as design ratios or a modeled instrument's own rate. A rate that is a deployment preference is exposed as a constructor parameter, and read off the instance here.

The build refuses a value that is not such a NamedTuple, a bare number in place of a wrapper, a key that names no immediate child, and a key on a continuous child, each as RatesViolation.

source
Redstone.transparent_container — Function
transparent_container(c) -> Union{Symbol,Nothing}

Return the name of the one container field whose children go by bare key, or nothing.

Its elements are children of the component, named "field/key" or "field/1". Returning that field's Symbol names them "key" and "1" instead, everywhere a child name appears: wiring endpoints, sample_times keys, read paths, at prefixes and diagnostics. Naming is the only thing it changes, and the container still has no wires, faces or rate of its own.

The declaration is optional, and a component may name at most one field. The default, nothing, keeps every container's key segment. The build refuses a name that matches no container field as TransparentContainerUnknown, and a bare key that collides with a sibling child's name as ChildNameCollision.

Redstone.Relative — Type
Relative(K, φ) -> Relative
Relative(K::Integer) -> Relative

A sample time in ticks of the enclosing scope: every K-th tick, starting from the φ-th.

A sample_times entry Relative(K, φ) runs its child at every K-th tick of the enclosing rate scope, starting from its φ-th, and φ defaults to 0. Scope ticks are the unit system, so relative entries compose affinely down the tree. Under a scope that ticks every D_s base ticks at phase Φ_s, the child ticks every K·D_s base ticks at phase Φ_s + φ·D_s.

K = 1 admits no stagger. Two same-rate siblings are staggered one level down instead: declare their scope at twice their rate, and give them Relative(2, 0) and Relative(2, 1).

The constructor checks nothing. The build refuses K < 1, or a φ outside 0 ≤ φ < K, as RatesViolation.

source
Redstone.Absolute — Type
Absolute(q::Period, τ::Union{Integer,Rational{<:Integer}} = 0) -> Absolute

A sample time in exact rational seconds, with ticks at t = τ + k·T.

q is a period T, built with Period or Hz, and τ is the offset in seconds. The entry is an anchor. It severs its child from the enclosing scope's grid, so the child may tick faster than its scope. The child's ticks are counted in base ticks only once a Deployment fixes Δt_base. Anchor periods and nonzero offsets constrain that grid together, and an offset of T/1000 can cost a grid 1000 times finer.

A float offset is refused as ArgumentInvalid, and so is a bare number in place of a Period: write Absolute(Hz(50), 1//500). The build refuses a period that is not positive, or an offset outside 0 ≤ τ < T, as RatesViolation.

source
Redstone.Period — Type
Period(T::Union{Integer,Rational{<:Integer}}) -> Period

A time period T, in exact rational seconds.

A Period is what Absolute and the Δt_base keyword of Deployment take. Period(1//50) and Hz(50) are the same value, a spelling choice: both are normalized to the exact rational period at construction. See Hz for the frequency spelling.

A float is refused as ArgumentInvalid, because the base grid is derived by GCD arithmetic, which is ill-defined over floats. Write Period(1//50), not Period(0.02).

source
Redstone.Hz — Function
Hz(frequency::Union{Integer,Rational{<:Integer}}) -> Period

Return the Period of a frequency, 1 // frequency seconds.

Hz(50) and Period(1//50) are the same value, and either may be given to Absolute or as the Δt_base keyword of Deployment. A float is refused as ArgumentInvalid, because the grid arithmetic is exact: write Hz(1//2) for 0.5 Hz, not Hz(0.5).

Redstone.stop_reason — Function
stop_reason(c) -> String

Return the reason the component's stop requests report, "" by default.

A stop request is an output port of type StopFlag. The build reads stop_reason for every component that publishes such a port, and all of the component's requests share the reason. It is instance data, never a port value. A run that a request ends carries the reason on its ModelRequestedStop source.

source
Redstone.Pinned — Type
Pinned{P}

The marker that keeps one u_types or y_types entry at type P, whatever scalar the model runs at.

Pinned wraps a whole entry of u_types or y_types, as in Pinned{Float64} or Pinned{SVector{3,Float64}}, to say the entry never follows the scalar of an activation. On an output the port's value is a P at every activation. On an input the entry demands an arriving value that never carries partials. The build strips the marker at Float64, so no value, layout or message carries the wrapper itself. It is a type-level marker, never instantiated.

A marker below the top of an entry, in a type parameter, is refused as IllegalPortType on both tiers. The marker is continuous-only: a discrete primitive's entries never follow the scalar, so a Pinned entry there is refused as DeclarationOnWrongTier.

Redstone.build — Function
build(root::AbstractComponent; activations::Tuple = ()) -> Build

Check a component tree and return its Build, with no grid chosen yet.

build runs the structure step, the nominal evaluation and the eager activations. The structure step flattens the tree, classifies its components and type-checks the wires into the Structure. The nominal evaluation probes every user function. It returns the Outputs, the Events and the nominal activation. Nothing here needs h, N_base or Δt_base, which are the Deployment's.

Keywords

  • activations: the scalar types whose activations are made at once instead of at first request, such as (Float64, ProbeDual) in a test that checks the tree types at a dual number. See ProbeDual.

A tree the build rejects is refused as one DiagnosticError that carries every diagnostic the failing step found, and the warnings raised so far. A build that succeeds logs each warning once and keeps it, read with warnings.

See also descriptor, Model, Simulation.

source
Redstone.Build — Type
Build

The artifact build produces, the checked contract of a component tree before any grid is fixed.

A build holds the Structure, the Outputs and the Events, which the build's steps produce, then its activations and the warnings its construction raised, read with warnings. The first three do not depend on the scalar type, by construction. The nominal Float64 activation is made by the build, and any other is derived at first request and kept.

Everything in a build is settled before Δt_base exists: h, N_base and Δt_base are the Deployment's. A build is immutable apart from its activation cache, whose insertion is safe across tasks. One build backs any number of deployments and Models, concurrently, each materializing its own stores and buffers.

See also descriptor.

source
Redstone.Structure — Type
Structure

The structure step's product, the declared facts the component tree alone fixes, held as rows.

Structure is read off a Build as build.structure. Nothing in it depends on a scalar type. Its rows hold the component instances, and paths, names and rationals the REPL prints as they are.

  • components: one entry per primitive, in the order the build walks the tree.
  • anchors: one entry per Absolute declaration, the exact (T, τ) pair (period and offset in rational seconds) with the declaring scope and key.
  • scopes: one entry per assembly a sample_times key names, with its path, the key and the timing the build derived for it.
  • root_inputs and root_types: the root inputs, in order, with the types the wire check fixed for them.
  • levels: one entry per assembly, in pre-order with the root first, holding its children and the wires it declares. A primitive root's entry has no children and no wires.

No table of resolved faces is stored. A face at any level is resolved over the levels wires when it is read.

source
Redstone.Outputs — Type
Outputs

The output port names each component's stages produce, and the order the components run in.

Outputs is a product of the nominal evaluation, read off a Build as build.outputs. Its components field holds one entry per component, in the order the build walks the tree. Each entry carries the component's path, the ports y_state returns as stage1, in the return's order, and the declared remainder, in y_types order, as stage2. Their concatenation is the order of the component's products. The order field is the execution order over the indices of components.

Outputs holds names only and does not depend on the scalar type, so a reader that wants a list of port names takes it from here rather than from an activation. The feedthrough graph the order was computed over is not carried. Where it is shown, it is derived from the Structure's connections and the producers' stage2.

source
Redstone.Events — Type
Events

The detection policy of each component's events, and the field names of its event bundle.

Events is the other product of the nominal evaluation, read off a Build as build.events. Its components field holds one entry per component, in the order the build walks the tree, so one index addresses it and Outputs alike. Each entry carries the component's path, its policies and its bundle.

  • policies: a NamedTuple from each event name, in declaration order, to the detection policy its guard's return form fixes, :boundary for a Bool guard checked at step boundaries only, or :localized for a guard returning a Float64, whose crossing is located in time.
  • bundle: the field names of the event bundle, () where the component declares no events.

Like Outputs, Events holds names only and does not depend on the scalar type.

Redstone.descriptor — Function
descriptor(build::Build) -> NamedTuple
descriptor(deployment::Deployment) -> NamedTuple

Return the artifact's descriptor, its rendering to data.

The descriptor is an envelope with the fields format_version, redstone_version and kind, and the body under the key the kind names, build or deployment. A deployment's body embeds the build's whole. The artifact is a Build or a Deployment.

The value is a tree of NamedTuples and vectors, ready for any JSON encoder, and conforms to the schema the package ships as schema/descriptor.json. Encoding it is the caller's job.

See also Build, Deployment.

Redstone.ProbeDual — Type
ProbeDual

The framework's public canonical probe scalar, the concrete ForwardDiff.Dual{ProbeTag,Float64,1}.

ProbeDual is the one concrete Dual a test lists to check that a component tree types at a dual number, as in build(root; activations = (Float64, ProbeDual)). An activation is keyed by a concrete scalar, and the bare Dual, a UnionAll, can key none.

Its width is one because the check tests that the tree's types follow the scalar, not any particular Jacobian. linearize sets its own width with its width keyword.

Redstone.resolve — Function
resolve(assembly, path::AbstractString) -> AbstractComponent

Return the immediate child of an assembly that path names.

resolve walks the assembly's declared fields along the / segments of path. The path names one child: its field's name, plus a key segment where the child is an element of a container field, as in "units/1" or "units/left". The elements of a container declared name-transparent with transparent_container go by their bare keys, "1" or "left". Declaration bodies such as input_wires call it to compute entries from a child's contract.

Resolution goes one level only. A path that reaches past the child it names is refused as PathResolution, naming that child. An empty path, and a segment that names no child, are refused as PathResolution too.

Redstone.input_faces — Function
input_faces(comp) -> Vector{String}

Return the component's input face names, in declaration order.

For a primitive the input faces are the keys of its u_types, which do not depend on the scalar type. For an assembly they are the face names its input_wires declares. Declaration order is kept, so printouts are deterministic and diagnostics stable.

Called from a declaration body during a build, input_faces reuses the build's evaluation of the child's declaration rather than evaluating it again. Either way the vector returned is a fresh one, the caller's to change.

See output_faces for the output side, and input_passthrough for the helper built on it.

source
Redstone.output_faces — Function
output_faces(comp) -> Vector{String}

Return the component's output face names, in declaration order.

For a primitive the output faces are the keys of its y_types. For an assembly they are the face names its output_wires declares.

Called from a declaration body during a build, output_faces reuses the build's evaluation of the child's declaration rather than evaluating it again. Either way the vector returned is a fresh one, the caller's to change.

See input_faces, the mirror on the input side, and output_passthrough for the helper built on it.

Redstone.input_passthrough — Function
input_passthrough(assembly, child_path::AbstractString; sep::AbstractString = ".",
                  prefix::AbstractString = replace(child_path, "/" => sep),
                  except::Tuple = (), only::Tuple = (), select = nothing) -> Tuple

Return input wire entries that expose a child's input faces on the assembly's own boundary.

The helper serves the pass-through case, where an assembly hands up the inputs of a child it does not feed itself. Its entries are splatted into the assembly's input_wires, and mix freely with hand-written ones: input_wires(w::World) = (input_passthrough(w, "aircraft"; except = ("atm",))...,). Each face of the child, as input_faces lists it, becomes the pair prefix * sep * face => child_path * "/" * face.

child_path names an immediate child, a bare key where the container is name-transparent. A deeper path is refused as resolve refuses it.

Keywords

  • sep: the separator between the prefix and the face name.
  • prefix: the label in front of each face. The default folds the path's / into sep, so a container element "units/1" labels its faces "units.1.…", a legal face name. An explicit prefix is used verbatim, and prefix = "" drops the prefixing entirely.
  • except: the face names to leave out.
  • only: the face names to keep.
  • select: a predicate that receives each face name as a String and keeps the ones it accepts.

The three selection keywords are exclusive, one per call. More than one is refused as UnknownFaceSelection with reason :multiple_selectors, and an except or only name the child does not have as UnknownFaceSelection with the child's faces listed. A selection keyword that keeps nothing warns EmptyFaceSelection on the build, while a call with no selection keyword over a child without faces is silent.

See also output_passthrough.

source
Redstone.output_passthrough — Function
output_passthrough(assembly, child_path::AbstractString; sep::AbstractString = ".",
                   prefix::AbstractString = replace(child_path, "/" => sep),
                   except::Tuple = (), only::Tuple = (), select = nothing) -> Tuple

Return output wire entries that expose a child's output faces on the assembly's own boundary.

output_passthrough is input_passthrough's sibling on the outward boundary, and its entries are splatted into the assembly's output_wires. It takes the same keywords over the faces output_faces lists, with the same folded default prefix and the same three exclusive selection keywords, one per call, select receiving face names. Its pairs read along the flow, child_path * "/" * face => prefix * sep * face, internal source to face name, as every pair in that declaration does.

Each level re-exports the outputs it surfaces, so an output deep in the tree reaches the root only through one entry per level, which this helper computes. Redstone.attach! — Function

Add a device to the roster under a binding, and return the device's handle.

The roster is fixed for each run. attach! is therefore a stopped-sim operation. It registers the device and spawns nothing: the device's task starts with the next run!.

The binding declares the device's sides. On the input side, the device's claim is what the binding's claims returns, or, for a binding declaring is_greedy, every face no other device has claimed at this moment.   • should_abort: whether the device's departure also stops the run. Set, the device's loop returning, a crash or a failed init! requests a stop. Clear, the run continues without the device's task, and its claim holds until the run ends.

attach! is refused as ServiceLifecycle while running, and once errored, since no run follows an errored simulation. A binding or device that breaks its contract is refused as BindingContractMismatch or DeviceContractMismatch, and a device instance already on the roster as AlreadyAttached; to rebind one, detach! it first. init!(sim::Simulation, condition = set(); t0::Real = 0.0, trace = true,
      log = true, log_every = 1, log_max = 65536) -> Nothing

Initialize the simulation from a condition on the declared defaults, and run boundary zero at t0.

init! resets the state to the declared defaults, applies the condition's overrides, sets the clock to t0 and runs boundary zero. The condition is a sparse overlay addressed by component path, built with set and its combinators. Root inputs have no declared default, so the condition must give every one of them a value.

Boundary zero derives every output's value from the state. Every event starts as not holding, so an event that already holds in the initialized state fires at t0. Calling init! again resets the state and the events from scratch, and such an event fires again at the new t0.

init! opens a fresh run, with a new log and a new trace rather than cleared ones, and the input mode back at :live. It clears the stop word. It also drops every batch still waiting, so nothing staged earlier reaches the new trajectory. Stage after init! and before run!, and the batch waits for the first frame. The diagnostic cells are not cleared. A rejection recorded while stopped therefore still reaches the status of the next run's first snapshot. The trace header is the checkpoint taken after boundary zero publishes, and replay! restores it rather than running boundary zero again.

init! is the only call that runs boundary zero, and a completed boundary zero is what run! and step! need. restore! and replay! are the alternatives, which start from a checkpoint in the condition's place. To start again from a saved state, call checkpoint, then restore!, then run!.

Keywords

  • t0: the start time, any real, held as a Float64 origin. Time is a keyword, never a condition entry.
  • trace: record the input trace of this run. Turn it off only to save memory in a long session, since an untraced session can never be reproduced.
  • log: keep the snapshot log of this run.
  • log_every: keep every log_every-th published boundary in the log, an integer of at least 1.
  • log_max: the most snapshots the log keeps between its first and latest, an integer of at least 1, or Inf for no bound. The first and the latest snapshots are always kept, and at the bound the log thins its middle by doubling its stride.

The four recording keywords never change the trajectory: two runs that differ only in them produce bitwise-identical trajectories. Each configures the run this call opens, and the next run follows whatever its own call declares. overlay!, restore! and replay! take the same four.

init! is refused as ServiceLifecycle while the simulation is running, and once it is errored. A recording keyword out of range is refused as ArgumentInvalid, a condition that does not resolve against the build as ConditionResolution, and a root input the condition leaves without a value as UninitializedInputs. Every refusal comes before any write, so a refused init! leaves the simulation exactly as it was. A throw inside boundary zero arrives as a StepError with pointer 0 and leaves the simulation built, with no trace, and init!, restore! and replay! legal again. init! under the same condition reproduces it.

Redstone.trim! — Function
trim!(model::Model{Float64}, problem::TrimProblem; baseline, t0::Real = 0.0,
      backend = LevenbergMarquardt()) -> TrimReport

Solve a trim problem on the model, and commit the solution through init!.

trim! searches the TrimProblem's decisions for a point where every residual sits within its tolerance. Every evaluation runs on scratch stores, so the search never writes the model. Setup layers the problem's condition at the guess over the baseline, as override(baseline, problem.condition(guess)). It then runs one establishment round: the sweep of boundary zero, with every discrete output stage run and no projection, events or discrete update. Each iteration then writes the decisions, sweeps the continuous chain and reads the residuals, with no boundaries and no events. The discrete tier does not run during the search, so its outputs hold the values the establishment round gave them. The Jacobian is exact, carried by dual numbers through the same evaluation.

The verdict is trim!'s own. After the backend returns, trim! evaluates once more at the returned point and tests each residual against its tolerance, in the residuals' own units. That test sets the report's converged, whatever status the backend gave. A solve that does not converge commits nothing and leaves the model as it was, its status included: a :built model stays :built. Non-convergence is reported in the TrimReport, never thrown.

A converged solve commits through the model's own init!, as init!(model, override(baseline, problem.condition(solution)); t0). Boundary zero can then move the committed stores off the solved point, through x_projection or an event whose guard already holds. trim! surfaces both: the events fired, in the report's fired_events with a TrimCommitEvents warning, and the residuals read again at the committed state, with a TrimCommitResiduals warning when they leave their tolerances. The checks are read from the same boundary-zero sweep, and TrimCommitChecks warns of those outside their tolerances.

A problem with no decisions, guess = (;), is legal. It skips the backend, its establishment round is its one evaluation, and the ordinary tolerance test decides. It answers whether the operating point is already an equilibrium, and commits as usual when it is.

Keywords

  • baseline: the baseline the problem's condition is layered over, at setup and at the commit. Required. Together with the problem's condition at the guess, it must give every root input a value.
  • t0: the start time of the committing boundary zero, any real, held as a Float64 origin.
  • backend: the solver, any value with a solve method. LevenbergMarquardt is the default.

The problem is checked in two collecting passes, each refused as TrimProblemInvalid. The first runs before any evaluation, with the read set's own ReadResolution failures beside the problem's faults. The second checks the residual and check returns at the guess evaluation, and again at the first seeded one. A root input the baseline and the guess's condition leave without a value is refused as UninitializedInputs. A model a Simulation has claimed is refused as ArgumentInvalid, before any check. So is a second argument that is not a TrimProblem, and a model at a scalar type other than Float64.

The value a trim solves: the decisions to vary, the condition they set, and the equations to satisfy.

A trim problem is a condition given implicitly, as a function of decisions. trim! searches the decisions for the point where every residual sits within its tolerance, and commits the condition at that point. The first seven keywords are required, and the two check keywords default to no checks.

Keywords

  • guess, lower, upper: the decisions' starting point and bounds, as NamedTuples of Float64 with one set of names. The names pair them, and setup reorders the bounds to guess's order, so their spelling order does not matter.

Redstone.LevenbergMarquardt — Type
LevenbergMarquardt(; maxiter::Integer = 100,
                   λ₀::Real = 1e-3) -> LevenbergMarquardt

The default trim backend, a dense Levenberg–Marquardt solver that stops on the problem's own tolerances.

Each iteration solves (JᵀJ + λ·diag(JᵀJ)) δ = −Jᵀr for a step, and projects the step onto the bounds. A step is accepted when it lowers the normalized residual norm ‖r ./ tol‖. λ then shrinks by a factor of 10, and a rejected step grows it by 10. The descent test and the stopping rule both measure the residuals in their tolerances' units, the test trim! applies to the result.

The solver stops with status :converged when every residual is within its tolerance, all(abs.(r) .≤ tol). It stops with :maxiter after maxiter iterations. It stops with :stalled when no step lowers the residual norm: the step is not finite, it falls below the rounding scale of the decisions it would move, or every trial is rejected until the damping passes its ceiling.

Keywords

  • maxiter: the most iterations the solver runs.
  • λ₀: the starting damping factor.

See also solve.

solve is the one method a trim solver implements. A new backend type adds one method, solve(backend::MyBackend, eval!, d0, lower, upper, tol), and trim! calls it with vectors, never names. The decisions are packed in guess's order and the residuals in tolerances' order, and the returned point unpacks by that order.

Return the linearization of the model at an operating point.

linearize returns the Jacobians A, B, C and D of the model about an operating point, as a Linearization. It is a pure query. It works on scratch stores and commits nothing. It runs no boundary zero and never writes the model.

By default the operating point is checkpoint(model), the model's state at the frame top its clock rests on, at that clock's time. about, a condition, places the operating point anywhere else, at time t0. The condition is applied over the declared defaults, and one sweep with every discrete output stage run then sets the discrete outputs.

The tap set, built by taps, names the axes. It is three lists of selectors, declaring what linearization seeds and reads. linearize seeds one direction per x tap and per u tap, and evaluates the model with dual numbers.   • about: a condition placing the operating point, or nothing for checkpoint(model).

Redstone.run! — Function
run!(sim::Simulation; pace = Inf, margin = 0.002, t_end = Inf,
     ignore_stop_requests = ()) -> Nothing

Advance the simulation frame by frame until a termination source ends the run.

A frame applies the staged inputs at its top, integrates one step and settles every boundary it reaches. It publishes a snapshot at each. The run ends when one of three sources fires. The first is t_end, when the frame that reaches it completes. The second is an honoured stop request holding in a published snapshot. The third is a stop through the control plane, seen at a frame top. A stop request ends the run at the boundary that published it, an event boundary inside a frame included, and that snapshot is the final one. t_end ends the run at the first frame top at or past it, in whole frames from t₀. run! blocks its caller until the run ends.

Each rostered device is initialized and given a task of its own as the run starts, and shut down as it ends; the loop itself runs on the calling task. The run leaves the simulation stopped, with the record that says why readable through termination. In the :replay input mode the recording also bounds the run. A run that consumes the last record halts there initialized, with no termination record, and the mode turns :live. A failure inside the loop leaves it errored instead, the cause kept on the record. With no device rostered, run! then rethrows the failure; with one or more, it logs the failure and returns. Ctrl-C is a stop, never a failure: caught at a frame top or during a pause, it ends the run stopped with ControlRequestedStop(:interrupt).

Keywords

  • pace: simulated seconds per wall-clock second, a positive real. Inf, the default, never waits, and 1 is real time. pace! retunes it during the run.
  • margin: the seconds of each pacing wait spent spinning rather than sleeping, a non-negative real. margin! retunes it during the run.
  • t_end: the time at which this advance ends the run, a non-negative real or Inf.
  • ignore_stop_requests: the stop requests this advance does not honour, :all or the paths of the requesting components. The default () honours every request.

t_end and ignore_stop_requests declare this call's stop policy alone, validated per call. A live run with t_end = Inf and no honoured request ends only through the control plane, Ctrl-C included. It is allowed, and the loop reports UnboundedRun into its own diagnostic cell. The pace inserts wall time between frames and nothing else, so a paced run is bit-identical to an unpaced one. A frame that overruns leaves debt, and debt past five frames' budget is forgiven with a DebtReanchor warning in the loop's cell. Every snapshot's status carries the pacer's record. With fewer threads than rostered devices plus one, the loop reports ThreadBudget into its cell.

run! needs an initialized simulation. It is refused as MissingInit when built, since init! or another call that opens a run must come first, and as ServiceLifecycle when running, stopped or errored. A keyword out of range is refused as ArgumentInvalid, and an ignored path that names no requester as StopRequestInvalid.

Redstone.step! — Function
step!(sim::Simulation; frames = nothing, t_plus = nothing, t_end = Inf,
      ignore_stop_requests = ()) -> Int

Advance the simulation by whole frames, synchronously, and return the number of frames advanced.

Each frame runs exactly as under run!, so a stepped simulation is bit-identical to the same frames under run!. The staged inputs still apply at each frame's top, so stage!(sim, …), then step!, then latest(sim) drives a model and checks its response one step at a time. step! never waits for the pacer, and the pacer record of its snapshots reads Inf and zeros. It spawns no device task and initializes no device, but a batch staged into a rostered device's cell while stopped is applied as usual.

Between calls the simulation stays initialized, so attach! is legal there and run! may follow, continuing from the current boundary. A termination source that fires inside the call ends the run there: the simulation is left stopped with its termination record set, and step! returns the frames advanced before the stop. A return below the frames requested is how a caller detects the stop without reading the clock. A failure inside the loop leaves the simulation errored, and step! always rethrows it.

In the :replay input mode the frames take their inputs from the recording, which bounds the advance. A step! past its end advances only to the last recorded frame, returns fewer frames than asked and turns the mode :live.

Keywords

  • frames: the number of frames to advance, an integer of at least 1. One frame when neither frames nor t_plus is given.
  • t_plus: the duration to advance, a positive finite real, in whole frames until the boundary time first covers it. Mutually exclusive with frames.
  • t_end, ignore_stop_requests: this advance's stop policy, as for run!, with the same defaults, validated per call.

step! needs an initialized simulation, as run! does: it is refused as MissingInit when built, and as ServiceLifecycle otherwise. Both frames and t_plus, or either out of range, is refused as ArgumentInvalid, and an ignored path that names no requester as StopRequestInvalid.

Redstone.replay! — Function
replay!(sim::Simulation, trc::Trace; to_boundary = nothing, to_time = nothing,
        pace = Inf, margin = 0.002, t_end = Inf, ignore_stop_requests = (),
        trace = true, log = true, log_every = 1, log_max = 65536,
        restore = true) -> Nothing

Re-drive a recorded session through the ordinary loop, with the recording supplying every frame's inputs.

Replay differs from run! in two places only. It starts from the trace's header as restore! does. No boundary zero runs, so nothing is applied twice. At each frame top, it applies the recording's batches for that frame verbatim. It drops whatever sits in the live staging cells with a ReplayDiscardedStaging warning. The replayed trajectory is bit-identical to the recorded one.

The replay halts at the recording's end, or earlier at to_boundary or to_time, always at a frame top. A replay that halts there ends initialized, never stopped, so it can be inspected, stepped with step! or continued with run!. A termination source that fires first ends it stopped, like any run. A failure inside the loop ends it errored, rethrown when no device is rostered and logged when one is, as under run!.

The recording stays attached after the call, in the :replay input mode. A later step! or run! goes on consuming the records from the halt, and no advance runs past the recording's last frame. The mode returns to :live, the recording detaching with it, when an advance halts at that last frame; live! detaches it earlier.

Replay records a new trace that inherits the old header, so its replayed prefix is bit-identical to the recording and a live continuation appends to it. Rostered devices initialize, run and read snapshots as in any run, but their writes are dropped.

restore = false attaches the recording to the simulation as it stands, and restores nothing. The simulation must be initialized, at the recording's t₀, and at a frame from the header's up to one short of the recording's last; the records apply from the frame after its own. This form replays a modified model initialized under the authored condition, or seeks: restore! a checkpoint the recording passed through, then replay from the next frame. The new trace's header is then this simulation's own checkpoint, the state the replay starts from.

Keywords

  • to_boundary: halt after the frame that publishes boundary k, a whole number from the frame the replay starts at up to the recording's length. An event boundary localized inside a frame is reproduced, but a replay cannot halt there.
  • to_time: the same halt by time, at the last frame top at or before it, k = ⌊(to_time − t₀)/h⌋ against the header's t₀. A time between two frame tops halts at the earlier one. Mutually exclusive with to_boundary.
  • pace, margin: as for run!. A paced replay is bit-identical to an unpaced one.
  • t_end, ignore_stop_requests: this replay's stop policy, as for run!, with the same defaults. When neither binds, the recording bounds the replay. A live run that ignored some requests replays under the same ignore_stop_requests.
  • trace, log, log_every, log_max: as for init!, with the same defaults. Under trace = false nothing is re-recorded.
  • restore: false to attach the recording without restoring its header.

replay! is refused as ServiceLifecycle while running, and once errored, as init! is. Under restore = false it needs an initialized simulation, and is refused as MissingInit when built and as ServiceLifecycle otherwise. A keyword out of range, or both to_boundary and to_time, is refused as ArgumentInvalid, and an ignored path that names no requester as StopRequestInvalid. A header that does not match this simulation is refused as CheckpointMismatch or ReplaySchemaMismatch before any record is read, and the records' own mismatches, such as ReplayUnknownFace, are then collected into one throw. Every refusal comes before any write.

Redstone.lifecycle — Function
lifecycle(sim::Simulation) -> Symbol

Return the simulation's lifecycle state, one of five symbols.

The state is derived at each read and never stored, and any task may read it. The five states are these.

  • :built: the buffers are allocated and boundary zero has not completed. A throw inside boundary zero returns the simulation here.
  • :initialized: consistent at a boundary and ready to advance. init! establishes it, and a completed step! returns to it.

  • :stopped: the run has ended, and its termination record is written.

Redstone.mode — Function
mode(sim::Simulation) -> Symbol

Return the input mode, :live or :replay.

Under :live they come from the staging cells, which stage! and the devices write. Under :replay they come from the recording that replay! attached. The mode is independent of the lifecycle state (:built, :initialized, :running, :stopped or :errored), which says whether the simulation may advance at all.

Redstone.live! — Function

Detach the rest of an attached recording, and set the input mode to :live.

Nothing else changes. The trajectory stands at the replay's halt, and the run's trace keeps its header and the batches it re-recorded. Redstone.Blocks.Junction — Type
Junction{In, Out, N}(f) -> Junction{In, Out, N}

A continuous primitive that publishes a fold of its N inputs as its one output.

The inputs in1 to inN are typed In, and the output out is typed Out, with out = f(in1, …, inN), the fold applied in positional order. The block is stateless. The fold f is instance data, and the type parameter F is inferred from it. A custom fold, such as a weighted blend or a mass-properties composition, is written at the site.

The fold is stateless and declares no events, so a discontinuity written into it lands wherever it lands inside a step. A clamp is fine, since its kink is second-order downstream. So is a branch on a Bool that flips at a boundary, as a saturation code does. A branch on a continuous quantity makes a mode silently, which the moded blocks such as Relay exist to declare.

See also SumJunction, Or, And, Pack.

Redstone.Blocks.Group — Type
Group

An assembly built on the fly, whose values are the ad-hoc topologies.

A Group is an assembly that holds its children and its declarations as field values. The elements of its children field, a NamedTuple of components, are its children. Its local_wires, input_wires, output_wires and sample_times are ordinary functions of the instance, which return its fields.

Redstone.Blocks.Step — Type
Step(; t_step, before = 0.0, after = 1.0, localized::Bool = true) -> Step

A continuous primitive that publishes one value before a given time and another from then on.

out publishes before until t_step and after from then on. The block is a mode-only primitive with no inputs. The mode fired picks the value, and one state event, fire, sets it once t reaches t_step. out is pinned at V. The value depends on neither state nor an input that follows the scalar, so it carries zero partials under every activation, as a Constant's does.

  • after: the value from t_step on. before and after are promoted to one V, Float64 or a static array of Float64, and taken by float, so integer values qualify.
  • localized: true for a localized step, false for a boundary-detected one.

Redstone.Blocks.LimitedIntegrator — Type
LimitedIntegrator(; lower, upper, x0 = zero(lower), localized::Bool = true) -> LimitedIntegrator

A continuous primitive that publishes the time integral of its input, held between two limits.

The block holds one continuous state q, with q̇ = in while free and q̇ = 0 while saturated, and out publishes q from stage 1. It is not a clamp. The mode saturation is read by the derivative, and four state events move it. It is a signed Int8 code, the sign of the limit in force: -1 at lower, 0 free and +1 at upper. hit_upper and hit_lower fire when q reaches a limit, and their handlers write q to the limit exactly and saturate. leave_upper and leave_lower fire when in turns strictly back into the range, and free it. An input of exactly zero at a limit keeps the mode saturated. The hit events are localized.

A second output, also saturation, publishes the code from stage 1, so it has no feedthrough. It serves an anti-windup consumer, such as a controller that gates its integrator on the code. The code flips only when an event fires, and so only on a declared boundary.

localized picks the detection policy of the leave events. Localized, the guards are sign forms gated by the mode, and the departure ends the step at the input's zero crossing. Boundary-detected, the guards are the Bool predicates. The departure then fires at the end of the step in which in first pointed back into the range, so q is held on the limit for the rest of that step. It carries an offset of at most a h² / 2 from then on, a the input's slope at its zero crossing. What the cheap form buys is that a departure costs no root-finding and splits no step, where a localized one pays about 22 trial sweeps and a boundary. The policy is the type parameter L rather than a field because the build reads it off the guard's return type.

Over a static vector, the limits and the codes are componentwise, and saturation publishes a static vector of Int8. The block declares N copies of the scalar events, one per component, named hit_upper_1 to hit_upper_N, then hit_lower_i, leave_upper_i and leave_lower_i. Each guard reads its one component and each handler writes it.

Boundary zero sets every prior to not-holding. An x0 outside the limits is therefore clamped there, and the initial mode agrees with the initial input.

Keywords

  • lower: the lower limit, below upper, componentwise over a vector.
  • upper: the upper limit.
  • x0: the initial value of q. x0, lower and upper are promoted to one V, which is Float64 or a static array of Float64, and taken by float, so integer values qualify.
  • localized: true for localized leave events, false for boundary-detected ones.

See also DiscreteLimitedIntegrator, Integrator.

Any of the nine parameters may be an input port in place of a field, spelled K_fbk = AsPort() with AsPort and typed as the field would be, an SMatrix{NU, NX, Float64, NU * NX} for K_fbk. That is how a gain schedule reaches the block. Under a Dual activation, the port carries partials, and a model that wants it frozen at its plain Float64 value routes it through Freeze.

The first form reads NX, NU and NZ off the values given, K_fbk first, then K_fwd, K_int and the trims, and passes every keyword on to the second, the explicit spelling, which takes the sizes and the same keywords. A matrix or a vector that does not fit the sizes read is refused as an ArgumentError. A size no value carries, every carrier a port or left at its default, is refused likewise, naming the explicit spelling.

u is a stage-2 output, so every input makes a feedthrough edge, whether y_direct reads it or not. An x assembled from what the plant publishes from state, and a z selected from the same, close no loop. A z_ref computed memorylessly from the block's own u closes an AlgebraicCycle classified real, since the direct law reads it. A tracking input wired from a memoryless clamp of u closes one classified artificial, since only the derivative reads it, which is why the limits live inside the block. A scheduled parameter computed memorylessly from u closes a cycle too, artificial for K_int and Tt and real for the others.

The block publishes no saturation code, since a continuous one would need a mode and events per channel for a consumer that does not exist. The gains are designed outside, from trim! and linearize.

K_int and the trims default to zero. Tt, u_min and u_max are each a real broadcast to an SVector{NU, Float64}, or a vector of length NU. Integer entries qualify.

Keywords

The nine parameters come in this order.

  • K_fbk: the NU × NX feedback gain, any AbstractMatrix of reals stored as a static matrix of Float64.
  • K_fwd: the NU × NZ feedforward gain, stored likewise.
  • K_int: the NU × NZ integral gain, stored likewise. A zero K_int is the tracker without integral action.
  • x_trim: the plant state at trim, a vector of length NX.
  • u_trim: the control input at trim, a vector of length NU.
  • z_trim: the command variables at trim, a vector of length NZ.
  • Tt: the time constant of the correction per channel, Inf to switch it off.
  • u_min: the lower limit of u per channel.
  • u_max: the upper limit of u per channel.
  • hold: true to add the inputs saturation and engaged, the parameter Hold.
  • tracking: true to add the input v, the parameter Track.

See also DiscreteLQRTracker, LQRTrackerBlock.

A discrete primitive that runs an LQR tracker about a trim point, with anti-windup.

The block takes the parameters, defaults, ports, outputs and law of LQRTracker to the discrete tier. A store field q stands in for its continuous state, and a second, saturated, holds its code. Δt is the component's own period. The inputs are x, z and z_ref, and the two outputs come from stage 2,

u_raw = u_trim + K_fwd (z_ref - z_trim) - K_fbk (x - x_trim) + q

and u, its clamp to [u_min, u_max] per channel. Each tick moves the integral term by forward Euler and the correction's exact step,

q⁺ = q + Δt ε + β (ref - u_raw),    β = 1 - exp(-Δt / Tt)

with its slots ε and ref filled over the two anti-windup axes and the integrator input e = K_int (z_ref - z), channel by channel, by the table of ControllerBlock.

hold adds the inputs saturation and engaged, and a channel not engaged without tracking freezes. tracking adds the input v. tracking = true with a Tt given infinite in any channel is refused as an ArgumentError. With the hold, the reference falls back to u in each channel that is free. All of this is as in LQRTracker. Every Tt is stable: Tt = Inf switches the correction off, and Tt = 0 is legal and brings u_raw to the reference by the next tick, so a channel not engaged with tracking follows v exactly.

The ports, the nine parameters and their types, the AsPort spelling, the size inference and the explicit spelling, the second form, are those of LQRTracker, and so are the refusals.

A third output, saturated, publishes the Int8 code of the block's own clamp per channel at SVector{NU, Int8}: 1 with u_raw at or above u_max, -1 at or below u_min and 0 between. s_update writes it to the store from u_raw at the tick, and y_state publishes it from stage 1 at the next. It is therefore one tick stale, and flips only on a tick boundary. It serves the hold of an outer block in a cascade, wired to its input saturation, each channel reaching a scalar consumer through Unpack{Int8, NU}. The outer integrator takes one extra step before the hold engages, and as a stage-1 port the code closes no cycle through the outer block's u. The block never reads its own code, since its own windup is the correction's.

u is a stage-2 output, so every input makes a feedthrough edge, as for LQRTracker. A z_ref or a tracking input computed memorylessly from the block's own u is refused as an AlgebraicCycle classified real: a discrete member's dependences are traced from its structure, so no hop is named dead. A scheduled parameter computed memorylessly from u closes a cycle likewise.
